Grouped-Query Attention: one set of keys for several heads

Ainslie et al., 2023 — and Shazeer, 2019

The whole implementation is one repeat. Getting it in the wrong place produces plausible garbage and no error.

Download gqa_from_scratch.py — everything below runs from it. NumPy only, under a second.

I read the KV-cache page — I wrote it — and it ends on arithmetic. The cache is what stops you serving the model; shrink kv_heads and the cache shrinks by exactly the same factor. Fine. Then I opened a real implementation to see what "shrink kv_heads" is as code, and it was six lines, four of them a tensor reshape I couldn't read. Nobody told me the change is one repeat in the right place, and that the whole class of bugs here is putting it in the wrong one.

A read replica shared by several app servers

You've sized this before:

app_server_0 -> replica_0     # one replica each. Perfect isolation,
app_server_1 -> replica_1     # and you pay for eight replicas.
...
app_server_7 -> replica_7

Replicas are the expensive part, so you consolidate. Eight app servers, two replicas, four servers per replica: 

app_server_0..3 -> replica_0   # each server still does its own work,
app_server_4..7 -> replica_1   # but they read the same snapshot

That is grouped-query attention, exactly. Query heads are the app servers — every one keeps its own Wq, its own scores, its own output. Key and value heads are the replicas, and they're what you store. Multi-head is one replica per server. Multi-query is one replica for the whole fleet. GQA is the middle setting, and like every capacity decision you've made, the question is how much shared staleness you can tolerate.

Why anyone did this

Not for FLOPs. Decoding is memory-bound: each step drags the weights and the whole cache across the memory bus to do a rounding error's worth of arithmetic. The cache is the term that grows with every token and every concurrent user, and kv_heads is the only factor in it that the architecture gets to choose. The KV-cache page has that table — bytes per token, the 4× and 32× reductions, the point where the cache outgrows the checkpoint. I'm not reprinting it. This page is the forward pass and what the sharing costs.

Multi-query came first: Shazeer, 2019, "Fast Transformer Decoding: One Write-Head is All You Need", a short paper whose whole argument is decoding speed. GQA arrived in 2023 with two claims — that the useful setting is in between, and that you don't have to pre-train it. You can convert a checkpoint you already have.

The one formula

headi = Attention(Qi, K⌊i/g⌋, V⌊i/g⌋),   g = nheads / nkv

That's the entire paper as notation. The subscript on K and V is the only thing that changed since 2017, where it read Ki, Vi. Read the layer as pipeline stages:

StepShapeWhat it does
X @ W_q(n_heads, n, head_dim)All the query heads. Unchanged in every variant
X @ W_k, X @ W_v(n_kv, n, head_dim)The narrower projections. This is the change, and this is what gets cached
repeat_kv_heads→ (n_heads, n, head_dim)The whole implementation. Expand each KV head g times so the queries have something to meet
Q @ KT / √d(n_heads, n, n)Ordinary scaled dot-product. Full head count, full cost
softmax @ V(n_heads, n, head_dim)Weighted blend, per head
merge @ W_o(n, d_model)Concatenate heads, project out. Also unchanged
Note where the repeat sits: after the projection, before the matmul, and never on the cache. You store the narrow K and V and expand them at compute time. Expand first and you've written multi-head attention with extra steps.

One function, three variants

The three names are one function with one argument. Pass n_kv_heads = n_heads and it's multi-head. Pass 1 and it's multi-query. Pass anything in between and it's grouped-query. The script prints the shape at every step so you can see that the only line that differs is the K/V projection width — everything downstream is identical.

The repeat, and the bug nobody catches

You have 2 KV heads and need 8. There are two obvious ways to stretch a list of 2 into a list of 8, and NumPy gives you both: 

np.repeat(kv, 4, axis=0)   -> [kv0 kv0 kv0 kv0 kv1 kv1 kv1 kv1]  # block
np.tile(kv, (4, 1, 1))     -> [kv0 kv1 kv0 kv1 kv0 kv1 kv0 kv1]  # interleaved

Same shape. Same dtype. No error, either way. But every checkpoint on disk was saved under the convention that query head i belongs to KV head i // g — contiguous blocks — so only the first one is right. Llama's reference implementation calls the operation repeat_kv and documents it as torch.repeat_interleave over the head axis, which is the block version. 

  n_heads=8, n_kv_heads=2, group=4
  query head       : [0, 1, 2, 3, 4, 5, 6, 7]
  block  -> kv head: [0, 0, 0, 0, 1, 1, 1, 1]  matches i // group
  interl -> kv head: [0, 1, 0, 1, 0, 1, 0, 1]  matches i %  n_kv
  convention (i // group): [0, 0, 0, 0, 1, 1, 1, 1]

  output shapes equal?            True
  no exception raised?            True
  max |block - interleave|        0.2661
  mean |block|                    0.0651
  -> same shape, no error, different answer. That is the bug.
The error is four times the size of the signal. Not a crash, not a NaN, not a shape mismatch — a model that loads, runs, and talks nonsense. If you ever port weights between frameworks and the outputs are "close but wrong", this is the first thing to check.

At n_kv = n_heads, it is exactly multi-head

Worth proving rather than asserting, because it's how you sanity-check any GQA implementation you write: set the group size to 1 and the repeat becomes a no-op, so the function must reduce to plain 2017 attention. The script computes multi-head the long way, with no repeat call anywhere, and diffs. 

  max |grouped(n_kv=8) - plain multi-head| = 0.000e+00
  bit-identical?                            True
  group size is 1, so np.repeat is a no-op. Same code path.

Not "to float precision" — bit-identical, because np.repeat with a count of 1 returns the same numbers in the same order. Your first test for any implementation of this: does it still match multi-head when you turn the sharing off?

What sharing actually costs

Now the honest part. Heads exist because they look for different things. Force four of them through one set of keys and they can't all get what they want. To show that mechanically I build eight query heads whose ideal key is a different token each, then mean-pool the key heads into fewer and fewer groups and measure how far the output drifts from the ideal. 

    n_kv | group |  max |out - ideal| | mean |out - ideal|
       8 |     1 |           0.0000 |           0.0000
       4 |     2 |           0.0321 |           0.0092
       2 |     4 |           0.5660 |           0.1723
       1 |     8 |           1.4787 |           0.4548

  per-head error at n_kv=2 (heads 0-3 share, heads 4-7 share):
    head 0  group 0  error 0.3688   argmax attends to token 0 (wanted 0)
    head 1  group 0  error 0.4308   argmax attends to token 1 (wanted 1)
    head 2  group 0  error 0.3620   argmax attends to token 2 (wanted 2)
    head 3  group 0  error 0.4960   argmax attends to token 3 (wanted 3)
    head 4  group 1  error 0.2810   argmax attends to token 4 (wanted 4)
    head 5  group 1  error 0.3821   argmax attends to token 5 (wanted 5)
    head 6  group 1  error 0.2884   argmax attends to token 6 (wanted 6)
    head 7  group 1  error 0.5660   argmax attends to token 7 (wanted 7)

The shape of it is what matters. Halving the KV heads is nearly free (0.0092); quartering costs an order of magnitude more; collapsing to one costs another factor of three. The heads still point at the right token — the argmax is right in every row — but the distribution around it has been dragged toward the group average, and the output carries that. That's the graceful-degradation curve GQA is trading on.

This is a mechanical illustration on vectors I constructed to make the point, not a quality measurement. The paper's quality claims — that GQA lands close to multi-head while MQA loses more — are the paper's, measured on real tasks with real uptrained checkpoints. Don't quote my numbers as evidence about language models; they're evidence about averaging.

Parameters shrink a little. FLOPs don't move at all.

The interview question here is "so GQA is faster because it does less arithmetic, right?" — and no. The keys are expanded back to the full head count before the matmul, so the attention does exactly the same work. Wq and Wo are untouched. Only Wk and Wv get narrower, which is a rounding error against total parameters — and the cache, which is not. 

  Llama-2-7B-shaped layer: d_model=4096, n_heads=32, head_dim=128, seq=2048

    variant     | n_kv | W_k+W_v params | vs MHA | attn MACs/token
    multi-head  |   32 |     33,554,432 |   1.0x | 16,777,216
    GQA-8       |    8 |      8,388,608 |   4.0x | 16,777,216
    GQA-4       |    4 |      4,194,304 |   8.0x | 16,777,216
    multi-query |    1 |      1,048,576 |  32.0x | 16,777,216

  W_q and W_o are untouched: 16,777,216 params each, in every variant.

Same column, four times. The win is memory traffic, not maths: fewer bytes to read per decode step, and a cache small enough to batch more users against. Bytes per token, and how fast that becomes your whole hardware bill, is the KV-cache page.

Uptraining: the part of the paper everyone forgets

The paper is titled Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints, and that title is the contribution. Nobody wants to pre-train a 70B model again to change one hyperparameter. So: take the multi-head checkpoint you already have, mean-pool the key and value heads inside each group, and train briefly — the paper reports doing it with a small fraction of the original pre-training compute.

Mean-pooling, specifically, and not "keep head 0". W_k is (d_model, n_heads × head_dim); view it as (d_model, n_kv, group, head_dim), average over the group axis, flatten. Four lines. The mean is the vector closest to all group members at once; selecting one throws the other g−1 away. So mean-pooling starts the short training run from a better place. That's the whole argument, and it's measurable: 

  original multi-head output, mean |y| = 0.0673

    n_kv | mean-pooled err | first-head err | first/mean
       4 |          0.0414 |         0.0671 |       1.62x
       2 |          0.0580 |         0.1005 |       1.73x
       1 |          0.0653 |         0.0794 |       1.22x

Mean-pooling is closer at every group size — up to 1.7× closer. Note also that at n_kv=1 the error is the same size as the signal itself: conversion alone does not give you a working model. It gives you an initialisation. The brief training run is not optional, it's the point. That distinction is the thing to have straight if someone asks you how Llama-2 70B got its GQA.

Where this landed. Llama-2's 70B model uses GQA, and most open models released since have followed. The notable dissent is DeepSeek, which compresses K and V into a shared latent vector instead of sharing heads — that's multi-head latent attention, a different answer to the same cache problem. The rest of the Llama recipe — RMSNorm, SwiGLU, RoPE — is on its own page, and the attention this all modifies is here.

Repeat எங்கே இருக்கிறது என்பதைக் கவனியுங்கள்: projection-க்குப் பிறகு, matmul-க்கு முன், cache-ல் ஒருபோதும் இல்லை. குறுகிய K, V-ஐ store செய்து, compute நேரத்தில் விரிவாக்குகிறீர்கள். முதலிலேயே விரிவாக்கினால் நீங்கள் எழுதியது கூடுதல் step-களுடன் கூடிய multi-head attention தான்.

அந்த repeat, யாரும் பிடிக்காத bug

உங்களிடம் 2 KV head இருக்கின்றன, 8 வேண்டும். 2 உள்ள list-ஐ 8 ஆக நீட்ட இரண்டு வெளிப்படையான வழிகள் உள்ளன, NumPy இரண்டையும் தருகிறது: 

np.repeat(kv, 4, axis=0)   -> [kv0 kv0 kv0 kv0 kv1 kv1 kv1 kv1]  # block
np.tile(kv, (4, 1, 1))     -> [kv0 kv1 kv0 kv1 kv0 kv1 kv0 kv1]  # interleaved

ஒரே shape. ஒரே dtype. இரண்டிலும் error இல்லை. ஆனால் disk-ல் உள்ள ஒவ்வொரு checkpoint-ம் query head i என்பது KV head i // g-க்கு சொந்தம் என்ற convention-ல்தான் — அதாவது தொடர்ச்சியான block-களாக — சேமிக்கப்பட்டது, அதனால் முதலாவது மட்டுமே சரி. Llama-வின் reference implementation இந்த operation-ஐ repeat_kv என்று அழைத்து, head axis மேல் torch.repeat_interleave என்று ஆவணப்படுத்துகிறது — அதுதான் block வடிவம்.

Error என்பது signal-ஐ விட நான்கு மடங்கு பெரியது. Crash இல்லை, NaN இல்லை, shape mismatch இல்லை — load ஆகி, ஓடி, முட்டாள்தனமாகப் பேசும் ஒரு model. Framework-களுக்கு இடையே weights-ஐ port செய்யும்போது output "கிட்டத்தட்ட சரி, ஆனால் தவறு" என்று இருந்தால், முதலில் சரிபார்க்க வேண்டியது இதைத்தான்.

Block-um interleave-um ore shape, ore dtype, error-e illa — aana answer vera. Disk-la irukka checkpoint ellam i // g convention-la save aagirukku, so block dhaan sari.

n_kv = n_heads ஆனால், அது சரியாக multi-head தான்

இதை வெறுமனே சொல்லாமல் நிரூபிப்பது மதிப்புள்ளது, ஏனெனில் நீங்கள் எழுதும் எந்த GQA implementation-ஐயும் இப்படித்தான் sanity-check செய்வீர்கள்: group size-ஐ 1 ஆக வையுங்கள், repeat ஒரு no-op ஆகிவிடும், அதனால் function சாதாரண 2017 attention-ஆகச் சுருங்க வேண்டும். Script multi-head-ஐ நீளமான வழியில், எங்கும் repeat அழைப்பு இல்லாமல் கணக்கிட்டு, வித்தியாசத்தைப் பார்க்கிறது.

  group size is 1, so np.repeat is a no-op. Same code path.

"Float precision அளவுக்கு" அல்ல — bit-identical, ஏனெனில் count 1-உடன் np.repeat அதே எண்களை அதே வரிசையில் திருப்பித் தருகிறது. இதன் எந்த implementation-க்கும் உங்கள் முதல் test: பகிர்வை off செய்தால் அது இன்னும் multi-head-உடன் பொருந்துகிறதா?

பகிர்வு உண்மையில் என்ன விலை கேட்கிறது

இப்போது நேர்மையான பகுதி. Head-கள் இருப்பதே அவை வெவ்வேறு விஷயங்களைத் தேடுவதால்தான். அவற்றில் நான்கை ஒரே set key வழியாகத் திணித்தால் எல்லாவற்றுக்கும் வேண்டியது கிடைக்காது. இதை இயந்திரத்தனமாகக் காட்ட, ஒவ்வொன்றுக்கும் வெவ்வேறு token-ஐ ideal key ஆகக் கொண்ட எட்டு query head-களை உருவாக்கி, பிறகு key head-களை மேலும் மேலும் குறைவான group-களாக mean-pool செய்து, output ideal-லிருந்து எவ்வளவு விலகுகிறது என்று அளக்கிறேன்.

Head-கள் இன்னும் சரியான token-ஐத்தான் சுட்டிக்காட்டுகின்றன — ஒவ்வொரு வரியிலும் argmax சரி — ஆனால் அதைச் சுற்றியுள்ள distribution group சராசரியை நோக்கி இழுக்கப்பட்டுள்ளது, output அதைச் சுமக்கிறது. GQA வியாபாரம் செய்யும் graceful-degradation வளைவு அதுதான்.

இது நான் இந்தக் கருத்தைக் காட்டவே உருவாக்கிய vector-கள் மேல் செய்த ஒரு இயந்திரத்தனமான விளக்கம், quality அளவீடு அல்ல. Paper-ன் quality கூற்றுகள் — GQA multi-head-க்கு அருகில் வருகிறது, MQA அதிகம் இழக்கிறது — அவை paper-ன் கூற்றுகள், உண்மையான task-களில் உண்மையான uptrained checkpoint-களுடன் அளக்கப்பட்டவை. என் எண்களை language model பற்றிய ஆதாரமாக மேற்கோள் காட்டாதீர்கள்; அவை சராசரி எடுப்பதைப் பற்றிய ஆதாரம்.

Parameter கொஞ்சம் குறையும். FLOPs சிறிதும் அசையாது.

இங்கு வரும் interview கேள்வி "அப்படியானால் GQA குறைவான கணக்கு செய்வதால் வேகமானது, சரிதானே?" — இல்லை. Matmul-க்கு முன் key-கள் முழு head எண்ணிக்கைக்கு விரிவாக்கப்படுகின்றன, அதனால் attention அதே வேலையைத்தான் செய்கிறது. Wq-ம் Wo-ம் தொடப்படவில்லை. Wk, Wv மட்டுமே குறுகுகின்றன — மொத்த parameter-க்கு எதிராக அது ஒரு rounding error — மற்றும் cache, அது rounding error அல்ல.

Uptraining: paper-ல் எல்லோரும் மறக்கும் பகுதி

Paper-ன் தலைப்பு Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints, அந்தத் தலைப்புதான் அதன் பங்களிப்பு. ஒரு hyperparameter-ஐ மாற்ற 70B model-ஐ மீண்டும் pre-train செய்ய யாரும் விரும்பவில்லை. அதனால்: ஏற்கனவே உங்களிடம் இருக்கும் multi-head checkpoint-ஐ எடுத்து, ஒவ்வொரு group-க்குள்ளும் key மற்றும் value head-களை mean-pool செய்து, சிறிது நேரம் train செய்யுங்கள் — original pre-training compute-ன் ஒரு சிறிய பகுதியில் இதைச் செய்ததாக paper சொல்கிறது.

குறிப்பாக mean-pooling, "head 0-ஐ வைத்துக்கொள்" அல்ல. W_k என்பது (d_model, n_heads × head_dim); அதை (d_model, n_kv, group, head_dim) ஆகப் பாருங்கள், group axis மேல் சராசரி எடுங்கள், flatten செய்யுங்கள். நான்கு வரிகள். சராசரிதான் group-ல் உள்ள எல்லா உறுப்பினர்களுக்கும் ஒரே சமயத்தில் மிக அருகில் இருக்கும் vector; ஒன்றைத் தேர்ந்தெடுத்தால் மற்ற g−1-ஐத் தூக்கி எறிகிறீர்கள். அதனால் mean-pooling அந்தச் சிறிய training run-ஐ ஒரு சிறந்த இடத்திலிருந்து தொடங்குகிறது. முழு வாதமும் அதுதான், அதை அளக்கவும் முடியும்: 

  original multi-head output, mean |y| = 0.0673

    n_kv | mean-pooled err | first-head err | first/mean
       4 |          0.0414 |         0.0671 |       1.62x
       2 |          0.0580 |         0.1005 |       1.73x
       1 |          0.0653 |         0.0794 |       1.22x

ஒவ்வொரு group size-லும் mean-pooling அருகில் இருக்கிறது — 1.7× வரை அருகில். n_kv=1-ல் error signal-ன் அளவுக்கே இருக்கிறது என்பதையும் கவனியுங்கள்: conversion மட்டும் உங்களுக்கு வேலை செய்யும் model-ஐத் தராது. அது ஒரு initialisation-ஐத் தருகிறது. அந்தச் சிறிய training run விருப்பத்தேர்வு அல்ல, அதுதான் விஷயம். Llama-2 70B-க்கு GQA எப்படி வந்தது என்று யாராவது கேட்டால் தெளிவாக இருக்க வேண்டிய வேறுபாடு அதுதான்.

இது எங்கே வந்து நின்றது. Llama-2-ன் 70B model GQA பயன்படுத்துகிறது, அதற்குப் பிறகு வெளியான பெரும்பாலான open model-களும் அதையே பின்பற்றின. குறிப்பிடத்தக்க மாற்றுக் கருத்து DeepSeek — அது head-களைப் பகிர்வதற்குப் பதிலாக K, V-ஐ ஒரு பகிரப்பட்ட latent vector-ஆகச் சுருக்குகிறது — அதுதான் multi-head latent attention, அதே cache பிரச்சனைக்கு வேறொரு பதில். மீதி Llama recipe — RMSNorm, SwiGLU, RoPE — தனிப் பக்கத்தில் இருக்கிறது, இவை எல்லாம் மாற்றும் attention இங்கே.

मैंने KV-cache वाला पेज पढ़ा — वह मैंने ही लिखा है — और वह गणित पर ख़त्म होता है। Model को serve करने से जो रोकता है वह cache है; kv_heads घटाइए और cache ठीक उसी अनुपात में घट जाता है। ठीक। फिर मैंने एक असली implementation खोली यह देखने के लिए कि "kv_heads घटाना" code में क्या है — छह लाइनें, जिनमें चार एक tensor reshape थीं जो मुझे पढ़नी ही नहीं आईं। किसी ने नहीं बताया कि यह बदलाव सही जगह पर एक repeat है, और यहाँ के bugs की पूरी नस्ल उसे ग़लत जगह रख देने से पैदा होती है।

ध्यान दें: English technical words (grouped-query, multi-query, multi-head, key, value, query, head, repeat, checkpoint…) मैंने वैसे ही रखे हैं। क्योंकि code में और बाक़ी papers में आपको वही शब्द दिखेंगे। समझ हिंदी में, शब्दावली English में।

यही grouped-query attention है, बिल्कुल वैसा ही। Query heads app servers हैं — हर एक के पास अपना Wq, अपने scores, अपना output। Key और value heads replicas हैं, और वही आप store करते हैं। Multi-head यानी हर server का अपना replica। Multi-query यानी पूरे fleet के लिए एक replica। GQA बीच वाली setting है, और आपके हर capacity फ़ैसले की तरह सवाल यही है कि साझा staleness आप कितनी बर्दाश्त कर सकते हैं।

यह किया ही क्यों गया

FLOPs के लिए नहीं। Decoding memory-bound है: हर step में weights और पूरा cache memory bus के पार खींचे जाते हैं, और गणित उतना ही होता है जितना एक rounding error। हर token और हर concurrent user के साथ जो बढ़ता है वह cache है, और उसमें architecture जिसे चुन सकती है वह अकेला factor kv_heads है। वह table — प्रति token bytes, 4× और 32× की कमी, वह बिंदु जहाँ cache checkpoint से बड़ा हो जाता है — KV-cache पेज पर है। मैं उसे दोबारा नहीं छाप रहा। यह पेज forward pass है, और साझा करने की क़ीमत।

Multi-query पहले आया: Shazeer, 2019, "Fast Transformer Decoding: One Write-Head is All You Need" — एक छोटा paper जिसकी पूरी दलील decoding speed है। GQA 2023 में दो दावों के साथ आया — कि काम की setting बीच में है, और कि उसे pre-train करने की ज़रूरत नहीं। जो checkpoint आपके पास पहले से है, उसी को बदला जा सकता है।

वह एक सूत्र

headi = Attention(Qi, K⌊i/g⌋, V⌊i/g⌋),   g = nheads / nkv

Notation में यही पूरा paper है। 2017 में जो Ki, Vi लिखा था, उसके बाद बदली है तो सिर्फ़ K और V की subscript। Layer को pipeline stages की तरह पढ़िए:

ध्यान दीजिए repeat कहाँ बैठता है: projection के बाद, matmul से पहले, और cache पर कभी नहीं। आप सँकरे K और V store करते हैं और compute के समय उन्हें फैलाते हैं। पहले फैला दिया तो आपने अतिरिक्त steps वाला multi-head attention ही लिखा है।

एक function, तीन variants

तीनों नाम एक ही function हैं, एक ही argument के साथ। n_kv_heads = n_heads दीजिए तो multi-head। 1 दीजिए तो multi-query। बीच का कुछ भी दीजिए तो grouped-query। Script हर step पर shape print करती है ताकि आप देख सकें कि फ़र्क़ सिर्फ़ एक लाइन में है — K/V projection की चौड़ाई — उसके आगे सब कुछ एक जैसा है।

तीनों blocks में एक ही लाइन बदलती है: repeat से पहले K और V के shapes। यही paper है। Repeat के बाद जो है वह 2017 का वही code है जो आप पहले से जानते हैं।

वह repeat, और वह bug जो किसी को नहीं पकड़ में आता

आपके पास 2 KV heads हैं और चाहिए 8। 2 की list को 8 तक खींचने के दो ज़ाहिर तरीक़े हैं, और NumPy दोनों देता है: 

np.repeat(kv, 4, axis=0)   -> [kv0 kv0 kv0 kv0 kv1 kv1 kv1 kv1]  # block
np.tile(kv, (4, 1, 1))     -> [kv0 kv1 kv0 kv1 kv0 kv1 kv0 kv1]  # interleaved

वही shape। वही dtype। दोनों में कोई error नहीं। पर disk पर हर checkpoint इस convention के तहत सहेजा गया है कि query head i KV head i // g का है — यानी लगातार blocks — इसलिए सही सिर्फ़ पहला है। Llama का reference implementation इस operation को repeat_kv कहता है और उसे head axis पर torch.repeat_interleave के रूप में दर्ज करता है, जो block वाला रूप है। 

  n_heads=8, n_kv_heads=2, group=4
  query head       : [0, 1, 2, 3, 4, 5, 6, 7]
  block  -> kv head: [0, 0, 0, 0, 1, 1, 1, 1]  matches i // group
  interl -> kv head: [0, 1, 0, 1, 0, 1, 0, 1]  matches i %  n_kv
  convention (i // group): [0, 0, 0, 0, 1, 1, 1, 1]

  output shapes equal?            True
  no exception raised?            True
  max |block - interleave|        0.2661
  mean |block|                    0.0651
  -> same shape, no error, different answer. That is the bug.
Error signal से चार गुना बड़ा है। न crash, न NaN, न shape mismatch — एक ऐसा model जो load होता है, चलता है, और बकवास बोलता है। अगर कभी frameworks के बीच weights port करें और outputs "क़रीब पर ग़लत" लगें, तो सबसे पहले यही जाँचिए।

n_kv = n_heads पर यह ठीक-ठीक multi-head है

इसे कहने से बेहतर है साबित करना, क्योंकि आप जो भी GQA implementation लिखेंगे उसकी sanity-check यही है: group size 1 कर दीजिए, repeat no-op बन जाता है, तो function को सादे 2017 attention में सिमट जाना चाहिए। Script multi-head को लंबे रास्ते से, कहीं भी repeat बुलाए बिना, गणना करती है और फ़र्क़ निकालती है। 

  max |grouped(n_kv=8) - plain multi-head| = 0.000e+00
  bit-identical?                            True
  group size is 1, so np.repeat is a no-op. Same code path.

"Float precision तक" नहीं — bit-identical, क्योंकि count 1 के साथ np.repeat वही संख्याएँ उसी क्रम में लौटाता है। इसके किसी भी implementation के लिए आपका पहला test: sharing बंद कर दें तो क्या वह अब भी multi-head से मेल खाता है?

साझा करने की असली क़ीमत

अब ईमानदार हिस्सा। Heads इसलिए हैं क्योंकि वे अलग-अलग चीज़ें ढूँढ़ते हैं। चार को एक ही set keys से गुज़ार दीजिए तो सबको वह नहीं मिलेगा जो चाहिए। इसे यांत्रिक रूप से दिखाने के लिए मैं आठ query heads बनाता हूँ जिनका ideal key अलग-अलग token है, फिर key heads को कम से कम groups में mean-pool करके नापता हूँ कि output ideal से कितना खिसकता है।

असली बात इसका आकार है। KV heads आधे करना लगभग मुफ़्त है (0.0092); चौथाई करना एक order of magnitude महँगा; एक पर सिकोड़ना उससे भी तीन गुना। Heads अब भी सही token की ओर इशारा करते हैं — हर पंक्ति में argmax सही है — पर उसके आसपास का distribution group के औसत की ओर खिंच गया है, और output वही ढोता है। यही वह graceful-degradation curve है जिस पर GQA का सौदा टिका है।

यह उन vectors पर एक यांत्रिक उदाहरण है जो मैंने बात समझाने के लिए ख़ुद बनाए हैं, quality की माप नहीं। Paper के quality दावे — कि GQA multi-head के क़रीब रहता है जबकि MQA ज़्यादा खोता है — paper के हैं, असली tasks पर असली uptrained checkpoints के साथ नापे गए। मेरे नंबरों को language models के बारे में सबूत की तरह मत उद्धृत कीजिए; वे averaging के बारे में सबूत हैं।

Parameters थोड़े घटते हैं। FLOPs ज़रा भी नहीं हिलते।

यहाँ का interview सवाल है "तो GQA तेज़ है क्योंकि वह कम गणित करता है, है न?" — नहीं। Matmul से पहले keys पूरी head संख्या तक फैला दी जाती हैं, इसलिए attention बिल्कुल उतना ही काम करता है। Wq और Wo अछूते हैं। सिर्फ़ Wk और Wv सँकरे होते हैं, जो कुल parameters के मुक़ाबले एक rounding error है — और cache, जो नहीं है।

वही column, चार बार। जीत memory traffic की है, गणित की नहीं: हर decode step पर कम bytes पढ़ने हैं, और cache इतना छोटा कि ज़्यादा users एक साथ batch किए जा सकें। प्रति token bytes, और वह कितनी जल्दी आपका पूरा hardware bill बन जाता है, यह KV-cache पेज है।

Uptraining: paper का वह हिस्सा जो सब भूल जाते हैं

Paper का शीर्षक है Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints, और वही शीर्षक उसका योगदान है। एक hyperparameter बदलने के लिए 70B model दोबारा pre-train कोई नहीं करना चाहता। तो: जो multi-head checkpoint आपके पास है उसे लीजिए, हर group के भीतर key और value heads को mean-pool कीजिए, और थोड़ी देर train कीजिए — paper बताता है कि यह मूल pre-training compute के एक छोटे से अंश में हो जाता है।

ख़ास तौर पर mean-pooling, "head 0 रख लो" नहीं। W_k है (d_model, n_heads × head_dim); उसे (d_model, n_kv, group, head_dim) की तरह देखिए, group axis पर औसत लीजिए, flatten कीजिए। चार लाइनें। औसत वह vector है जो group के सभी सदस्यों के एक साथ सबसे क़रीब है; किसी एक को चुनना बाक़ी g−1 को फेंक देना है। इसलिए mean-pooling उस छोटे training run को बेहतर जगह से शुरू करता है। यही पूरी दलील है, और यह नापी जा सकती है: 

  original multi-head output, mean |y| = 0.0673

    n_kv | mean-pooled err | first-head err | first/mean
       4 |          0.0414 |         0.0671 |       1.62x
       2 |          0.0580 |         0.1005 |       1.73x
       1 |          0.0653 |         0.0794 |       1.22x

हर group size पर mean-pooling ज़्यादा क़रीब है — 1.7× तक क़रीब। यह भी देखिए कि n_kv=1 पर error signal जितना ही बड़ा है: अकेला conversion आपको चलता हुआ model नहीं देता। वह एक initialisation देता है। वह छोटा training run वैकल्पिक नहीं है, वही असल बात है। कोई पूछे कि Llama-2 70B को उसका GQA कैसे मिला, तो यही फ़र्क़ साफ़ होना चाहिए।

यह कहाँ जाकर टिका। Llama-2 का 70B model GQA इस्तेमाल करता है, और उसके बाद रिलीज़ हुए ज़्यादातर open models ने वही राह ली। उल्लेखनीय असहमति DeepSeek की है, जो heads साझा करने के बजाय K और V को एक साझा latent vector में दबा देता है — वह है multi-head latent attention, उसी cache समस्या का दूसरा जवाब। बाक़ी Llama recipe — RMSNorm, SwiGLU, RoPE — अपने अलग पेज पर है, और यह सब जिस attention को बदलते हैं वह यहाँ है।

# THE WHOLE IMPLEMENTATION. One repeat, in the right place.
#
# kv is (n_kv_heads, n, head_dim). We need (n_heads, n, head_dim) so
# every query head has a key head to talk to.
#
#   "block"      np.repeat -> [kv0 kv0 kv0 kv0 kv1 kv1 kv1 kv1]
#                             head i uses kv head i // group  <-- right
#   "interleave" np.tile   -> [kv0 kv1 kv0 kv1 kv0 kv1 kv0 kv1]
#                             head i uses kv head i %  n_kv   <-- wrong
#
# Both produce the correct SHAPE. Only one matches the convention every
# checkpoint on disk was saved with. Getting it wrong raises nothing.
def repeat_kv_heads(kv, n_heads, mode="block"):
    n_kv_heads = kv.shape[0]
    if n_heads % n_kv_heads != 0:
        raise ValueError(
            f"n_heads={n_heads} not divisible by n_kv_heads={n_kv_heads}: "
            "groups must be equal-sized"
        )
    group = n_heads // n_kv_heads
    if mode == "block":
        return np.repeat(kv, group, axis=0)   # head i -> kv head i // group
    if mode == "interleave":
        return np.tile(kv, (group, 1, 1))     # head i -> kv head i % n_kv
    raise ValueError(f"unknown repeat mode {mode!r}")


# This ONE function is multi-head, multi-query and grouped-query. The
# only difference is how many rows K and V arrive with.
#
#   Q  (n_heads,    n, head_dim)
#   K  (n_kv_heads, n, head_dim)   n_kv == n_heads -> multi-head
#   V  (n_kv_heads, n, head_dim)   n_kv == 1       -> multi-query
#                                  in between      -> grouped-query
def attention(Q, K, V, mode="block", causal=False, verbose=False):
    n_heads, n, head_dim = Q.shape
    K = repeat_kv_heads(K, n_heads, mode)
    V = repeat_kv_heads(V, n_heads, mode)

    scores = Q @ K.transpose(0, 2, 1) / np.sqrt(head_dim)   # (H, n, n)
    if causal:
        mask = np.tril(np.ones((n, n), dtype=bool))
        scores = np.where(mask, scores, -np.inf)
    weights = softmax(scores, axis=-1)
    out = weights @ V                                       # (H, n, dim)
    return out, weights


# One attention layer. n_kv_heads picks the variant. W_q and W_o do not
# move; only W_k and W_v get narrower.
def forward(X, W, n_heads, n_kv_heads, head_dim, mode="block"):
    Q = split_heads(X @ W["W_q"], n_heads, head_dim)
    K = split_heads(X @ W["W_k"], n_kv_heads, head_dim)
    V = split_heads(X @ W["W_v"], n_kv_heads, head_dim)
    out, _ = attention(Q, K, V, mode=mode)
    merged = out.transpose(1, 0, 2).reshape(X.shape[0], n_heads * head_dim)
    return merged @ W["W_o"]


# UPTRAINING, the paper's actual contribution. You do not train a GQA
# model from scratch. You take an existing multi-head checkpoint and
# MEAN-POOL the key and value heads inside each group, then train
# briefly. The mean is the projection closest to all group members;
# picking one head throws the other g-1 away.
def convert_checkpoint(W_mha, n_heads, n_kv_heads, head_dim, how="mean"):
    group = n_heads // n_kv_heads
    out = {"W_q": W_mha["W_q"].copy(), "W_o": W_mha["W_o"].copy()}
    for name in ("W_k", "W_v"):
        w = W_mha[name].reshape(-1, n_kv_heads, group, head_dim)
        if how == "mean":
            w = w.mean(axis=2)            # mean-pool inside each group
        elif how == "first":
            w = w[:, :, 0, :]             # keep head 0, bin the rest
        out[name] = w.reshape(-1, n_kv_heads * head_dim)
    return out

On the maths anxiety

There isn't any here, and that's not me being encouraging. GQA needs one idea: the mean of g vectors is the single vector closest to all of them. You already believe that. Everything else on this page is array indexing — knowing that head i lives at columns i·head_dim : (i+1)·head_dim, and that i // g maps a head to its group.

What is genuinely hard is the reshape. (n, h·d) → (h, n, d) and back, with a transpose in the middle, is where I lose an afternoon every time. Print .shape after every line — that's how the people who wrote these implementations debug them too. And the judgement call, 8 groups or 4, GQA or latent attention, isn't maths either. It's capacity planning: cache bytes per token against acceptable quality loss, at your context length and batch size.

Where to go next

    Read the method section for the uptraining procedure — the mean-pooling figure is the one picture worth having. Then the ablations, for the quality claims I refused to paraphrase into numbers. It's a short paper and you now know its implementation better than its notation.

  • Fast Transformer Decoding: One Write-Head is All You Need Shazeer, 2019. Where multi-query starts.

    The endpoint GQA interpolates from, argued four years earlier and almost entirely on memory-bandwidth grounds. Worth reading for the framing this page assumes: that decoding is bound by bytes moved, not FLOPs done.

  • llama/model.py — repeat_kv and Attention Meta. The reference implementation.

    My repeat_kv_heads written for real, in about eight lines of PyTorch, with the cache, RoPE and tensor-parallel sharding around it. Read it to see the block convention stated as torch.repeat_interleave, and where the repeat sits relative to the cache.

    The context this page sits in: multi-query alongside quantisation, pruning, sparsity and the memory-bandwidth argument for all of them. Go here when you want to know which knob to reach for before you reach for the architecture.
