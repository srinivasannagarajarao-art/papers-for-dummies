Multi-head Latent Attention: the KV cache, compressed

DeepSeek-AI, 2024

The sequel to the KV-cache page. Same formula, one term attacked from a completely different direction.

Download mla_from_scratch.py — everything below runs from it. NumPy only, under a second.

The KV-cache page ends on the number that decides what you can serve: bytes per token. I'm not going to re-derive the cache here — go read that first if you haven't, because everything below assumes it. This page is about one line in that formula.

Multi-query and grouped-query attention attack kv_heads by sharing keys and values across heads, and the GQA paper's own ablations show them losing quality doing it — that's the trade Llama-2 70B took with GQA-8. MLA doesn't touch kv_heads. It changes what a cache entry is.

Store the archive, not the files

You've made this call before. A directory of files is too big to keep around, so you tar and gzip it: 

store(tar_gz(files))            # small on disk
files = untar(gunzip(archive))  # pay CPU to get them back

The usual objection is that decompression costs you on every read. Now the twist. Suppose the only thing you ever do with the decompressed files is feed them into one specific function — and that function is a matrix multiply, and so is the decompression: 

scores = (x @ W_q) @ (c @ W_uk).T     # decompress c into keys, then dot
scores = x @ (W_q @ W_uk.T) @ c.T     # same thing. Fold the two matrices
W_abs  = W_q @ W_uk.T                 # once, at load. Now:
scores = (x @ W_abs) @ c.T            # the keys are NEVER built

That's the whole paper. The decompression step folds into the operation you were going to do anyway, so at inference it costs nothing. Matrix multiplication being associative is not a deep fact. Noticing that it makes a 57× cache reduction free is.

The one formula

Not an attention formula. The cache formula from the previous page, and what MLA does to it:

MHA: 2 × layers × kvheads × headdim × seq × dtype
MLA:     layers × (dc + drope)     × seq × dtype

Two things changed. Read them as terms:

TermValueWhat it does
2goneK and V are compressed jointly. One latent serves both, so there is no separate V to store
kv_heads × head_dimgoneReplaced by dc. The latent is shared across every head, so adding heads no longer adds cache
dc512The latent width. This is the dial. DeepSeek-V2 runs 512 against 128 × 128 = 16384 expanded dimensions
drope64The decoupled position block. Also shared across heads. Exists only because RoPE breaks the trick — see below
layers, seq, dtypeunchangedStill the model, still your users, still fp16

The table that is the whole argument

Look at what happens when the head count goes from 32 to 128. Multi-head cache goes up 7.5×, to 3.75 MiB per token per sequence — unservable, which is why nobody builds that. GQA-8 only doubles, and that doubling comes from the layer count (32 to 60), not the heads — it pinned kv_heads at 8. MLA doesn't move at all: 576 floats per layer regardless of how many heads read them. That invariance is the property, and it's what lets DeepSeek run 128 heads in the first place.

The MLA-vs-GQA number is 3.6× at both shapes, and that's the honest comparison. The eye-catching 57× is against a multi-head baseline nobody would have shipped at 128 heads. DeepSeek report their own reduction against DeepSeek-V1's actual architecture, and separately report MLA outperforming GQA in their ablations at comparable cache. Quote both carefully; they are different claims.

Is it still attention? At full rank, exactly

A cache that changes the answer isn't a cache. So the script builds one toy model, runs textbook multi-head attention through it, then runs the same inputs through the down-projection and up-projection, and diffs.

One honesty note: to make the rank sweep mean anything I factor the joint [W_k | W_v] with an SVD and shape its singular values to decay, because trained weight matrices have a decaying spectrum and freshly randomised ones don't.

At full rank it's not an approximation at all — it's a lossless re-encoding, and 7.8 × 10−15 is float64 addition order. Below it you can watch the price. Halving the cache costs about 5% on the output; quartering it costs 60%. The output error tracks the key error closely, sometimes under and sometimes over, because softmax renormalises whatever it's given.

That curve is the entire design decision. Everything about picking dc = 512 is finding where it turns, on real learned weights instead of a shaped-spectrum toy. The mechanism is trivial; the calibration is the work.

Absorption: the part that makes it free

Compressing the cache is easy and obvious. The reason it isn't a disaster is the fold. Written out per head, with Wq at (dmodel, headdim) and Wuk at (dc, headdim):

(x Wq) · (c Wuk)T  =  x Wq WukT cT  =  (x (Wq WukT)) · cT

Nothing in that expression is new attention — it is still the softmax(QKT/√d) V lookup, with the K factored. The middle term is the point: nothing in W_q @ W_uk.T depends on the data, so you compute it once when the model loads and never again. The query gets projected straight into latent space and dotted against the cache. Keys are never materialised. 

cached tokens n = 64, d_c = 16, head_dim = 8
  W_q       (32, 8)   W_uk (16, 8)
  W_absorbed = W_q @ W_uk.T -> (32, 16)  (built ONCE at load)
  expanded scores[0][:4] = [ 1.4168  1.7375  0.3522 -5.6463]
  absorbed scores[0][:4] = [ 1.4168  1.7375  0.3522 -5.6463]
  max abs difference     = 8.438e-15   <- same thing ✓

operation counts, per head per decode step:
   cached n |  expanded MACs |  absorbed MACs | saving
         64 |          8,960 |          1,536 |  5.83x
        512 |         69,888 |          8,704 |  8.03x
      4,096 |        557,312 |         66,048 |  8.44x
     32,768 |      4,456,704 |        524,800 |  8.49x

Be careful with that second table in an interview. At this toy's ratio of dc to headdim the absorbed path is genuinely fewer multiply-accumulates; at DeepSeek's real ratios it isn't always. The reliable win is that the expansion tensor never exists, so it never crosses the memory bus — and decode is memory-bound, which the previous page measured at 0.48 MACs per byte.

RoPE, and why the explanations stop here

Every blog post I read about MLA describes the compression, describes the absorption, and then quietly moves on. Here's what they skipped.

RoPE rotates q and k by an angle proportional to their position. So the score isn't (x W_q) · (c W_uk), it's (R(m) x W_q) · (R(n) c W_uk) — and R(n) is a different matrix for every cached token. There is no way to pull it out and fold it into a fixed Wq at load time. The absorption and the rotation do not commute. Not "approximately"; at all. 

scores over 8 cached tokens, head 0, with RoPE applied:
  correct (expand, then rotate) : [ 2.5354 -2.1796  0.0678 -3.9345]
  absorbed then rotated         : [ 6.6998  2.1142  2.3629 -2.7651]
  max abs difference            = 7.4962   <- wrong
  ranking preserved?              False

Not a rounding difference. The ranking of which tokens to attend to is different, which means it isn't a slightly worse model, it's a different one. DeepSeek's fix is to stop trying: split each head in two. Most dimensions carry no position and stay absorbable. A small extra block of drope = 64 dimensions carries the rotation, is computed the ordinary way, and is cached separately — one copy, shared by every head. The score is the sum of the two parts. 

DeepSeek's fix -- split the head in two:
  content part (absorbed, no position) : [ 2.2504 -0.2611 -0.1965 -0.022 ]
  decoupled RoPE part (d_rope=8)   : [ -3.7696   8.6941 -19.5117   6.6326]
  score = sum                          : [ -1.5192   8.4329 -19.7082   6.6107]
  matches the explicit two-part sum?     True, max diff 0.000e+00 ✓

what the decoupled block costs, per token, DeepSeek-V2 shape:
  latent only        :  61,440 bytes/token
  + decoupled RoPE   :  69,120 bytes/token (+7,680, +12.5%)
  still vs multi-head: 56.9x smaller
Twelve percent more cache, and the whole architecture survives. That is what the decoupled dimensions are for. Not a tuning knob, not an ablation — a structural repair to a hole that rotary embeddings punched in the absorption. If someone explains MLA to you without mentioning it, they have explained a model that doesn't work.

Where the saving actually lands

Cache bytes per token is an abstraction. The number your finance team feels is how many concurrent sequences fit on one card. Fix a budget of 80 GiB for cache alone, on the DeepSeek-V2 shape: 

   context | multi-head |    GQA-8 |      MLA | MLA seqs in 80 GiB
     4,096 |     15.00G |    0.94G |    0.26G |    303
    16,384 |     60.00G |    3.75G |    1.05G |     75
    32,768 |    120.00G |    7.50G |    2.11G |     37
   131,072 |    480.00G |   30.00G |    8.44G |      9

  sequences that fit in 80 GiB at 32k context:
    multi-head  :      0 concurrent sequences
    GQA-8       :     10 concurrent sequences
    MLA         :     37 concurrent sequences ✓

At 32k context this shape cannot serve a single multi-head sequence in 80 GiB. GQA-8 fits 10. MLA fits 37. Per-token latency is identical in all three — the weights are in flight anyway — so that's roughly 3.7× the tokens per second per GPU, for the same silicon. This is the argument, and a lab that serves its own model at scale is exactly who would make it.

What it costs, said plainly

MLA is not free, and I'd rather you had the honest version before an interviewer hands it to you. Per attention layer, at DeepSeek-V2's shape: 

per attention layer, d_model=5120, 128 heads x 128:
  multi-head    params:   335,544,320
  GQA-8         params:   178,257,920
  MLA           params:   229,441,536  (0.68x multi-head, 1.29x GQA-8)

  cache at 32,768 tokens, batch 1:
  multi-head :  120.00 GiB
  GQA-8      :    7.50 GiB
  MLA        :    2.11 GiB ✓

Against 128-head multi-head, MLA is actually cheaper in parameters, because the latent is a bottleneck. Against GQA-8 it costs about 1.29×, plus arithmetic: an extra projection on every token and a wider per-head dimension once the RoPE block is bolted on. The trade is a fixed cost you pay once and share across the whole batch, in exchange for a per-sequence per-token cost. That's a good deal at serving scale and a bad one at batch 1 on your laptop.

One more thing to keep straight, because it's the easiest place to be confidently wrong. DeepSeek also apply a low-rank compression to the queries. That one has nothing to do with the KV cache — queries are never cached, as the previous page's break-it table showed. It reduces activation memory during training. Same technique, different problem, and the papers are clear about it even though summaries usually aren't.

A caveat on quality. That MLA matches or beats grouped-query attention on quality at comparable cache size is DeepSeek's reported claim from their own ablations. Nothing on this page measures it. What I measured here is bytes, MACs and reconstruction error — the parts that fit on a laptop.

Files-ஐ அல்ல, archive-ஐச் சேமியுங்கள்

இந்த முடிவை நீங்கள் ஏற்கனவே எடுத்திருக்கிறீர்கள். ஒரு directory-யிலுள்ள files வைத்திருக்க முடியாத அளவு பெரிதாக இருக்கிறது, அதனால் tar செய்து gzip செய்கிறீர்கள்: 

store(tar_gz(files))            # disk-ல் சிறியது
files = untar(gunzip(archive))  # திரும்பப் பெற CPU செலவு

வழக்கமான ஆட்சேபனை: ஒவ்வொரு read-லும் decompression உங்களுக்குச் செலவு. இப்போது திருப்பம். decompress செய்யப்பட்ட files-ஐ வைத்து நீங்கள் செய்யும் ஒரே காரியம் ஒரு குறிப்பிட்ட function-க்குள் அதைச் செலுத்துவது மட்டுமே என்று வைத்துக்கொள்ளுங்கள் — அந்த function ஒரு matrix multiply, decompression-ம் ஒரு matrix multiply: 

scores = (x @ W_q) @ (c @ W_uk).T     # c-ஐ keys ஆக்கு, பிறகு dot
scores = x @ (W_q @ W_uk.T) @ c.T     # அதே விஷயம். இரு matrix-ஐ மடி
W_abs  = W_q @ W_uk.T                 # load-ல் ஒருமுறை. இப்போது:
scores = (x @ W_abs) @ c.T            # keys ஒருபோதும் உருவாக்கப்படுவதில்லை

முழுப் paper-ம் இதுதான். decompression படி, நீங்கள் எப்படியும் செய்யப்போகும் operation-க்குள் மடிந்துவிடுகிறது, அதனால் inference-ல் அதற்குச் செலவே இல்லை. Matrix multiplication associative என்பது ஒன்றும் ஆழமான உண்மை அல்ல. அது 57× cache குறைப்பை இலவசமாக்குகிறது என்று கவனிப்பதுதான் ஆழம்.

GQA-8 இரட்டிப்பாகிறது, அந்த இரட்டிப்பும் layer எண்ணிக்கையால் வருகிறது (32-லிருந்து 60), heads-ஆல் அல்ல — அது kv_heads-ஐ 8-ல் நிறுத்தியது. MLA சிறிதும் அசையவில்லை: எத்தனை heads படித்தாலும் ஒரு layer-க்கு 576 floats. அந்த மாறாத்தன்மைதான் இதன் இயல்பு, DeepSeek முதலிலேயே 128 heads இயக்க முடிவதற்குக் காரணமும் அதுதான்.

MLA-vs-GQA எண் இரு shapes-லும் 3.6×, அதுதான் நேர்மையான ஒப்பீடு. கண்ணைக் கவரும் 57× என்பது, 128 heads-உடன் யாருமே ship செய்திருக்க மாட்டார்கள் என்கிற multi-head baseline-க்கு எதிரானது. DeepSeek தங்கள் சொந்தக் குறைப்பை DeepSeek-V1-ன் உண்மையான architecture-க்கு எதிராகவே அறிக்கையிடுகிறார்கள்; ஒப்பிடத்தக்க cache-ல் MLA, GQA-ஐ மிஞ்சுவதாகத் தங்கள் ablations-ல் தனியாகச் சொல்கிறார்கள். இரண்டையும் கவனமாக மேற்கோள் காட்டுங்கள்; அவை வெவ்வேறு உரிமைகோரல்கள்.

Cache formula-la rendu term poidum: 2-um, kv_heads × head_dim-um. Latent ellaa heads-kkum share aagum, adhanaala heads koodinaalum cache koodaadhu. Aana honest-aana ottumottha comparison MLA vs GQA-8 = 3.6x dhaan; andha 57x yaarum ship pannaadha multi-head baseline-kku edhiraana en sondha kanakku.

இது இன்னும் attention-தானா? Full rank-ல், சரியாக

விடையையே மாற்றும் cache, cache அல்ல. அதனால் script ஒரு toy model-ஐக் கட்டி, அதன் வழியே பாடநூல் multi-head attention-ஐ இயக்கி, பிறகு அதே inputs-ஐ down-projection மற்றும் up-projection வழியே இயக்கி, வித்தியாசம் பார்க்கிறது.

Absorption: இதை இலவசமாக்கும் பகுதி

Cache-ஐ compress செய்வது எளிது, வெளிப்படையானது. அது ஒரு பேரழிவாக இல்லாததற்குக் காரணம் அந்த மடிப்பு. Wq (dmodel, headdim)-ல், Wuk (dc, headdim)-ல் இருக்க, ஒரு head-க்கு எழுதினால்:

(x Wq) · (c Wuk)T  =  x Wq WukT cT  =  (x (Wq WukT)) · cT

அந்த expression-ல் புதிய attention எதுவும் இல்லை — இது இன்னும் அதே softmax(QKT/√d) V lookup, K மட்டும் factor செய்யப்பட்டிருக்கிறது. நடுவிலிருக்கும் term-தான் விஷயம்: W_q @ W_uk.T-ல் எதுவும் data-வைச் சார்ந்திருக்கவில்லை, அதனால் model load ஆகும்போது ஒருமுறை கணக்கிட்டால் போதும், மீண்டும் வேண்டாம். Query நேராக latent space-க்குள் project செய்யப்பட்டு cache-உடன் dot செய்யப்படுகிறது. Keys ஒருபோதும் உருவாக்கப்படுவதில்லை.

RoPE, விளக்கங்கள் ஏன் இங்கேயே நின்றுவிடுகின்றன

MLA பற்றி நான் படித்த ஒவ்வொரு blog post-ம் compression-ஐ விவரிக்கிறது, absorption-ஐ விவரிக்கிறது, பிறகு அமைதியாக அடுத்ததற்குச் சென்றுவிடுகிறது. அவர்கள் தவிர்த்தது இதுதான்.

RoPE, q-ஐயும் k-ஐயும் அவற்றின் position-க்கு விகிதாசாரமான கோணத்தில் சுழற்றுகிறது. அதனால் score (x W_q) · (c W_uk) அல்ல, அது (R(m) x W_q) · (R(n) c W_uk) — R(n) ஒவ்வொரு cache செய்யப்பட்ட token-க்கும் வேறு matrix. அதை வெளியே இழுத்து, load நேரத்தில் நிலையான Wq-க்குள் மடிக்க வழியே இல்லை. Absorption-ம் சுழற்சியும் commute ஆகாது. "தோராயமாக" அல்ல; சுத்தமாகவே இல்லை.

இன்னொன்றைத் தெளிவாக வைத்திருங்கள், ஏனெனில் இங்குதான் நம்பிக்கையுடன் தவறாகச் சொல்வது மிக எளிது. DeepSeek queries-க்கும் ஒரு low-rank compression-ஐப் பயன்படுத்துகிறார்கள். அதற்கும் KV cache-க்கும் சம்பந்தமே இல்லை — queries ஒருபோதும் cache செய்யப்படுவதில்லை, முந்தைய பக்கத்தின் break-it table அதைக் காட்டியது. அது training-ன்போது activation memory-ஐக் குறைக்கிறது. அதே நுட்பம், வேறு பிரச்சனை; papers இதில் தெளிவாக இருக்கின்றன, சுருக்கங்கள் பொதுவாகத் தெளிவாக இருப்பதில்லை.

தரம் பற்றிய ஒரு எச்சரிக்கை: MLA, GQA-ஐ விட நல்ல தரம் தருகிறது என்பது DeepSeek தங்கள் paper-ல் அறிக்கையிட்ட உரிமைகோரல்; இந்தப் பக்கத்தில் அது அளக்கப்படவில்லை. இங்கே நான் அளந்தது bytes, MACs, மற்றும் reconstruction error மட்டுமே.

KV-cache वाला पन्ना उसी संख्या पर ख़त्म होता है जो तय करती है कि आप क्या serve कर सकते हैं: प्रति token कितने bytes। उस cache को यहाँ दोबारा नहीं निकालूँगा — अगर नहीं पढ़ा है तो पहले वही पढ़िए, क्योंकि नीचे सब कुछ उसी को मानकर चलता है। यह पन्ना उस formula की सिर्फ़ एक line के बारे में है।

ध्यान दें: English technical words (latent, absorption, up-projection, down-projection, rank, KV cache, multi-head, grouped-query, decoupled RoPE…) मैंने वैसे ही रखे हैं। क्योंकि code में और बाक़ी papers में आपको वही शब्द दिखेंगे। समझ हिंदी में, शब्दावली English में।

Multi-query और grouped-query attention, heads के बीच keys और values साझा करके kv_heads पर हमला करते हैं — और ऐसा करने में गुणवत्ता गिरती है, यह GQA paper के अपने ablations दिखाते हैं। यही सौदा Llama-2 70B ने GQA-8 के साथ किया। MLA kv_heads को छूता ही नहीं। वह यह बदल देता है कि एक cache entry होती क्या है।

Files नहीं, archive रखिए

यह फ़ैसला आप पहले भी ले चुके हैं। files की एक directory रखने के लिए बहुत बड़ी है, तो आप tar और gzip कर देते हैं: 

store(tar_gz(files))            # disk पर छोटा
files = untar(gunzip(archive))  # वापस पाने के लिए CPU खर्च

आम आपत्ति यह है कि हर read पर decompression का ख़र्च पड़ता है। अब मोड़। मान लीजिए decompress की गई files के साथ आप बस एक ही काम करते हैं — उन्हें एक ख़ास function में डालना — और वह function एक matrix multiply है, और decompression भी: 

scores = (x @ W_q) @ (c @ W_uk).T     # c को keys बनाओ, फिर dot
scores = x @ (W_q @ W_uk.T) @ c.T     # वही बात। दोनों matrix मोड़ दो
W_abs  = W_q @ W_uk.T                 # load पर एक बार। अब:
scores = (x @ W_abs) @ c.T            # keys कभी बनते ही नहीं

पूरा paper यही है। decompression का क़दम उसी operation में मुड़ जाता है जो आप वैसे भी करने वाले थे, इसलिए inference पर उसका कोई ख़र्च नहीं। Matrix multiplication का associative होना कोई गहरी बात नहीं है। यह ध्यान देना कि इससे 57× cache की कमी मुफ़्त हो जाती है — वह गहरी बात है।

वह एक formula

Attention वाला formula नहीं। पिछले पन्ने का cache formula, और MLA उसके साथ क्या करता है:

MHA: 2 × layers × kvheads × headdim × seq × dtype
MLA:     layers × (dc + drope)     × seq × dtype

दो चीज़ें बदलीं। उन्हें अलग-अलग terms की तरह पढ़िए:

क्या यह अब भी attention है? Full rank पर, बिलकुल

जो cache जवाब बदल दे वह cache नहीं है। इसलिए script एक toy model बनाती है, उसमें से किताबी multi-head attention चलाती है, फिर वही inputs down-projection और up-projection से गुज़ारकर फ़र्क़ निकालती है।

एक ईमानदारी की बात: rank sweep का कोई मतलब बने, इसके लिए मैं संयुक्त [W_k | W_v] को SVD से factor करके उसकी singular values को घटते हुए आकार में ढालता हूँ, क्योंकि प्रशिक्षित weight matrices का spectrum घटता हुआ होता है और ताज़ा randomise किए गए का नहीं।

Full rank पर यह approximation है ही नहीं — यह बिना नुक़सान वाली re-encoding है, और 7.8 × 10−15 float64 के जोड़ने के क्रम का असर है। उसके नीचे आप क़ीमत देख सकते हैं। cache आधा करने पर output पर क़रीब 5% का ख़र्च; चौथाई करने पर 60%। output की error, key की error के साथ-साथ चलती है — कभी कम, कभी ज़्यादा — क्योंकि softmax जो मिलता है उसे दोबारा normalise कर देता है।

वही curve पूरा design फ़ैसला है। dc = 512 चुनने का मतलब बस यह ढूँढ़ना है कि वह कहाँ मुड़ता है — और वह भी असली सीखे हुए weights पर, न कि जान-बूझकर आकार दिए गए spectrum वाले किसी toy पर। ऊपर दिखाया गया sweep ठीक ऐसे ही जान-बूझकर गढ़े spectrum पर चलता है। तरकीब मामूली है; असली काम calibration है।

Absorption: वह हिस्सा जो इसे मुफ़्त बनाता है

Cache को compress करना आसान और ज़ाहिर है। यह आपदा नहीं बनता, इसकी वजह वह मोड़ है। प्रति head लिखें, जहाँ Wq (dmodel, headdim) पर है और Wuk (dc, headdim) पर:

(x Wq) · (c Wuk)T  =  x Wq WukT cT  =  (x (Wq WukT)) · cT

इस expression में कुछ भी नया attention नहीं है — यह अब भी वही softmax(QKT/√d) V lookup है, बस K factor कर दिया गया है। बीच वाला term ही असल बात है: W_q @ W_uk.T में कुछ भी data पर निर्भर नहीं, इसलिए आप उसे model load होते समय एक बार निकालते हैं और फिर कभी नहीं। Query सीधे latent space में project होकर cache से dot हो जाती है। Keys कभी बनते ही नहीं।

RoPE, और व्याख्याएँ यहीं क्यों रुक जाती हैं

MLA पर मैंने जितनी भी blog posts पढ़ीं, सब compression बताती हैं, absorption बताती हैं, और फिर चुपचाप आगे बढ़ जाती हैं। जो वे छोड़ देती हैं, वह यह है।

RoPE, q और k को उनकी position के समानुपाती कोण से घुमाता है। तो score (x W_q) · (c W_uk) नहीं है, वह (R(m) x W_q) · (R(n) c W_uk) है — और R(n) हर cached token के लिए अलग matrix है। उसे बाहर खींचकर load time पर किसी स्थिर Wq में मोड़ने का कोई तरीक़ा नहीं। Absorption और rotation commute नहीं करते। "लगभग" नहीं; बिलकुल नहीं।

32k context पर यह shape 80 GiB में एक भी multi-head sequence serve नहीं कर सकता। GQA-8 में 10 आती हैं। MLA में 37। प्रति token latency तीनों में एक जैसी है — weights तो वैसे भी आ-जा रहे हैं — तो उतने ही silicon पर प्रति GPU प्रति सेकंड लगभग 3.7 गुना tokens। यही दलील है, और यह दलील वही lab रखेगी जो अपना model ख़ुद बड़े पैमाने पर serve करती है।

128-head multi-head के मुक़ाबले MLA parameters में सचमुच सस्ता है, क्योंकि latent एक bottleneck है। GQA-8 के मुक़ाबले वह लगभग 1.29× महँगा है, और साथ में गणित भी: हर token पर एक अतिरिक्त projection, और RoPE block जुड़ने के बाद प्रति head चौड़ा dimension। सौदा यह है — एक बार चुकाई जाने वाली और पूरे batch में बँटने वाली स्थिर लागत, बदले में प्रति sequence प्रति token की लागत। serving के पैमाने पर यह अच्छा सौदा है और आपके laptop पर batch 1 पर बुरा।

एक और बात साफ़ रखिए, क्योंकि यहीं आत्मविश्वास के साथ ग़लत होना सबसे आसान है। DeepSeek queries पर भी एक low-rank compression लगाते हैं। उसका KV cache से कोई लेना-देना नहीं — queries कभी cache नहीं होतीं, जैसा पिछले पन्ने की break-it table ने दिखाया। वह training के दौरान activation memory घटाता है। वही तकनीक, अलग समस्या, और papers इस पर साफ़ हैं, भले सारांश आमतौर पर न हों।

गुणवत्ता पर एक चेतावनी: MLA, GQA से बेहतर गुणवत्ता देता है — यह DeepSeek का अपने paper में बताया गया दावा है; इस पन्ने पर वह नापा नहीं गया। यहाँ मैंने सिर्फ़ bytes, MACs और reconstruction error नापे हैं।

The code

Pure NumPy. No torch, no training — a forward pass and some byte counting, which is all a linear-algebra paper needs. Runs in about a seventh of a second. Every function under 20 lines.

def kv_cache_bytes(layers, kv_heads, head_dim, seq_len, dtype_bytes=2,
                   batch=1):
    """Standard KV cache. Same formula as the KV-cache page, unchanged."""
    return 2 * layers * kv_heads * head_dim * seq_len * dtype_bytes * batch


def mla_cache_bytes(layers, d_c, d_rope, seq_len, dtype_bytes=2, batch=1):
    """MLA cache: one latent per token per layer, plus the decoupled RoPE key.
    Both are shared across ALL heads, which is where the saving comes from."""
    return layers * (d_c + d_rope) * seq_len * dtype_bytes * batch


def low_rank_factors(W, rank):
    """W (m, n) -> (W_down (m, rank), W_up (rank, n)) with W ~ W_down @ W_up."""
    U, S, Vt = np.linalg.svd(W, full_matrices=False)
    return U[:, :rank] * S[:rank], Vt[:rank]


class ToyMLA:
    def __init__(self, d_model, n_heads, head_dim, d_c, seed=0):
        rng = np.random.default_rng(seed)
        self.d_model, self.n_heads, self.head_dim = d_model, n_heads, head_dim
        self.d_c = d_c
        d_all = n_heads * head_dim

        self.W_q = rng.normal(0, 0.4, (d_model, d_all))

        # The joint K/V projection. I shape its singular values to DECAY,
        # because a trained weight matrix has a decaying spectrum and a
        # freshly randomised one does not. Without this the rank sweep below
        # is meaningless -- every direction matters equally, so truncation is
        # uniformly catastrophic and you learn nothing from it.
        raw = rng.normal(0, 0.4, (d_model, 2 * d_all))
        U, _, Vt = np.linalg.svd(raw, full_matrices=False)
        spectrum = 6.0 * (0.82 ** np.arange(min(U.shape[1], Vt.shape[0])))
        W_kv = (U * spectrum) @ Vt                            # (d, 2*d_all)
        self.W_k, self.W_v = W_kv[:, :d_all], W_kv[:, d_all:]

        # Compress K and V JOINTLY -- one latent serves both. That joint-ness
        # is the paper's word and it is why there is no factor of 2 above.
        self.W_dkv, W_ukv = low_rank_factors(W_kv, d_c)
        self.W_uk = W_ukv[:, :d_all]      # (d_c, d_all)
        self.W_uv = W_ukv[:, d_all:]      # (d_c, d_all)

    def latent(self, X):
        """The ONLY thing that gets cached: (n, d_c)."""
        return X @ self.W_dkv

    def attention_via_latent(self, X):
        """MLA the naive way: compress, then re-expand K and V and carry on.
        Correct, but it materialises the full K and V -- no saving at all
        except in what you STORE. Demo 4 removes the expansion."""
        C = self.latent(X)                           # (n, d_c)  <- cached
        Q = self.heads(X @ self.W_q)
        K = self.heads(C @ self.W_uk)                # re-expanded
        V = self.heads(C @ self.W_uv)                # re-expanded
        w = softmax(Q @ K.transpose(0, 2, 1) / np.sqrt(self.head_dim))
        out = w @ V
        return out.transpose(1, 0, 2).reshape(X.shape[0], -1)


def absorb_q_into_latent(W_q_head, W_uk_head):
    """(d_model, head_dim) x (d_c, head_dim) -> (d_model, d_c). Done ONCE."""
    return W_q_head @ W_uk_head.T


def scores_absorbed(x, W_absorbed, C):
    """The MLA way: project into latent space, dot against the cache."""
    q_c = x @ W_absorbed                 # (1, d_c)
    return q_c @ C.T                     # (1, n)


def decoupled_score(x_q, pos_q, C, positions, W_absorbed, W_qr, K_rope):
    """DeepSeek's score: absorbable content part + decoupled RoPE part.

    K_rope is (n, d_rope), already rotated and cached -- ONE copy for all
    heads. That sharing is why the extra cache is cheap."""
    content = (x_q @ W_absorbed) @ C.T                       # no position
    q_r = apply_rope(x_q @ W_qr, np.array([pos_q]))          # (1, d_rope)
    return content + q_r @ K_rope.T

On the maths anxiety

This one is genuinely just linear algebra, and less of it than the attention page needed. You need three things: that a matrix product is associative, that a matrix can be written as a thin product of two smaller ones, and that throwing away the smallest singular values is the best approximation of a given rank. The first is the whole trick. The second is what "low-rank" means. The third is only how I built the toy — a real model learns its factors by gradient descent and never runs an SVD.

What you do need is the byte arithmetic, and you need it fast, because the interview question is not "explain MLA". It's "you have an 80 GB card and a 32k context — what's your maximum batch size, and which architecture gets you there". That's multiplication and division on numbers you can read off a config file, and demo 5 is exactly that computation.
