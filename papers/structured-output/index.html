Constrained decoding: making the model return valid JSON

Willard & Louf, 2023 · Geng et al., 2023

Stop asking the model nicely. Make the invalid output unrepresentable.

Download structured_output_from_scratch.py — everything below runs from it. NumPy and plain Python. There is no language model anywhere in it: a model contributes exactly one thing to this idea — a vector of logits over the vocabulary — so I generate that with numpy and spend the file on the part that does the work.

I'm an AI Engineer. I've shipped models, done the MLOps, and for two years my answer to "the JSON came back malformed" was a better prompt and a retry loop. It worked. That is the worst thing that can be said about it. It worked in dev, it worked in staging, it worked for the demo, and then it failed in production at a rate nobody could put a number on, and the retry loop hid it until the invoice arrived.

Nobody told me there was a version of this problem with an actual guarantee, and that the guarantee is one line long.

It's the causal mask, pointed somewhere else

You already know the retry shape. You've written it for flaky HTTP: 

for attempt in range(5):
    text = model(prompt)
    try:
        return json.loads(text)      # hope
    except ValueError:
        continue                     # hope again, with feeling
raise                                 # and now what?

That is validation. It runs after the fact, it can fail, and its cost is a random variable. Now the other version. At every step the model hands you one vector of logits over the whole vocabulary. A parser knows which of those tokens could possibly continue a valid document. So: 

state = parser.start
while not parser.done(state):
    logits = model(prefix)                  # unchanged. the model is innocent
    logits[not_allowed(state)] = -np.inf    # <-- the entire paper
    tok = sample(logits)
    state = parser.step(state, tok)

That loop is the sampling loop from the GPT page with one line inserted into it. If you read the attention page you have seen that middle line before. It is the causal mask — set the forbidden entries to −∞ before the softmax so they come out at exactly 0. The only difference is what it runs over. The causal mask runs over positions and is driven by time. This one runs over the vocabulary and is driven by a parser.

Validation after the fact is a test. Constrained decoding is a type.

TermMeansProgrammer's analogy
GrammarThe set of strings you will acceptThe schema, before anything is written
Parser stateWhere in the document you areThe cursor in a state machine
Allowed setToken ids that keep the document validThe whitelist for this one step
Logit mask−∞ on everything elseA read-lock on the rest of the vocabulary
Indexstate → allowed set, precomputedA dict you build at boot instead of a scan per request

Why the retry loop is worse than it looks

Say one attempt returns parseable JSON with probability p. Attempts until success is a geometric distribution: mean 1/p, and the quantiles are a log away. My script prices it.

Don't take my word for it. Here's the actual output:

A request costs 400 tokens. You retry until the JSON parses.
p = probability one attempt returns valid JSON.

     p  E[attempts]  p95 attempts   p99.9  tokens/1k reqs  worst case
  0.70         1.43             3       6         571,428   unbounded
  0.90         1.11             2       3         444,444   unbounded
  0.95         1.05             1       3         421,052   unbounded
  0.99         1.01             1       2         404,040   unbounded

simulated 20,000 requests at p=0.95: mean attempts 1.053, max 4

Look at the last column, not the second. 95% costs you about 5% extra tokens, which is fine, and it has no worst case — there is no n at which you can tell your on-call "this will have succeeded". At p=0.99 you still can't. You have bought yourself a tail you haven't measured yet, and a latency budget you can't write down.

The interview question is the last column. Anyone can say "retry with a validator". The answer they're listening for is that a retry loop turns a correctness problem into an unbounded cost-and-latency problem, and constrained decoding turns it into 1.00 attempts.

The one formula

p̃(t | s) = softmax( ℓt + ms(t) ) where ms(t) = 0 if t ∈ A(s), −∞ otherwise

ℓ is the logit vector the model gave you. s is the parser state. A(s) is the set of tokens allowed from that state. That's it — everything else in both papers is how you compute A(s) fast enough to run per token. Read it as pipeline stages:

StepShapeWhat it does
ℓ(V,)One logit per vocabulary entry. The model's whole contribution
A(s)a setThe paper. Which token ids keep the document parseable
+ ms(V,)0 on the allowed ones, −∞ on the rest. Before the softmax
softmax(V,)Renormalises over what's left. Still sums to 1
sampleone idOrdinary sampling. Temperature, top-p, all unchanged
parser.stepnew sAdvance the state machine by the token you actually emitted

Two things worth staring at. The 98.5% of probability mass that the model put on tokens which cannot appear here — that is the fraction of the retry loop's failures you are pre-emptively deleting. And the last line: write the mask as 0.0 instead of −∞ and 97% of the mass is still on garbage. 0 is not "off". 0 is a perfectly ordinary logit. Exactly the bug the attention page's mask table warns about, in a different file.

A real state machine, and what "by construction" means

My grammar is one fixed schema, no whitespace: {"name":"<letters>","age":<digits>}. That language is regular, so a finite-state machine is enough — 20 states, 15 of which are just single steps inside the fixed literals. Then the loop runs, and at each step the mask is whatever that state allows.

500 for 500 is not a good hit rate. It is not a hit rate at all. The parser cannot leave the set of valid prefixes, because the tokens that would take it out of that set were never sampleable. The logits are random noise from rng.normal — a genuinely terrible model — and the output still parses every time. That's the claim: the guarantee comes from the mask, not from the model having been persuaded.

Be precise about "JSON" in an interview. A fixed schema like mine is a regular language, and a finite-state machine handles it. JSON in general is not regular — arbitrary nesting needs a stack, which means a context-free grammar and a pushdown automaton. The state-machine story covers the schemas most applications actually want; it does not cover "any JSON".

The hard part: grammars speak characters, models emit tokens

This is where most explanations stop, and it's the part that actually costs you. Your grammar is defined over characters. The model emits tokens, and a token is a multi-character string that some compression algorithm picked years ago without consulting your schema — see the tokenisation page. So a single token can straddle a grammar boundary.

Sitting inside the name string, 28 characters are legal here. Watch what that does and does not tell you about tokens: 

     token  first char ok?  whole token ok?  why
      '"}'            True            False  walks off the DFA
     '","'            True             True  ends in state 15
'lovelace'            True             True  ends in state 1
     'ace'            True             True  ends in state 1
       '}'           False            False  walks off the DFA
     'age'            True             True  ends in state 1
     '":"'            True            False  walks off the DFA

The same token flips legality with the state. Token '0}':
  from state 0 (start          ): None
  from state 1 (in name string ): None
  from state 2 (need a digit   ): None
  from state 3 (in age         ): 4
  from state 4 (done           ): None

'"}' is the one to hold on to. Its first character is legal — the quote closes the name string. The } welded to it is not, because the schema still owes us an age field. A character-level check on the first character says yes; the token as a unit is a no; and you cannot emit half a token. That is why you run the whole token through the automaton and keep only tokens that survive end to end.

'0}' shows the other direction: the same token is illegal in "need a digit" (JSON forbids a leading zero) and legal one state later. Legality is a property of the pair, not of the token. So the answer is a table: 

So the answer is an index -- parser state -> allowed token ids:
  state 0 (start          )  2 tokens  ['{', '{"']
  state 1 (in name string ) 18 tokens  [' ', '"', '","', 'a', 'ace', 'ada', '...']
  state 2 (need a digit   ) 13 tokens  ['1', '180', '2', '3', '36', '36}', '...']
  state 3 (in age         ) 16 tokens  ['0', '0}', '1', '180', '2', '3', '...']
  state 4 (done           )  0 tokens  []
  ... and the other 15 literal states, 1 or 2 tokens each

That table is Willard and Louf's contribution. Not the masking — people were masking already, and Geng et al. had wired a grammar to a decoder the same year. The Outlines claim is about when you compute the allowed set: once per (grammar, tokeniser) pair, at load time, instead of once per generated token.

What the index costs, and what it saves

I count DFA character-steps rather than milliseconds, so the script prints the same numbers on your laptop as on mine. It's also the more honest unit: it's the work, not my machine's mood. 

vocabulary 45 tokens, grammar 20 states

  parser state   naive scan   index lookup
         start        46 steps         1 lookup
in name string        82 steps         1 lookup
  need a digit        51 steps         1 lookup
        in age        52 steps         1 lookup
          done        45 steps         1 lookup

index built once, at load time: 986 character-steps, 68 entries

and the scan grows with the vocabulary while the lookup does not:
  vocab    45: naive      82 steps per generated token, index 1
  vocab   180: naive     487 steps per generated token, index 1
  vocab   720: naive    2107 steps per generated token, index 1
  vocab  2880: naive    8587 steps per generated token, index 1

The whole index cost 986 character-steps to build — under a dozen naive scans — and after that every step is a dict lookup. Multiply the left column by a real vocabulary (50k–200k entries), a real grammar, and every token of every request, and you have the difference between a technique and a product. That is the word "Efficient" in the title, and all it claims.

What this does not buy you

Six outputs from the constrained decoder. All six parse. All six match the schema. Zero of them are true. 

ground truth: {'name': 'ada lovelace', 'age': 36}

                            output  parses  schema  correct
           {"name":"age","age":36}     yes     yes       NO
             {"name":"","age":479}     yes     yes       NO
              {"name":"","age":30}     yes     yes       NO
               {"name":"","age":8}     yes     yes       NO
     {"name":"","age":93594505170}     yes     yes       NO
         {"name":"null","age":390}     yes     yes       NO

6 distinct outputs, all valid JSON, all matching the
schema. The number that were right about Ada Lovelace: 0

Schema validity is a property of the output's syntax. It says nothing about the world. My "model" here is random noise, which makes the point loudly, but the same thing is true of a good model: constraining moves the failures from "unparseable" to "parseable and wrong", and parseable and wrong is the one that gets into your database. Whether the age is 36 is an eval question — see the evals page.

One honest cost, while we're here. Masking renormalises over a subset, so the constrained distribution is not the model's distribution conditioned on validity — it's a greedy, per-step approximation of it, and people have measured quality shifts from it in both directions. Don't sell constrained decoding as free. Sell it as a guarantee you're buying with a known, small distortion.

p̃(t | s) = softmax( ℓt + ms(t) ) where ms(t) = 0 if t ∈ A(s), −∞ otherwise

ஒரு உண்மையான state machine, "by construction" என்றால் என்ன

என் grammar ஒரே ஒரு நிலையான schema, whitespace இல்லை: {"name":"<letters>","age":<digits>}. அந்த மொழி regular, அதனால் ஒரு finite-state machine போதும் — 20 states, அவற்றில் 15 வெறும் நிலையான literals-க்குள் ஒற்றை steps. பிறகு loop ஓடுகிறது, ஒவ்வொரு step-லும் mask என்பது அந்த state அனுமதிப்பதுதான்.

500-க்கு 500 என்பது ஒரு நல்ல hit rate அல்ல. அது hit rate-ஏ அல்ல. Parser valid prefixes-ன் தொகுப்பிலிருந்து வெளியேற முடியாது, ஏனெனில் அதை வெளியே கொண்டுசெல்லும் tokens ஒருபோதும் sample செய்யக்கூடியவையாக இருக்கவில்லை. Logits என்பவை rng.normal-லிருந்து வரும் random noise — உண்மையிலேயே மோசமான ஒரு model — இருந்தும் output ஒவ்வொரு முறையும் parse ஆகிறது. கூற்று இதுதான்: guarantee வருவது mask-லிருந்து, model சம்மதிக்க வைக்கப்பட்டதிலிருந்து அல்ல.

Interview-ல் "JSON" பற்றி துல்லியமாகப் பேசுங்கள். என்னுடையது போன்ற ஒரு நிலையான schema ஒரு regular மொழி, ஒரு finite-state machine அதைக் கையாளும். ஆனால் பொதுவான JSON regular அல்ல — வரம்பற்ற nesting-க்கு ஒரு stack தேவை, அதாவது ஒரு context-free grammar-ம் ஒரு pushdown automaton-ம். State-machine கதை பெரும்பாலான applications உண்மையில் விரும்பும் schemas-ஐ உள்ளடக்கும்; "எந்த JSON-ம்" என்பதை அல்ல.

கடினமான பகுதி: grammars characters பேசுகின்றன, models tokens தருகின்றன

பெரும்பாலான விளக்கங்கள் இங்கே நின்றுவிடுகின்றன, ஆனால் உங்களுக்கு உண்மையில் செலவாகும் பகுதி இதுதான். உங்கள் grammar characters மீது வரையறுக்கப்பட்டது. Model tokens-ஐ emit செய்கிறது, ஒரு token என்பது உங்கள் schema-ஐக் கேட்காமல் வருடங்களுக்கு முன்பு ஒரு compression algorithm தேர்ந்தெடுத்த பல-character string — tokenisation page-ஐப் பாருங்கள். அதனால் ஒரே token ஒரு grammar எல்லையைத் தாண்டி நிற்கலாம்.

Name string-க்குள் இருக்கும்போது, இங்கே 28 characters சட்டப்படி அனுமதிக்கப்படுகின்றன. அது tokens பற்றி என்ன சொல்கிறது, என்ன சொல்லவில்லை என்று பாருங்கள்:

'"}'-ஐத்தான் மனதில் வைத்துக்கொள்ள வேண்டும். அதன் முதல் character சட்டப்படி சரி — அந்த quote name string-ஐ மூடுகிறது. அதனுடன் ஒட்டியிருக்கும் } சரியல்ல, ஏனெனில் schema இன்னும் ஒரு age field-ஐக் கடன்பட்டிருக்கிறது. முதல் character மீதான character-level சோதனை ஆம் என்கிறது; token ஒரு முழு அலகாகப் பார்த்தால் இல்லை; ஒரு token-ல் பாதியை emit செய்ய முடியாது. அதனால்தான் முழு token-ஐயும் automaton வழியாக ஓட்டி, முழுவதும் தப்பிப்பிழைக்கும் tokens-ஐ மட்டும் வைத்துக்கொள்ள வேண்டும்.

'0}' மறுதிசையைக் காட்டுகிறது: அதே token "need a digit"-ல் சட்டவிரோதம் (JSON முன்னால் ஒரு zero வருவதைத் தடுக்கிறது), ஒரு state கழித்து சட்டப்படி சரி. சட்டப்படி சரியா என்பது அந்த ஜோடியின் பண்பு, token-ன் பண்பு அல்ல. அதனால் விடை ஒரு table:

Grammar characters-la pesudhu, model tokens-a kudukkudhu. Full token-a automaton-la ottunga; first character mattum paathaa '"}' nuzhainjidum.

அந்த table-தான் Willard-ம் Louf-ம் தந்த பங்களிப்பு. Masking அல்ல — மக்கள் ஏற்கனவே mask செய்துகொண்டிருந்தார்கள், அதே வருடத்தில் Geng et al. ஒரு grammar-ஐ ஒரு decoder-உடன் இணைத்திருந்தார்கள். Outlines-ன் கூற்று allowed set-ஐ எப்போது கணக்கிடுகிறீர்கள் என்பது பற்றியது: ஒவ்வொரு உருவாக்கப்பட்ட token-க்கும் ஒரு முறை அல்ல, ஒவ்வொரு (grammar, tokeniser) ஜோடிக்கும் ஒரு முறை, load time-ல்.

Index என்ன செலவாகிறது, என்ன மிச்சப்படுத்துகிறது

நான் milliseconds-க்குப் பதிலாக DFA character-steps-ஐ எண்ணுகிறேன், அதனால் script உங்கள் laptop-லும் என்னுடையதிலும் ஒரே எண்களை அச்சிடும். அதுவே நேர்மையான அலகும் கூட: அது வேலை, என் machine-ன் மனநிலை அல்ல.

இது உங்களுக்கு வாங்கித் தராதது என்ன

Constrained decoder-லிருந்து ஆறு outputs. ஆறும் parse ஆகின்றன. ஆறும் schema-வுடன் பொருந்துகின்றன. அவற்றில் பூஜ்ஜியம் உண்மை.

Schema validity என்பது output-ன் syntax-ன் பண்பு. உலகத்தைப் பற்றி அது எதுவும் சொல்வதில்லை. இங்கே என் "model" random noise, அது இந்தக் கருத்தைச் சத்தமாகச் சொல்கிறது — ஆனால் ஒரு நல்ல model-க்கும் இதே உண்மை: constraining தோல்விகளை "parse ஆகாதவை"-லிருந்து "parse ஆகும், ஆனால் தவறு" என்பதற்கு நகர்த்துகிறது — உங்கள் database-க்குள் நுழைவது இரண்டாவதுதான். Age 36-ஆ என்பது ஒரு eval கேள்வி — evals page-ஐப் பாருங்கள்.

இங்கேயே ஒரு நேர்மையான செலவும் சொல்லிவிடுகிறேன். Masking ஒரு subset மீது மறு-normalise செய்கிறது, அதனால் constrained distribution என்பது validity-ஐ வைத்து condition செய்யப்பட்ட model-ன் distribution அல்ல — அது ஒரு greedy, per-step approximation, அதனால் வரும் quality shifts-ஐ மக்கள் இரு திசைகளிலும் அளந்திருக்கிறார்கள். Constrained decoding-ஐ இலவசம் என்று விற்காதீர்கள். தெரிந்த, சிறிய ஒரு distortion கொடுத்து வாங்கும் ஒரு guarantee என்று விற்குங்கள்.

मैं एक AI Engineer हूँ। मैंने models ship किए हैं, MLOps किया है, और दो साल तक "JSON malformed आया" का मेरा जवाब एक बेहतर prompt और एक retry loop ही था। वह चलता था। इसके बारे में कही जा सकने वाली सबसे बुरी बात यही है। dev में चला, staging में चला, demo में चला, और फिर production में ऐसी दर पर fail हुआ जिसे कोई संख्या में नहीं बता सकता था — और retry loop उसे तब तक छिपाए रखता रहा जब तक invoice नहीं आ गया।

ध्यान दें: English technical words (constrained decoding, grammar, finite-state machine, mask, logits, token, vocabulary, parser state, JSON schema, regular, context-free, retry…) मैंने वैसे ही रखे हैं। क्योंकि code में और बाक़ी papers में आपको वही शब्द दिखेंगे। समझ हिंदी में, शब्दावली English में।

किसी ने मुझे नहीं बताया कि इस समस्या का एक ऐसा रूप भी है जिसमें असली guarantee मिलती है, और वह guarantee एक लाइन लंबी है।

        return json.loads(text)      # उम्मीद
    except ValueError:

यह validation है। यह बाद में चलता है, fail हो सकता है, और इसकी लागत एक random variable है। अब दूसरा रूप। हर step पर model आपको पूरे vocabulary पर एक logits vector देता है। एक parser जानता है कि उनमें से कौन-से tokens एक valid document को आगे बढ़ा सकते हैं। तो:

    logits[not_allowed(state)] = -np.inf    # <-- पूरा paper यही है

retry loop दिखने से ज़्यादा बुरा क्यों है

एक असली state machine, और "by construction" का मतलब

मेरा grammar एक तय schema है, whitespace नहीं: {"name":"<letters>","age":<digits>}. वह भाषा regular है, इसलिए एक finite-state machine काफ़ी है — कुल 20 states, जिनमें से 15 तय literals के भीतर बस एक-एक क़दम हैं। फिर loop चलता है, और हर step पर mask वही है जो वह state allow करता है।

Interview में "JSON" को लेकर सटीक रहिए। मेरे जैसा एक तय schema एक regular भाषा है, और एक finite-state machine उसे सँभाल लेता है। सामान्य JSON regular नहीं है — मनमाने nesting के लिए एक stack चाहिए, यानी एक context-free grammar और एक pushdown automaton। state-machine वाली कहानी उन schemas को cover करती है जो ज़्यादातर applications सचमुच चाहते हैं; "कोई भी JSON" को नहीं।

The code

Plain Python and NumPy. No torch, no model, no training — the automaton, the mask and the index, so you can watch the allowed set shrink. Every function under 20 lines.

Download the full script — nine short functions plus seven runnable demos. Then: 

python3 structured_output_from_scratch.py
def step_char(state, ch):
    """One character. None means 'this character cannot continue the doc'."""
    return DELTA.get(state, {}).get(ch)


def step_token(state, token):
    """Feed a whole token through, character by character.

    Returns the state after the token, or None if ANY character inside it
    fell off the automaton. A token is allowed or it is not; there is no
    partial credit, because you cannot emit half a token."""
    for ch in token:
        state = step_char(state, ch)
        if state is None:
            return None
    return state


def allowed_tokens(state):
    """Naive version: walk every token in the vocabulary through the DFA.

    Cost is O(vocab x token length) PER GENERATED TOKEN. This is the thing
    the Outlines paper removes."""
    out = {}
    for i, tok in enumerate(VOCAB):
        nxt = step_token(state, tok)
        if nxt is not None:
            out[i] = nxt
    return out


def apply_mask(logits, allowed):
    """Set every disallowed logit to -inf. Not 0 -- 0 is a perfectly ordinary
    logit that softmax will happily hand probability to."""
    masked = np.full_like(logits, -np.inf)
    idx = np.fromiter(allowed, dtype=int, count=len(allowed))
    masked[idx] = logits[idx]
    return masked


def build_index():
    """state -> {token id: state after that token}. Built once, reused forever."""
    return {s: allowed_tokens(s) for s in DELTA}

build_json_dfa (which chains one state per character of each fixed literal), generate (the loop from the top of this page, plus tracing), softmax, sample and the vocabulary list are all in the script.

On the maths anxiety

There is almost none here, and that surprised me. The retry section is one distribution — the geometric — and everything I printed from it is 1/p and a log to turn "how many attempts covers 95% of requests" into a number. You could derive that column in a spreadsheet.

The mechanism is a comparison and an assignment: is this token in a set, and if not, write −∞. The only "maths" is knowing why −∞ and not 0, and that's just knowing what exp(−∞) = 0 does inside a softmax. Same fact as the causal mask.

The genuinely useful theory is computer science, not maths, and it is the first-year kind: regular languages and finite-state machines, context-free grammars and pushdown automata, and the fact that a fixed schema lives in the first box while nested JSON lives in the second. If you can say which of those two your schema needs, you understand this paper. What you actually need on the job is different again: knowing your tokeniser, knowing your library (Outlines, guidance, llama.cpp's grammars, the structured-output modes the APIs now ship), and an eval set — because the failure mode you've just bought is confidently well-formed nonsense.

This page gave you the mask and the index. These give you the compiler, the competing designs, and the production ergonomics.

  • Efficient Guided Generation for Large Language Models Willard & Louf, 2023. The Outlines paper. The original.

    Read it for the construction I hand-wrote: regex and schema compiled to a finite-state machine, and the indexing argument that makes the allowed-set lookup cheap enough to run per token. Short, and much easier once you have the state table above in your head.

  • Grammar-Constrained Decoding for Structured NLP Tasks without Finetuning Geng, Josifoski, Peyrard & West, 2023. Earlier, and about the results.

    The half I skipped entirely: what constraining does to task accuracy on real benchmarks with real models, versus fine-tuning for the same output shape. Note the arXiv title says "without Finetuning" — the paper is often cited under an earlier wording.

  • Outlines documentation dottxt. The library the paper became. Code, not maths.

    What this looks like when someone else has done the work: a Pydantic model or a regex in, guaranteed-shaped output out. Read the JSON-schema and regex pages to see which parts of a schema actually compile to a machine.

  • Coalescence: making LLM inference 5× faster Louf. A blog post, with the diagrams the paper doesn't have.

    The follow-up idea I left out: when a state's allowed set has exactly one member you can skip the model call altogether, which is why constrained decoding can be faster than unconstrained. It also shows the distribution shift that trick causes, honestly.

Order I'd take them in: Outlines docs first — run it on your own schema and see the guarantee before you read about it — then the Willard & Louf paper for the machine, then Geng et al. for whether it helps accuracy, then coalescence when you start caring about latency.
