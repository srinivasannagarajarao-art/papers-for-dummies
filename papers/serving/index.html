How a serving engine actually works

Kwon et al., 2023 — PagedAttention and vLLM

The KV-cache page stopped at the arithmetic. Everything above that line is an operating system, and this is the part you actually operate.

Download serving_from_scratch.py — everything below runs from it. NumPy only, and no GPU: it simulates the queue and the allocator with counters.

I wrote the KV-cache page and it name-drops "continuous batching" and "PagedAttention" seven times without building either. That bothered me. Those two phrases are the difference between a demo that serves one person and a service that serves a thousand, and I was repeating them the way you repeat a library name you have never read the source of.

So here they are, both built. And the surprise, once you build them, is that neither one is about machine learning. Attention never changes. Not one line of the model changes. What changes is who gets a slot and where the bytes live — scheduling and memory management, the two problems an operating system was invented to solve.

A serving engine is an operating system

You already know both halves of this paper. Here is the first one — the batch loop everyone writes on day one: 

for batch in chunks(requests, 8):
    outputs = model.generate(batch)   # returns when the LAST one is done
    send(outputs)

That is run-to-completion scheduling. A 1970s batch mainframe. If seven replies finish in 8 tokens and the eighth runs to 128, seven slots sit there holding memory and doing nothing for 120 iterations. The fix is the same fix the OS people found: schedule between every iteration, not between every batch. 

while queue or running:
    while len(running) < slots and queue:
        running.append(queue.pop(0))   # a free slot is refilled NOW
    step(running)                      # every live sequence emits one token
    running = [r for r in running if not r.done()]

That is continuous batching, and it comes from Orca (Yu et al., "Orca: A Distributed Serving System for Transformer-Based Generative Models", OSDI 2022), where it is called iteration-level scheduling. Same idea, better name.

Now the second half. Here is how you would allocate the KV cache, and it is also the first thing anyone writes: 

cache = torch.empty(batch, MAX_MODEL_LEN, ...)   # reserve the worst case

That is a fixed-size contiguous allocation per process. You don't know how long the reply will be, so you reserve the maximum, and you reserve it contiguously because attention wants to index it as one array. Both of those choices cost you. PagedAttention's move is to notice that the operating system solved this in 1962 and stop reinventing it badly: fixed- size blocks, a per-sequence block table, allocate on demand.

The one formula

Not an attention formula. The paper's actual contribution is an address translation, and it is the same one your MMU does:

physical_addr(seq, i) = block_table[seq][ ⌊i / B⌋ ] × B + (i mod B)

Read it as stages:

TermTypicalWhat it does
i0…seq_lenThe logical position of a token in this sequence
B16Block size in tokens. The one tuning knob on this whole page
⌊i / B⌋0…n_blocksLogical block number. Which page of my cache
block_table[seq]a list of intsThe page table. One per sequence. This is the whole idea
i mod B0…B−1Offset inside the block

One indirection. That is the paper. Everything else — the sharing, the near-zero waste, the concurrency — falls out of the fact that logical positions no longer have to be physically adjacent.

Static batching: the GPU you paid for, idle

The script simulates 64 requests arriving over time with realistically uneven output lengths, and counts slot-steps: a slot held for one iteration. A slot-step that produced a token is work. One that didn't is money.

Identical tokens out of identical weights. Sixty-three per cent of the machine was being paid for and not used. You can see exactly where it goes if you print one batch at a time:

Batch 2 is the control. Its output lengths are nearly uniform, and its occupancy is 70% instead of 26%. Static batching isn't slow because batching is bad — it's slow because reply lengths vary and you can't know them in advance. If every reply were 64 tokens, none of this page would exist.

Reserving memory you will never write

Now the allocator. Same workload, requests arriving and finishing over time, and a 40 GiB slice of an 80 GB card for KV cache. At Llama-2-7B shape that is 512 KiB per token, so 81,920 tokens total — the arithmetic is straight out of the KV-cache page.

Three allocators, one budget: reserve max_model_len for everyone, reserve each caller's own max_new_tokens, or page it. 

contiguous, reserve max_model_len (2048) for everyone:
  peak concurrent requests :     40
  admitted / rejected      :     90 / 310
  at the first rejection   : wanted 2048 tokens, 0 free, biggest hole 0

contiguous, reserve each caller's own max_new_tokens:
  peak concurrent requests :    159
  admitted / rejected      :    305 / 95
  at the first rejection   : wanted 1160 tokens, 2,927 free, biggest hole 959
  external fragmentation   : 1,968 free tokens that exist but not in one piece

paged, block size 16, allocated on demand:
  peak concurrent requests :    230
  admitted / rejected      :    400 / 0
  tokens held / written    : 77,696 / 74,744
  internal waste           : 2,952 (3.8%, and never more than 15 per sequence)
  external fragmentation   : 0 -- every free block fits every sequence

peak concurrency, same 40 GiB:
  40 (reserve max_model_len) -> 159 (reserve max_new_tokens) -> 230 (paged)
  = 5.8x more concurrent users, and nobody was turned away

Read the middle block twice, because it is the one people miss. There were 2,927 free tokens and the request wanted 1,160 — and it was rejected anyway, because the biggest single hole was 959. That's external fragmentation: you have the memory, just not in one piece. Paging doesn't reduce it, it abolishes it. Every free block is interchangeable, so a free block is always usable by anyone.

Internal waste is the other half. Reserving 2,048 tokens for a reply that runs to 40 wastes 98% of the reservation. With 16-token blocks you can overshoot by at most 15 tokens, once, in the last block. That is what the paper means by near-zero waste: it isn't clever, it's just bounded.

And block size is the one knob, so break it in both directions:

block size sweep, same workload and same memory:
  block | peak | rejected | internal waste | table entries at peak
      1 |  230 |        0 |              0 |        42978
      4 |  230 |        0 |            588 |        10829
     16 |  230 |        0 |          2,952 |         2792 ✓
     64 |  230 |        0 |         12,360 |          783
    256 |  230 |        0 |         47,624 |          275
   1024 |   80 |      226 |        146,270 |           80

At block size 1 there is zero waste and the block table has 43,000 entries to manage — you have rebuilt malloc's metadata problem. At 1,024 the waste (146,270 tokens) is nearly twice the data actually written, concurrency collapses to 80, and 226 requests get turned away. vLLM ships 16.

The block table, printed small enough to read

Here is a 10-token sequence with a deliberately silly block size of 4, on an allocator whose free list has been shuffled by earlier traffic: 

sequence of 10 tokens, block size 4
  logical block -> physical block
    0 -> 5
    1 -> 2
    2 -> 9
  physical blocks: [5, 2, 9]  <- NOT contiguous, and that is fine
  tokens 10, blocks 3, internal waste 2 tokens (last block only)

decode 3 more tokens, one at a time:
  n_tokens= 11 table=[5, 2, 9]  wrote into the current block
  n_tokens= 12 table=[5, 2, 9]  wrote into the current block
  n_tokens= 13 table=[5, 2, 9, 0]  appended a new physical block

Blocks 5, 2 and 9. Nowhere near each other. Attention reads the sequence through the table, so it never notices — this is precisely why the paper needed a custom attention kernel, and precisely why nothing about the attention maths changed. And growth costs one block append, not a realloc-and-copy of the whole cache.

Copy-on-write, because you have used fork()

Ask for four samples from one prompt and the naive engine keeps four copies of the prompt's cache. But those four sequences are identical until the first token diverges. So: share the blocks, refcount them, and copy only the block someone actually writes into. 

prompt 90 tokens = 6 blocks: [0, 1, 2, 3, 4, 5]
blocks used after prompt: 6

forked 4 samples from it (parallel sampling):
  blocks used: 6  (unchanged -- all four share)
  refcounts  : [5, 5, 5, 5, 5, 5]
  naive copy would need 30 blocks; we hold 6
  saved: 24 blocks = 192.0 MiB

now each sample generates its first token (they diverge):
  sample-0: table=[0, 1, 2, 3, 4, 6]  copy-on-write triggered: True
  sample-1: table=[0, 1, 2, 3, 4, 7]  copy-on-write triggered: True
  sample-2: table=[0, 1, 2, 3, 4, 8]  copy-on-write triggered: True
  sample-3: table=[0, 1, 2, 3, 4, 9]  copy-on-write triggered: True
  blocks used now     : 10  (one private block each, the rest still shared)

Five shared blocks, one private each. Blocks 0–4 are still refcount 5 and still one copy. 192 MiB saved on a 90-token prompt, which sounds absurd until you remember that half a megabyte per token is the number from the KV-cache page.

Then the bug that this design invites. Sample-0 finishes. Do you free its blocks? 

the reference-counting guard:
  released sample-0. block 0 refcount now 4
  block 0 back on the free list? False  <- still referenced, so no
  released everyone. block 0 on the free list? True
This is a double free, and it fails silently. Delete the if self.refcount[b] == 0 guard and sample-0 finishing hands a live prompt block back to the pool. The next request allocates it, writes its own keys into it, and sample-1 keeps decoding — against someone else's prompt. No crash. No error. Just wrong tokens. Refcounting isn't bookkeeping here, it's the correctness argument.

Prefix caching: prefill you already did

Same trick, across requests instead of within one. A 300-token system prompt shared by everyone is 300 tokens of prefill that only ever needs doing once. Hash a block's prefix, and if it's resident, point at it. 

fraction of requests using the shared system prompt: 100%
  prompt tokens seen        :  17,000
  prompt tokens prefilled   :   2,888
  prefill work saved        :  83.0%
  block cache hit rate      :  84.0%

fraction of requests using the shared system prompt: 50%
  prompt tokens seen        :  17,000
  prompt tokens prefilled   :  11,528
  prefill work saved        :  32.2%
  block cache hit rate      :  32.6%

fraction of requests using the shared system prompt: 0%
  prompt tokens seen        :  17,000
  prompt tokens prefilled   :  17,000
  prefill work saved        :   0.0%
  block cache hit rate      :   0.0%

The saving is exactly the shared prefix and not one token more, which is the honest way to think about it: prefix caching is a workload property you can engineer, not a speedup you turn on. Put the volatile part of your prompt (the timestamp, the user id) at the front and your hit rate is the 0% row.

My script hashes whole prefixes in a dict, so it only matches from token 0. RadixAttention, in SGLang (Zheng et al.), keeps those prefixes in a radix tree instead. Two requests that share the first 300 tokens and diverge after still share every block up to the divergence, the tree finds the longest match automatically, and eviction is LRU on the leaves. A trie of prompts. You have written one.

Prefill and decode are two different jobs

The last piece is scheduling again, and it starts with the arithmetic intensity argument from the KV-cache page: MACs per byte of memory traffic, and whether a card can keep its arithmetic units fed. The script also applies a roofline — a pass takes as long as the slower of its arithmetic and its memory traffic — using an A100's two spec numbers. Nothing here is measured on a GPU; it is a count and a division. 

arithmetic intensity (MACs per byte moved), Llama-2-7B shape:
  prefill, 2048-token prompt :    783.8 MACs/byte
  decode, one token per seq, batch 32:     7.49 MACs/byte
  a card needs roughly 100-300 to keep its arithmetic units busy

roofline time (A100-shaped: 156 TMAC/s, 2.0 TB/s):
  prefill 2048 tokens :   11407.4 GMAC,   14.6 GB ->   73.12 ms  (compute-bound)
  decode step, batch 32:     165.4 GMAC,   22.1 GB ->   11.03 ms  (memory-bound)

Two different machines. Now put them on one GPU and let a 2,048-token prompt arrive while 32 people are mid-reply: 

shared GPU  : 32 sequences decoding, 40 steps
  median inter-token gap    :    11.03 ms
  p95 inter-token gap       :    11.03 ms
  worst inter-token gap     :    84.16 ms

disaggregated: 32 sequences decoding, 40 steps
  median inter-token gap    :    11.03 ms
  p95 inter-token gap       :    11.03 ms
  worst inter-token gap     :    11.03 ms ✓

the stall: one token took 84.2 ms instead of 11.0 -- 7.6x
all 32 decoding users saw it, and none of them sent that prompt.

That is head-of-line blocking, and note where it shows up: the median is untouched, the tail is 7.6× worse, and the victims are 32 people who did nothing. Your p50 dashboard will look fine.

The standard mitigation is to slice the prefill:

chunked prefill: same prefill, sliced, one chunk per iteration
  chunk  2048 ->  1 iterations, worst gap   84.16 ms
  chunk   512 ->  4 iterations, worst gap   29.32 ms
  chunk   256 ->  8 iterations, worst gap   20.18 ms
  chunk   128 -> 16 iterations, worst gap   18.31 ms

Watch the last two rows: halving the chunk from 256 to 128 barely helps. Below a certain size each chunk is dragging all 13 GB of weights across the bus anyway, so you have hit the memory floor and are only adding passes. Chunking caps the stall; it can't remove it, and it spends decode iterations on prefill work.

Disaggregation is the other answer. DistServe (Zhong et al.) puts prefill and decode on separate GPUs and ships the KV cache between them. A prefill then cannot delay a decode at all, and each pool can be sized and parallelised for its own bottleneck — FLOPs on one side, bandwidth on the other. The cost is a cache transfer per request, which is why this is a later idea and not the first one.

When there are no free blocks left

One more failure the block design lets you see clearly. Admit a request when the pool is empty and nothing can move: 

4 sequences x 2 blocks = 8/8 blocks used
free blocks: []

every sequence now wants one more token:
  seq-0 append -> OutOfBlocks: no free physical blocks
  no free block, no policy: the scheduler cannot advance ANY
  sequence, and none of them can finish without advancing.
  <- this is the deadlock

with preemption (vLLM's swap-or-recompute, all-or-nothing):
  preempt seq-3, evict its 2 blocks, push it back on the queue
  free blocks now: [6, 7]
  seq-0 append -> ok, table=[0, 1, 6], n_tokens=33

Every sequence needs one more block, every block is taken, and no sequence can finish without growing. Classic. The resolution is the OS one: pick a victim, take everything it has, put it back on the queue. Note everything — preemption is all-or-nothing per sequence, because a half-evicted sequence can't run at all. The evicted sequence loses its cache, not its tokens: it gets re-prefilled later, or its blocks get swapped back from host memory.

Serving engine என்பது ஒரு operating system

இந்தக் கட்டுரையின் இரண்டு பாதிகளும் உங்களுக்கு ஏற்கனவே தெரியும். இதோ முதல் பாதி — முதல் நாளே எல்லோரும் எழுதும் batch loop: 

for batch in chunks(requests, 8):
    outputs = model.generate(batch)   # கடைசி ஒன்று முடிந்தால்தான் return
    send(outputs)

இது run-to-completion scheduling. 1970-களின் batch mainframe. ஏழு பதில்கள் 8 tokens-ல் முடிந்து, எட்டாவது 128 வரை ஓடினால், அந்த ஏழு slots 120 iterations-க்கு memory-ஐப் பிடித்துக்கொண்டு ஒன்றுமே செய்யாமல் உட்கார்ந்திருக்கும். சரிசெய்யும் வழி, OS-காரர்கள் கண்டுபிடித்த அதே வழிதான்: ஒவ்வொரு batch-க்கும் இடையில் அல்ல, ஒவ்வொரு iteration-க்கும் இடையில் schedule செய். 

while queue or running:
    while len(running) < slots and queue:
        running.append(queue.pop(0))   # காலி slot உடனே நிரப்பப்படும்
    step(running)                      # ஒவ்வொரு sequence-ம் ஒரு token
    running = [r for r in running if not r.done()]

இதுதான் continuous batching. இது Orca-வில் இருந்து வருகிறது (Yu et al., "Orca: A Distributed Serving System for Transformer-Based Generative Models", OSDI 2022). அங்கே இதற்கு iteration-level scheduling என்று பெயர். ஒரே கருத்து, சிறந்த பெயர்.

Static batching = run-to-completion. Kadaisi sequence mudiyara varaikkum ellaa slots-um kaathirukkum. Continuous batching = ovvoru iteration-kkum idayila schedule pannu, kaali slot-a udane nirappu.

இப்போது இரண்டாம் பாதி. KV cache-ஐ நீங்கள் எப்படி allocate செய்வீர்கள் என்பது இதோ — இதுவும் எல்லோரும் முதலில் எழுதுவதுதான்: 

cache = torch.empty(batch, MAX_MODEL_LEN, ...)   # மோசமான நிலைக்கே ஒதுக்கு

இது ஒவ்வொரு process-க்கும் ஒரு நிலையான அளவு, தொடர்ச்சியான (contiguous) allocation. பதில் எவ்வளவு நீளமாக இருக்கும் என்று உங்களுக்குத் தெரியாது, அதனால் அதிகபட்சத்தை ஒதுக்குகிறீர்கள். Attention அதை ஒரே array-ஆக index செய்ய விரும்புவதால் தொடர்ச்சியாக ஒதுக்குகிறீர்கள். இந்த இரண்டு முடிவுகளும் விலை கேட்கும். PagedAttention-ன் நகர்வு எளிது: இதை operating system 1962-லேயே தீர்த்துவிட்டது, மோசமாக மறுகண்டுபிடிப்பு செய்வதை நிறுத்துங்கள் — நிலையான அளவு blocks, ஒவ்வொரு sequence-க்கும் ஒரு block table, தேவைப்படும்போது மட்டும் allocate.

அந்த ஒரு சூத்திரம்

இது attention சூத்திரம் அல்ல. இந்தக் கட்டுரையின் உண்மையான பங்களிப்பு ஒரு address translation — உங்கள் MMU செய்வதே இதுதான்:

physical_addr(seq, i) = block_table[seq][ ⌊i / B⌋ ] × B + (i mod B)

இதைப் படிகளாகப் படியுங்கள்:

சொல்வழக்கமான மதிப்புஎன்ன செய்கிறது
i0…seq_lenஇந்த sequence-ல் ஒரு token-ன் logical இடம்
B16Tokens-ல் block size. இந்தப் பக்கம் முழுவதிலும் உள்ள ஒரே tuning knob
⌊i / B⌋0…n_blocksLogical block number. என் cache-ன் எந்தப் page
block_table[seq]ints-ன் ஒரு listஅதுதான் page table. ஒரு sequence-க்கு ஒன்று. இதுதான் முழு கருத்து
i mod B0…B−1Block-க்கு உள்ளே offset

ஒரே ஒரு indirection. அதுதான் இந்தக் கட்டுரை. மீதி எல்லாம் — sharing, கிட்டத்தட்ட பூஜ்ஜிய வீண், concurrency — logical இடங்கள் இனி physical-ஆக அருகருகே இருக்க வேண்டியதில்லை என்ற ஒற்றை உண்மையிலிருந்து விழுகின்றன.

Static batching: நீங்கள் பணம் கொடுத்த GPU, சும்மா

Script, 64 requests நேரத்துக்கு நேரம் வருவதைச் சிமுலேட் செய்கிறது — நிஜத்தில் இருப்பது போல ஏற்றத்தாழ்வான output நீளங்களுடன். பிறகு slot-steps எண்ணுகிறது: ஒரு iteration-க்குப் பிடித்து வைத்த ஒரு slot. Token உற்பத்தி செய்த slot-step என்பது வேலை. செய்யாதது பணம்.

எழுதவே மாட்டீர்கள், ஆனாலும் ஒதுக்கும் memory

இப்போது allocator. அதே workload, requests வந்து முடிந்து போகின்றன, 80 GB card-ல் KV cache-க்கு 40 GiB துண்டு. Llama-2-7B அளவில் ஒரு token-க்கு 512 KiB, அதாவது மொத்தம் 81,920 tokens — இந்தக் கணக்கு நேராக KV-cache பக்கத்திலிருந்து வருகிறது.

மூன்று allocators, ஒரே budget: எல்லோருக்கும் max_model_len ஒதுக்கு, அல்லது ஒவ்வொருவரின் சொந்த max_new_tokens ஒதுக்கு, அல்லது page செய்.

  peak concurrent requests :     40

  at the first rejection   : wanted 2048 tokens, 0 free, biggest hole 0

contiguous, reserve each caller's own max_new_tokens:
  peak concurrent requests :    159

நடுவில் உள்ள block-ஐ இரண்டு முறை படியுங்கள் — இதைத்தான் பெரும்பாலானோர் தவறவிடுகிறார்கள். 2,927 tokens காலியாக இருந்தன, request கேட்டது 1,160 — இருந்தும் அது நிராகரிக்கப்பட்டது, ஏனெனில் மிகப்பெரிய ஒற்றைத் துளை 959 மட்டுமே. அதுதான் external fragmentation: memory உங்களிடம் இருக்கிறது, ஆனால் ஒரே துண்டாக இல்லை. Paging அதைக் குறைக்கவில்லை, அதை அழிக்கிறது. ஒவ்வொரு காலி block-ம் ஒன்றுக்கொன்று மாற்றக்கூடியது, அதனால் ஒரு காலி block எப்போதும் எவருக்கும் பயன்படும்.

Internal waste என்பது மற்றொரு பாதி. 40 tokens வரை மட்டும் ஓடும் ஒரு பதிலுக்கு 2,048 tokens ஒதுக்கினால், ஒதுக்கீட்டில் 98% வீண். 16-token blocks-உடன் நீங்கள் அதிகபட்சம் 15 tokens மட்டுமே, ஒரே ஒரு முறை, கடைசி block-ல் மீறுவீர்கள். கட்டுரை "near-zero waste" என்பதன் அர்த்தம் அதுதான்: இது புத்திசாலித்தனம் அல்ல, வெறுமனே எல்லை வகுக்கப்பட்டது.

Block size ஒன்றுதான் knob, அதனால் அதை இரு திசைகளிலும் உடையுங்கள்:

Block table, படிக்கும் அளவுக்குச் சிறியதாக print செய்யப்பட்டது

இதோ 10-token sequence, வேண்டுமென்றே முட்டாள்தனமான block size 4-உடன் — முந்தைய traffic-ஆல் free list கலைக்கப்பட்ட ஒரு allocator-ல்: 

sequence of 10 tokens, block size 4
  logical block -> physical block
    0 -> 5
    1 -> 2
    2 -> 9
  physical blocks: [5, 2, 9]  <- NOT contiguous, and that is fine
  tokens 10, blocks 3, internal waste 2 tokens (last block only)

decode 3 more tokens, one at a time:
  n_tokens= 11 table=[5, 2, 9]  wrote into the current block
  n_tokens= 12 table=[5, 2, 9]  wrote into the current block
  n_tokens= 13 table=[5, 2, 9, 0]  appended a new physical block

Blocks 5, 2, 9. ஒன்றுக்கொன்று அருகில் இல்லவே இல்லை. Attention அந்த sequence-ஐ table-ன் வழியாகப் படிக்கிறது, அதனால் அது இதைக் கவனிக்கவே இல்லை — கட்டுரைக்கு ஏன் ஒரு custom attention kernel தேவைப்பட்டது என்பதற்கும், attention-ன் கணிதத்தில் ஏன் ஒன்றுமே மாறவில்லை என்பதற்கும் இதுதான் காரணம். வளர்ச்சிக்கு ஒரு block append மட்டுமே செலவு, முழு cache-ஐயும் realloc செய்து copy செய்வதல்ல.

Copy-on-write, ஏனெனில் நீங்கள் fork() பயன்படுத்தியிருக்கிறீர்கள்

ஒரே prompt-லிருந்து நான்கு samples கேளுங்கள் — அப்பாவி engine, prompt-ன் cache-ஐ நான்கு முறை நகல் எடுத்து வைத்திருக்கும். ஆனால் முதல் token பிரியும் வரை அந்த நான்கு sequences-ம் ஒரே மாதிரிதான். எனவே: blocks-ஐப் பகிர்ந்து கொள், அவற்றை refcount செய், யாராவது உண்மையில் எழுதும் block-ஐ மட்டும் copy செய். 

prompt 90 tokens = 6 blocks: [0, 1, 2, 3, 4, 5]
blocks used after prompt: 6

forked 4 samples from it (parallel sampling):
  blocks used: 6  (unchanged -- all four share)
  refcounts  : [5, 5, 5, 5, 5, 5]
  naive copy would need 30 blocks; we hold 6
  saved: 24 blocks = 192.0 MiB

now each sample generates its first token (they diverge):
  sample-0: table=[0, 1, 2, 3, 4, 6]  copy-on-write triggered: True
  sample-1: table=[0, 1, 2, 3, 4, 7]  copy-on-write triggered: True
  sample-2: table=[0, 1, 2, 3, 4, 8]  copy-on-write triggered: True
  sample-3: table=[0, 1, 2, 3, 4, 9]  copy-on-write triggered: True
  blocks used now     : 10  (one private block each, the rest still shared)

ஐந்து பகிரப்பட்ட blocks, ஒவ்வொருவருக்கும் ஒரு தனிப்பட்ட block. Blocks 0–4 இன்னும் refcount 5, இன்னும் ஒரே ஒரு நகல். 90-token prompt-ல் 192 MiB சேமிப்பு — ஒரு token-க்கு அரை megabyte என்ற எண் KV-cache பக்கத்திலிருந்து வருகிறது என்பதை நினைவுபடுத்திக்கொள்ளும் வரை இது அபத்தமாகத் தோன்றும்.

பிறகு, இந்த design வரவழைக்கும் bug. Sample-0 முடிகிறது. அதன் blocks-ஐ free செய்வீர்களா? 

the reference-counting guard:
  released sample-0. block 0 refcount now 4
  block 0 back on the free list? False  <- still referenced, so no
  released everyone. block 0 on the free list? True
இது ஒரு double free, அது சத்தமே இல்லாமல் தோற்கிறது. if self.refcount[b] == 0 guard-ஐ நீக்குங்கள் — sample-0 முடியும்போது உயிருள்ள ஒரு prompt block-ஐ pool-க்குத் திருப்பித் தந்துவிடும். அடுத்த request அதை allocate செய்து, தன் keys-ஐ அதில் எழுதுகிறது, sample-1 தொடர்ந்து decode செய்கிறது — இன்னொருவரின் prompt-க்கு எதிராக. Crash இல்லை. Error இல்லை. வெறும் தவறான tokens. இங்கே refcounting என்பது கணக்கு வழக்கு அல்ல, அதுதான் correctness argument.

Refcount guard-a edunga, sample-0 mudiyum podhu live prompt block pool-ku poidum. Adutha request adhula ezhuthum, sample-1 vera oruthanoda prompt-a padikkum. Crash illa, error illa — thappana tokens mattum.

Prefix caching: ஏற்கனவே செய்த prefill

அதே தந்திரம், ஒரே request-க்குள் அல்ல, requests-க்கு இடையில். எல்லோரும் பகிர்ந்துகொள்ளும் 300-token system prompt என்பது ஒரே ஒரு முறை மட்டும் செய்ய வேண்டிய 300 tokens prefill. ஒரு block-ன் prefix-ஐ hash செய், அது இருந்தால் அதைச் சுட்டு.

சேமிப்பு என்பது சரியாகப் பகிரப்பட்ட prefix அளவுதான், ஒரு token கூட அதிகம் இல்லை. இதைப் பற்றி நேர்மையாக யோசிக்கும் வழி இதுதான்: prefix caching என்பது நீங்கள் on செய்யும் speedup அல்ல, நீங்கள் engineer செய்யக் கூடிய ஒரு workload பண்பு. உங்கள் prompt-ன் மாறும் பகுதியை (timestamp, user id) முன்னால் வையுங்கள் — உங்கள் hit rate அந்த 0% வரிதான்.

என் script முழு prefixes-ஐயும் ஒரு dict-ல் hash செய்கிறது, அதனால் அது token 0-லிருந்து மட்டுமே match ஆகும். RadixAttention, SGLang-ல் (Zheng et al.), அந்த prefixes-ஐ ஒரு radix tree-ல் வைக்கிறது. முதல் 300 tokens-ஐப் பகிர்ந்து பிறகு பிரியும் இரண்டு requests, பிரியும் இடம் வரை ஒவ்வொரு block-ஐயும் பகிர்கின்றன. Tree தானாகவே மிக நீளமான match-ஐக் கண்டுபிடிக்கிறது, eviction என்பது leaves-ல் LRU. Prompts-ன் ஒரு trie. நீங்கள் ஒன்று எழுதியிருக்கிறீர்கள்.

Prefill-ம் decode-ம் இரண்டு வெவ்வேறு வேலைகள்

கடைசிப் பகுதி மீண்டும் scheduling-தான். இது KV-cache பக்கத்தின் arithmetic intensity வாதத்திலிருந்து தொடங்குகிறது: memory traffic-ன் ஒவ்வொரு byte-க்கும் எத்தனை MACs, மற்றும் ஒரு card தன் arithmetic units-க்கு உணவு கொடுத்துக்கொண்டே இருக்க முடியுமா என்பது. Script ஒரு roofline-ஐயும் பயன்படுத்துகிறது — ஒரு pass, அதன் arithmetic-ஐயும் memory traffic-ஐயும் ஒப்பிட்டு எது மெதுவோ அவ்வளவு நேரம் எடுக்கும் — A100-ன் இரண்டு spec எண்களை வைத்து. இங்கே எதுவும் GPU-வில் அளக்கப்படவில்லை; இது ஒரு எண்ணிக்கையும் ஒரு வகுத்தலும் மட்டுமே. 

arithmetic intensity (MACs per byte moved), Llama-2-7B shape:
  prefill, 2048-token prompt :    783.8 MACs/byte
  decode, one token per seq, batch 32:     7.49 MACs/byte
  a card needs roughly 100-300 to keep its arithmetic units busy

roofline time (A100-shaped: 156 TMAC/s, 2.0 TB/s):

இரண்டு வெவ்வேறு இயந்திரங்கள். இப்போது இரண்டையும் ஒரே GPU-வில் வையுங்கள், 32 பேர் பதில் நடுவில் இருக்கும்போது ஒரு 2,048-token prompt வரட்டும்:

  median inter-token gap    :    11.03 ms
  p95 inter-token gap       :    11.03 ms
  worst inter-token gap     :    84.16 ms

disaggregated: 32 sequences decoding, 40 steps
  median inter-token gap    :    11.03 ms
  p95 inter-token gap       :    11.03 ms

அதுதான் head-of-line blocking. அது எங்கே தெரிகிறது என்பதைக் கவனியுங்கள்: median-ஐத் தொடவே இல்லை, tail 7.6× மோசம், பாதிக்கப்பட்டவர்கள் ஒன்றுமே செய்யாத 32 பேர். உங்கள் p50 dashboard நன்றாகவே இருக்கும்.

வழக்கமான தீர்வு prefill-ஐத் துண்டுகளாக வெட்டுவது:

chunked prefill: same prefill, sliced, one chunk per iteration
  chunk  2048 ->  1 iterations, worst gap   84.16 ms
  chunk   512 ->  4 iterations, worst gap   29.32 ms
  chunk   256 ->  8 iterations, worst gap   20.18 ms
  chunk   128 -> 16 iterations, worst gap   18.31 ms

கடைசி இரண்டு வரிகளைப் பாருங்கள்: chunk-ஐ 256-லிருந்து 128-ஆகப் பாதியாக்கினால் கிட்டத்தட்ட எந்த உதவியும் இல்லை. ஒரு குறிப்பிட்ட அளவுக்குக் கீழே, ஒவ்வொரு chunk-ம் 13 GB weights முழுவதையும் bus வழியாக இழுத்துக்கொண்டுதான் வருகிறது. அதாவது நீங்கள் memory தளத்தைத் தொட்டுவிட்டீர்கள், இனி passes-ஐ மட்டுமே கூட்டுகிறீர்கள். Chunking, stall-க்கு ஒரு உச்சவரம்பு வைக்கிறது; அதை நீக்க முடியாது, மேலும் prefill வேலைக்காக decode iterations-ஐச் செலவிடுகிறது.

Disaggregation என்பது மற்றொரு பதில். DistServe (Zhong et al.) prefill-ஐயும் decode-ஐயும் தனித்தனி GPUs-ல் வைத்து, KV cache-ஐ அவற்றுக்கு இடையே அனுப்புகிறது. அப்போது ஒரு prefill, ஒரு decode-ஐ கொஞ்சம் கூடத் தாமதப்படுத்த முடியாது. ஒவ்வொரு pool-ஐயும் அதன் சொந்த bottleneck-க்கு ஏற்ப அளவிடலாம், parallelise செய்யலாம் — ஒரு பக்கம் FLOPs, மறுபக்கம் bandwidth. விலை என்னவென்றால் ஒவ்வொரு request-க்கும் ஒரு cache transfer. அதனால்தான் இது பிந்தைய கருத்து, முதல் கருத்து அல்ல.

காலி blocks ஒன்றும் மிச்சமில்லாதபோது

Block design தெளிவாகக் காட்டும் இன்னொரு தோல்வி. Pool காலியாக இருக்கும்போது ஒரு request-ஐ உள்ளே விடுங்கள் — எதுவும் நகர முடியாது: 

4 sequences x 2 blocks = 8/8 blocks used
free blocks: []

every sequence now wants one more token:
  seq-0 append -> OutOfBlocks: no free physical blocks
  no free block, no policy: the scheduler cannot advance ANY
  sequence, and none of them can finish without advancing.
  <- this is the deadlock

with preemption (vLLM's swap-or-recompute, all-or-nothing):
  preempt seq-3, evict its 2 blocks, push it back on the queue
  free blocks now: [6, 7]
  seq-0 append -> ok, table=[0, 1, 6], n_tokens=33

ஒவ்வொரு sequence-க்கும் இன்னும் ஒரு block வேண்டும், ஒவ்வொரு block-ம் எடுக்கப்பட்டுவிட்டது, வளராமல் எந்த sequence-ம் முடிய முடியாது. வழக்கமான deadlock. தீர்வு OS-ன் தீர்வுதான்: ஒரு பலியைத் தேர்ந்தெடு, அதனிடம் உள்ள எல்லாவற்றையும் எடுத்துக்கொள், அதை மீண்டும் queue-ல் போடு. எல்லாவற்றையும் என்பதைக் கவனியுங்கள் — preemption என்பது ஒரு sequence-க்கு எல்லாம் அல்லது ஒன்றுமில்லை, ஏனெனில் பாதி வெளியேற்றப்பட்ட sequence ஓடவே முடியாது. வெளியேற்றப்பட்ட sequence இழப்பது அதன் cache-ஐ, அதன் tokens-ஐ அல்ல: பிறகு அது மீண்டும் prefill செய்யப்படும், அல்லது அதன் blocks host memory-லிருந்து swap செய்யப்பட்டு திரும்ப வரும்.

मैंने KV-cache वाला पन्ना लिखा और उसमें "continuous batching" और "PagedAttention" सात बार आते हैं — बिना दोनों में से एक भी बनाए। यह बात मुझे खटकती रही। ये दो शब्द ही वह फ़र्क़ हैं जो एक आदमी को जवाब देने वाले demo और हज़ार लोगों को जवाब देने वाली service के बीच है, और मैं उन्हें ऐसे दोहरा रहा था जैसे कोई library का नाम दोहराता है जिसका source उसने कभी पढ़ा ही नहीं।

ध्यान दें: English technical words (continuous batching, PagedAttention, block table, fragmentation, prefill, decode, preemption, throughput…) मैंने वैसे ही रखे हैं। क्योंकि code में, vLLM के config flags में और बाक़ी papers में आपको वही शब्द दिखेंगे। समझ हिंदी में, शब्दावली English में।

तो लीजिए, दोनों बने हुए। और बनाने के बाद जो हैरानी होती है वह यह है कि इनमें से किसी का भी machine learning से कोई लेना-देना नहीं। Attention कभी नहीं बदलता। Model की एक भी line नहीं बदलती। बदलता सिर्फ़ यह है कि slot किसे मिलेगा और bytes कहाँ रहेंगे — यानी scheduling और memory management, वही दो समस्याएँ जिन्हें हल करने के लिए operating system का आविष्कार हुआ था।

Serving engine एक operating system है

इस paper के दोनों हिस्से आप पहले से जानते हैं। यह रहा पहला — वही batch loop जो हर कोई पहले ही दिन लिखता है: 

for batch in chunks(requests, 8):
    outputs = model.generate(batch)   # आख़िरी वाला ख़त्म हो तभी return
    send(outputs)

यह run-to-completion scheduling है। 1970 का batch mainframe। अगर सात जवाब 8 tokens में ख़त्म हो जाएँ और आठवाँ 128 तक चले, तो सात slots 120 iterations तक memory पकड़े बैठे रहेंगे और कुछ नहीं करेंगे। इसका इलाज वही है जो OS वालों ने ढूँढा था: हर batch के बीच नहीं, हर iteration के बीच schedule करो। 

while queue or running:
    while len(running) < slots and queue:
        running.append(queue.pop(0))   # ख़ाली slot तुरंत भर जाता है
    step(running)                      # हर ज़िंदा sequence एक token
    running = [r for r in running if not r.done()]

यही continuous batching है, और यह Orca से आता है (Yu et al., "Orca: A Distributed Serving System for Transformer-Based Generative Models", OSDI 2022), जहाँ इसे iteration-level scheduling कहा गया है। विचार वही, नाम बेहतर।

अब दूसरा हिस्सा। KV cache आप कैसे allocate करेंगे — यह भी वही है जो हर कोई सबसे पहले लिखता है: 

cache = torch.empty(batch, MAX_MODEL_LEN, ...)   # सबसे बुरी हालत रिज़र्व

यह हर process के लिए एक तय आकार का contiguous allocation है। आपको पता नहीं कि जवाब कितना लंबा होगा, इसलिए आप अधिकतम रिज़र्व करते हैं, और contiguous रिज़र्व करते हैं क्योंकि attention उसे एक ही array की तरह index करना चाहता है। ये दोनों फ़ैसले महँगे पड़ते हैं। PagedAttention की चाल यही है कि operating system ने इसे 1962 में हल कर दिया था, तो उसे ख़राब तरीक़े से दोबारा मत बनाओ: तय आकार के blocks, हर sequence के लिए एक block table, और ज़रूरत पड़ने पर ही allocate।

वह एक सूत्र

यह attention का सूत्र नहीं है। इस paper का असली योगदान एक address translation है, और वही जो आपका MMU करता है:

physical_addr(seq, i) = block_table[seq][ ⌊i / B⌋ ] × B + (i mod B)

इसे चरणों की तरह पढ़िए:

शब्दआम मानयह क्या करता है
i0…seq_lenइसी sequence में token की logical जगह
B16Tokens में block size. इस पूरे पन्ने का इकलौता tuning knob
⌊i / B⌋0…n_blocksLogical block number. मेरे cache का कौन-सा page
block_table[seq]ints की एक listयही page table है. हर sequence के लिए एक। पूरा विचार यही है
i mod B0…B−1Block के अंदर offset

एक indirection। बस यही paper है। बाक़ी सब कुछ — sharing, लगभग शून्य बर्बादी, concurrency — इसी एक बात से निकलता है कि logical जगहों को अब physically साथ-साथ होने की ज़रूरत नहीं रही।

Static batching: जिस GPU के पैसे दिए, वह ख़ाली बैठा है

Script 64 requests को समय के साथ आते हुए simulate करता है, जिनकी output लंबाइयाँ असल दुनिया की तरह असमान हैं, और slot-steps गिनता है: एक iteration के लिए पकड़ा गया एक slot। जिस slot-step ने token बनाया वह काम है। जिसने नहीं बनाया वह पैसा है।

वह memory जिसे आप कभी लिखेंगे ही नहीं

अब allocator। वही workload, requests समय के साथ आती और ख़त्म होती हैं, और 80 GB card में से 40 GiB का हिस्सा KV cache के लिए। Llama-2-7B के आकार पर यह प्रति token 512 KiB है, यानी कुल 81,920 tokens — यह गणित सीधे KV-cache वाले पन्ने से आता है।

तीन allocators, एक ही budget: सबके लिए max_model_len रिज़र्व करो, या हर caller का अपना max_new_tokens रिज़र्व करो, या फिर उसे page करो। 

contiguous, reserve max_model_len (2048) for everyone:
  peak concurrent requests :     40
  admitted / rejected      :     90 / 310
  at the first rejection   : wanted 2048 tokens, 0 free, biggest hole 0

contiguous, reserve each caller's own max_new_tokens:
  peak concurrent requests :    159
  admitted / rejected      :    305 / 95
  at the first rejection   : wanted 1160 tokens, 2,927 free, biggest hole 959
  external fragmentation   : 1,968 free tokens that exist but not in one piece

paged, block size 16, allocated on demand:
  peak concurrent requests :    230
  admitted / rejected      :    400 / 0
  tokens held / written    : 77,696 / 74,744
  internal waste           : 2,952 (3.8%, and never more than 15 per sequence)
  external fragmentation   : 0 -- every free block fits every sequence

peak concurrency, same 40 GiB:
  40 (reserve max_model_len) -> 159 (reserve max_new_tokens) -> 230 (paged)
  = 5.8x more concurrent users, and nobody was turned away

बीच वाला block दो बार पढ़िए, क्योंकि यही वह जगह है जहाँ लोग चूक जाते हैं। 2,927 tokens ख़ाली थे और request को 1,160 चाहिए थे — फिर भी वह reject हुई, क्योंकि सबसे बड़ा अकेला छेद 959 का था। यही external fragmentation है: memory आपके पास है, बस एक टुकड़े में नहीं। Paging इसे कम नहीं करती, इसे ख़त्म कर देती है। हर ख़ाली block दूसरे जैसा ही है, इसलिए एक ख़ाली block हमेशा किसी के भी काम आ जाता है।

Internal waste दूसरा आधा हिस्सा है। जो जवाब 40 tokens में ख़त्म हो जाता है, उसके लिए 2,048 tokens रिज़र्व करने का मतलब है 98% रिज़र्वेशन बर्बाद। 16-token blocks के साथ आप ज़्यादा से ज़्यादा 15 tokens, एक ही बार, आख़िरी block में बर्बाद कर सकते हैं। Paper "near-zero waste" से यही कहना चाहता है: यह चतुराई नहीं है, यह बस सीमित है।

Block table, इतना छोटा छापा गया कि पढ़ा जा सके

यह रहा 10 tokens का एक sequence, जानबूझकर बेवक़ूफ़ाना block size 4 के साथ, एक ऐसे allocator पर जिसकी free list पहले की traffic से बिखर चुकी है: 

sequence of 10 tokens, block size 4
  logical block -> physical block
    0 -> 5
    1 -> 2
    2 -> 9
  physical blocks: [5, 2, 9]  <- NOT contiguous, and that is fine
  tokens 10, blocks 3, internal waste 2 tokens (last block only)

decode 3 more tokens, one at a time:
  n_tokens= 11 table=[5, 2, 9]  wrote into the current block
  n_tokens= 12 table=[5, 2, 9]  wrote into the current block
  n_tokens= 13 table=[5, 2, 9, 0]  appended a new physical block

Blocks 5, 2 और 9। एक-दूसरे के आसपास भी नहीं। Attention उस sequence को table के ज़रिए पढ़ता है, इसलिए उसे पता ही नहीं चलता — यही वजह है कि paper को एक custom attention kernel चाहिए था, और यही वजह है कि attention के गणित में कुछ नहीं बदला। और बढ़ने की क़ीमत सिर्फ़ एक block append है, पूरे cache का realloc-and-copy नहीं।

Copy-on-write, क्योंकि आपने fork() इस्तेमाल किया है

एक ही prompt से चार samples माँगिए और भोला engine prompt के cache की चार नक़लें रख लेगा। लेकिन पहला token अलग होने तक वे चारों sequences बिल्कुल एक जैसे हैं। तो: blocks साझा करो, उन्हें refcount करो, और सिर्फ़ उसी block की नक़ल बनाओ जिसमें कोई सच में लिखता है। 

prompt 90 tokens = 6 blocks: [0, 1, 2, 3, 4, 5]
blocks used after prompt: 6

forked 4 samples from it (parallel sampling):
  blocks used: 6  (unchanged -- all four share)
  refcounts  : [5, 5, 5, 5, 5, 5]
  naive copy would need 30 blocks; we hold 6
  saved: 24 blocks = 192.0 MiB

now each sample generates its first token (they diverge):
  sample-0: table=[0, 1, 2, 3, 4, 6]  copy-on-write triggered: True
  sample-1: table=[0, 1, 2, 3, 4, 7]  copy-on-write triggered: True
  sample-2: table=[0, 1, 2, 3, 4, 8]  copy-on-write triggered: True
  sample-3: table=[0, 1, 2, 3, 4, 9]  copy-on-write triggered: True
  blocks used now     : 10  (one private block each, the rest still shared)

पाँच साझा blocks, हर एक के पास एक निजी। Blocks 0–4 अब भी refcount 5 पर हैं और अब भी एक ही नक़ल हैं। 90 tokens के prompt पर 192 MiB की बचत — यह बेतुका लगता है, जब तक आपको याद न आए कि आधा megabyte प्रति token वाला आँकड़ा KV-cache वाले पन्ने से आता है।

और अब वह bug जो यह design ख़ुद बुलाता है। Sample-0 ख़त्म हो गया। क्या आप उसके blocks free करेंगे? 

the reference-counting guard:
  released sample-0. block 0 refcount now 4
  block 0 back on the free list? False  <- still referenced, so no
  released everyone. block 0 on the free list? True
यह एक double free है, और यह चुपचाप फ़ेल होता है। if self.refcount[b] == 0 guard हटा दीजिए, और sample-0 के ख़त्म होते ही एक ज़िंदा prompt block pool में वापस चला जाएगा। अगली request उसे allocate करेगी, अपनी keys उसमें लिखेगी, और sample-1 decode करता रहेगा — किसी और के prompt के ख़िलाफ़। न crash, न error। बस ग़लत tokens। यहाँ refcounting हिसाब-किताब नहीं है, वही correctness का तर्क है।

Prefix caching: वह prefill जो आप पहले ही कर चुके हैं

वही तरकीब, एक request के भीतर नहीं बल्कि requests के आर-पार। 300 tokens का एक system prompt जो सब साझा करते हैं, वह 300 tokens का prefill है जो ज़िंदगी में एक ही बार करना पड़ता है। Block के prefix को hash कीजिए, और अगर वह मौजूद है तो उसी की ओर इशारा कर दीजिए।

बचत ठीक उतनी ही है जितना साझा prefix है, एक token भी ज़्यादा नहीं — और इसे ईमानदारी से यूँ सोचना चाहिए: prefix caching कोई speedup नहीं है जिसे आप on करते हैं, यह workload का एक गुण है जिसे आप engineer कर सकते हैं। अपने prompt का बदलता हुआ हिस्सा (timestamp, user id) सबसे आगे रखिए और आपका hit rate वही 0% वाली पंक्ति होगा।

मेरा script पूरे prefixes को एक dict में hash करता है, इसलिए वह सिर्फ़ token 0 से match करता है। RadixAttention, जो SGLang (Zheng et al.) में है, उन prefixes को radix tree में रखता है। जो दो requests पहले 300 tokens साझा करती हैं और उसके बाद अलग हो जाती हैं, वे अलग होने तक हर block साझा करती हैं, tree सबसे लंबा match ख़ुद ढूँढ लेता है, और eviction पत्तों पर LRU है। Prompts का एक trie। आपने एक लिखा हुआ है।

Prefill और decode दो अलग काम हैं

आख़िरी हिस्सा फिर से scheduling का है, और यह KV-cache वाले पन्ने के arithmetic intensity वाले तर्क से शुरू होता है: memory traffic के हर byte पर कितने MACs, और क्या कोई card अपनी arithmetic units को व्यस्त रख सकता है। Script एक roofline भी लगाता है — एक pass उतना ही समय लेता है जितना उसके arithmetic और उसके memory traffic में से जो धीमा हो — A100 के दो spec आँकड़ों के साथ। यहाँ कुछ भी GPU पर मापा नहीं गया है; यह एक गिनती और एक भाग है। 

arithmetic intensity (MACs per byte moved), Llama-2-7B shape:
  prefill, 2048-token prompt :    783.8 MACs/byte
  decode, one token per seq, batch 32:     7.49 MACs/byte
  a card needs roughly 100-300 to keep its arithmetic units busy

roofline time (A100-shaped: 156 TMAC/s, 2.0 TB/s):
  prefill 2048 tokens :   11407.4 GMAC,   14.6 GB ->   73.12 ms  (compute-bound)
  decode step, batch 32:     165.4 GMAC,   22.1 GB ->   11.03 ms  (memory-bound)

दो अलग मशीनें। अब दोनों को एक ही GPU पर रखिए और 32 लोगों के जवाब के बीचों- बीच 2,048 tokens का एक prompt आने दीजिए:

  p95 inter-token gap       :    11.03 ms

यही head-of-line blocking है, और देखिए यह कहाँ दिखता है: median जस का तस, tail 7.6× ख़राब, और भुगतने वाले वे 32 लोग जिन्होंने कुछ किया ही नहीं। आपका p50 dashboard बिल्कुल ठीक दिखेगा।

आम इलाज यह है कि prefill को टुकड़ों में काट दिया जाए:

chunked prefill: same prefill, sliced, one chunk per iteration
  chunk  2048 ->  1 iterations, worst gap   84.16 ms
  chunk   512 ->  4 iterations, worst gap   29.32 ms
  chunk   256 ->  8 iterations, worst gap   20.18 ms
  chunk   128 -> 16 iterations, worst gap   18.31 ms

आख़िरी दो पंक्तियाँ देखिए: chunk को 256 से घटाकर 128 करने पर बमुश्किल कोई फ़ायदा होता है। एक हद के नीचे हर chunk वैसे भी पूरे 13 GB weights को bus पर घसीट रहा है, यानी आप memory की ज़मीन छू चुके हैं और अब सिर्फ़ passes बढ़ा रहे हैं। Chunking stall की सीमा बाँधती है; उसे मिटा नहीं सकती, और prefill के काम पर decode के iterations ख़र्च करती है।

Disaggregation दूसरा जवाब है। DistServe (Zhong et al.) prefill और decode को अलग-अलग GPUs पर रखता है और KV cache को उनके बीच भेजता है। तब कोई prefill किसी decode को ज़रा भी देर नहीं कर सकता, और हर pool को उसकी अपनी bottleneck के हिसाब से आकार और parallelism दिया जा सकता है — एक तरफ़ FLOPs, दूसरी तरफ़ bandwidth। क़ीमत है हर request पर एक cache transfer, और इसीलिए यह बाद का विचार है, पहला नहीं।

जब एक भी ख़ाली block नहीं बचता

एक और नाकामी जिसे यह block design साफ़ दिखा देता है। Pool ख़ाली हो और तब एक request भीतर लीजिए, फिर कुछ हिल ही नहीं सकता: 

4 sequences x 2 blocks = 8/8 blocks used
free blocks: []

every sequence now wants one more token:
  seq-0 append -> OutOfBlocks: no free physical blocks
  no free block, no policy: the scheduler cannot advance ANY
  sequence, and none of them can finish without advancing.
  <- this is the deadlock

with preemption (vLLM's swap-or-recompute, all-or-nothing):
  preempt seq-3, evict its 2 blocks, push it back on the queue
  free blocks now: [6, 7]
  seq-0 append -> ok, table=[0, 1, 6], n_tokens=33

हर sequence को एक और block चाहिए, हर block लिया जा चुका है, और बढ़े बिना कोई sequence ख़त्म नहीं हो सकती। क्लासिक। हल वही है जो OS का है: एक शिकार चुनो, उसके पास जो कुछ है सब ले लो, और उसे वापस queue में डाल दो। सब कुछ पर ध्यान दीजिए — preemption हर sequence के लिए "सब या कुछ भी नहीं" है, क्योंकि आधी हटाई गई sequence चल ही नहीं सकती। हटाई गई sequence अपना cache खोती है, अपने tokens नहीं: उसे बाद में दोबारा prefill किया जाता है, या उसके blocks host memory से swap करके वापस लाए जाते हैं।

The scheduler, entire:

def simulate_continuous_batching(reqs, slots):
    queue = list(reqs)
    running = []
    step = 0
    busy_slot_steps = 0
    total_slot_steps = 0
    tokens = 0
    while queue or running:
        # admit: refill any free slot from whoever has arrived
        while len(running) < slots and queue and queue[0].arrival <= step:
            r = queue.pop(0)
            r.start = step
            running.append(r)
        if not running:                    # idle gap, nobody has arrived yet
            step = queue[0].arrival
            continue
        for r in running:                  # one iteration = one token each
            r.generated += 1
            tokens += 1
            busy_slot_steps += 1
        total_slot_steps += slots
        step += 1
        for r in running:
            if r.done() and r.finish is None:
                r.finish = step
        running = [r for r in running if not r.done()]
    return dict(steps=step, tokens=tokens, busy=busy_slot_steps,
                capacity=total_slot_steps, reqs=reqs)

And the allocator — PagedAttention's storage layer, in about forty lines:

class BlockAllocator:
    def __init__(self, n_blocks, block_tokens=BLOCK_TOKENS):
        self.block_tokens = block_tokens
        self.free = list(range(n_blocks))      # a free list, nothing more
        self.refcount = {}                     # physical block -> refs
        self.n_blocks = n_blocks
        self.copies = 0                        # copy-on-write events

    def allocate(self):
        if not self.free:
            raise OutOfBlocks("no free physical blocks")
        b = self.free.pop(0)
        self.refcount[b] = 1
        return b

    def share(self, b):
        """Another sequence now points at this block. Do NOT copy it."""
        self.refcount[b] += 1
        return b

    def free_block(self, b):
        """The reference-counting guard: only the LAST owner really frees."""
        self.refcount[b] -= 1
        if self.refcount[b] == 0:
            self.free.append(b)
            del self.refcount[b]
            return True                        # actually returned to the pool
        return False                           # still shared, keep it alive

    def copy_on_write(self, b):
        """Writing into a shared block: take a private copy first."""
        if self.refcount[b] == 1:
            return b                           # sole owner, write in place
        new = self.allocate()
        self.refcount[b] -= 1
        self.copies += 1
        return new


class Sequence:
    """A sequence is a block table plus a length. That is the whole object."""

    def append_tokens(self, n):
        """Grow by n tokens, allocating a new physical block when needed."""
        for _ in range(n):
            slot = self.n_tokens % self.alloc.block_tokens
            if slot == 0:                                  # current block full
                self.table.append(self.alloc.allocate())
            else:                                          # writing inside one
                last = len(self.table) - 1
                self.table[last] = self.alloc.copy_on_write(self.table[last])
            self.n_tokens += 1

    def fork(self, name):
        """Parallel sampling: same prompt, new sequence, shared blocks."""
        child = Sequence(name, self.alloc)
        child.table = [self.alloc.share(b) for b in self.table]
        child.n_tokens = self.n_tokens
        return child

    def release(self):
        for b in self.table:
            self.alloc.free_block(b)
        self.table = []

On the maths anxiety

There is none here, and that is worth saying out loud. This page has one division and one modulo. If you can do i // 16 and i % 16, you have the maths.

The only arithmetic that gets close is the roofline in the last section, and it is two divisions: MACs divided by peak MACs per second, bytes divided by peak bytes per second, take the bigger one. That is a bound, not a prediction. I use it to show the shape — prefill compute-bound, decode memory-bound — because the shape is what decides your architecture, and the shape survives being wrong about the constants.

What this page needs instead is the stuff you already have: free lists, refcounts, fragmentation, head-of-line blocking, scheduling fairness, cache hit rates, deadlock. Those are the concepts under the arXiv numbers, and it is why this is the paper on the whole site an engineer is best equipped to read cold. If you have ever debugged a memory leak, you are qualified.
