The GPU, for people who only ever call .cuda()

The hardware every other page assumes

Not a paper. The model underneath four other pages on this site, so they stop being four separate mysteries.

Download gpu_from_scratch.py — everything below runs from it. NumPy only, no GPU required.

I wrote the FlashAttention page and said SRAM is small and HBM is far. I wrote the KV cache page and said decode is memory-bound. I wrote the DeepSeek-V3 page and said the interconnect is the constraint. Three pages, three hand-waves at the same machine, and I never once explained the machine.

This is that page. There is no paper to summarise — but there is one 2009 paper that organises all of it, and I have built the whole thing as arithmetic you can run. The claim: you can predict which of your operations will be slow before you profile anything, from one ratio.

Read this before anything else on the page. Every hardware number here is a published specification — a vendor datasheet figure, rounded, approximate, and named to the part it belongs to. Nothing was measured. Peak numbers are ceilings nobody reaches; real kernels land well below them. This page tells you which wall you are standing against, not how fast your code will run.

A memory hierarchy is a supply chain

You already reason like this about a database. Some data is in the process, some in Redis, some on a disk in the same rack, some in another region. You never think "this query is slow because the CPU is slow". You think "how many round trips did I just buy?" A GPU is the same shape:

LevelPlain meaningSupply chain
RegistersScratch values a single thread is holding right nowIn your hands
Shared memory / L1A scratchpad the programmer manages, private to one SMThe shelf behind you
L2 cacheShared by the whole die, automatic, not yours to controlThe stockroom
HBMThe GPU's main memory. What .cuda() puts things inWarehouse across the yard
NVLinkThe link to another GPU in the same serverThe next building
InfiniBandThe link to a GPU in another serverAnother site entirely

Three NVIDIA words, defined once. A streaming multiprocessor (SM) is one of the ~130 independent processors on the die; you get the whole GPU only if your work fills all of them. A warp is 32 threads executing the same instruction in lockstep. Shared memory is a software-managed scratchpad on each SM — not a cache you hope hits, a buffer you explicitly load into. HBM is the stacked DRAM on the package: the 80 GB number in the marketing.

The last column is the whole page in one number: peak FP16 throughput times the latency of that trip — the arithmetic you could have done while waiting. Half a billion floating point operations, for one round trip to the GPU's own main memory.

And the capacities run the other way: 228 KB of shared memory per SM against 80 GB of HBM. That asymmetry is not a detail — it is the entire reason FlashAttention exists, and why its tile size is what it is.

The chip is not slow at arithmetic. It is starving. Nearly every optimisation you will ever apply to a GPU is a way of taking fewer trips, or taking them further from the hot loop. Almost none of them are about doing less maths.

The one formula

Williams, Waterman and Patterson published this in 2009 — Roofline: An Insightful Visual Performance Model for Multicore Architectures, in Communications of the ACM. It predates CUDA's rise, predates tensor cores, predates every accelerator on this page, and still explains all of them, because it assumes only two things: you have a ceiling on arithmetic and a ceiling on bandwidth.

attainable FLOP/s = min( peak FLOP/s ,  bandwidth × I )    where I = FLOPs ÷ bytes moved

Read it as pipeline stages:

StepUnitsWhat it does
IFLOP/byteArithmetic intensity. A property of your operation, not the chip. How much work you get out of each byte you dragged in
bandwidth × IFLOP/sThe slanted roof. If you can only move B bytes a second and you do I flops per byte, that is your ceiling. No arithmetic unit can help
peak FLOP/sFLOP/sThe flat roof. The chip's published maximum. You cannot exceed it however many bytes you feed it
min(…)FLOP/sWhichever roof is lower is the one you hit. And which one it is tells you what to go and fix

That is it. Two straight lines and a min(). There is no curve to fit and nothing to measure. In code:

def roofline(intensity, peak_flops, bandwidth):
    memory_bound_ceiling = bandwidth * intensity
    attainable = min(peak_flops, memory_bound_ceiling)
    limiter = "compute" if memory_bound_ceiling >= peak_flops else "memory"
    return attainable, limiter

Six operations, and which wall each one hits

Here is the payoff. I counted FLOPs and bytes for six things you actually run, divided one by the other, and compared against two published H100 figures. Nothing profiled, nothing run on a GPU.

Byte counts assume the ideal case: each input read from HBM once, each output written once, everything else kept on chip. Real kernels move more, so these intensities are optimistic — which makes the bad news below worse, not better.

Ceiling  : 990 TFLOP/s dense FP16 tensor core (published peak)
Bandwidth: 3.35 TB/s HBM3 (published peak)
Ridge    : 295.5 FLOP/byte -- below this you are memory-bound

----------------------------------------------------------------------
element-wise add, n=67108864          0.167         0.6 TF/s     memory
mat-vec 4096x4096                     1.000         3.3 TF/s     memory
mat-mul 4096x4096x4096             1365.333       990.0 TF/s    compute ✓
attention, seq=512, d_head=64       256.000       857.6 TF/s     memory
attention, seq=8192, d_head=64     4096.000       990.0 TF/s    compute ✓
decode step, 7B params, batch=1       1.000         3.4 TF/s     memory

Four of six are memory-bound. The big square matrix multiply is the one operation here that genuinely uses the arithmetic units you paid for, and it is why a GPU looks fast in a benchmark. An element-wise add reaches 0.1% of the chip's arithmetic peak, because it touches every byte exactly once — which is why kernel fusion is not micro-optimisation for an add, it is the only lever that exists. Attention crosses the line as the sequence grows: seq=512 memory-bound, seq=8192 compute-bound, same kernel, same code. And the last row:

A single-token decode step sits at 1.00 FLOP/byte, roughly 296× below the ridge. Every weight is dragged out of HBM and used for two flops. The KV cache page argues decode is memory-bound from the software side, by counting what the cache costs. This is the same conclusion arriving from the hardware side, with no model in sight. Two independent routes, one answer — which is usually how you know a claim is structural rather than an artefact.

The ridge point, and why the field keeps getting more memory-bound

The two roofs meet somewhere. That crossover is the ridge point:

ridge = peak FLOP/s ÷ bandwidth   (FLOP per byte)

One number per chip per precision. Below it, memory-bound. Above it, compute-bound. It decides the fate of every kernel you will ever write, and you can compute it on a napkin from a datasheet.

Watch what it has been doing:

part                          HBM      FP16 peak ridge FLOP/byte
--------------------------------------------------------------
V100 SXM2 (2017)          0.90 TB/s        125 TF/s            139
A100 SXM  (2020)          2.04 TB/s        312 TF/s            153
H100 SXM  (2022)          3.35 TB/s        990 TF/s            296

Over those three parts:
  arithmetic throughput grew 7.9x
  memory bandwidth  grew 3.7x
  so the ridge point grew 2.1x

Arithmetic got cheap roughly twice as fast as bytes did. Which means the intensity you need in order to stay compute-bound goes up every generation. An operation that comfortably used a V100's arithmetic units can be memory-bound on an H100 without a single line of your code changing. You upgraded, and your kernel got relatively worse.

This is the thing I wish someone had told me five years ago. It explains why almost every interesting systems paper of the last five years is about moving fewer bytes rather than doing less arithmetic — FlashAttention, GQA, quantised caches, paged attention, all of it. The field did not decide to care about memory. The hardware decided for it.

Tensor cores: precision is a throughput knob

A tensor core is a unit that does a small fixed-size matrix multiply-accumulate as a single instruction, instead of one multiply-add at a time. It is much faster, and it is much faster the narrower the numbers get. Here is the same matrix multiply, four times, changing only the dtype:

Same operation: C = A @ B, 4096x4096x4096. Only the dtype changes.

precision              bytes/el        peak   ridge  FLOP/byte  bound by
------------------------------------------------------------------------
FP32 (no tensor core)         4     67 TF/s      20        683   compute
TF32 tensor core              4    495 TF/s     148        683   compute
FP16 tensor core              2    990 TF/s     296       1365   compute
FP8 tensor core               1   1979 TF/s     591       2731   compute ✓

Same maths, 137 GFLOPs either way.
Bytes moved: 201.3 MB at FP32, 50.3 MB at FP8 -- 4x less traffic.
Peak arithmetic: 67 TF/s at plain FP32 against 1979 TF/s at FP8
-- 30x more, from the published ceilings.

Look at what dropping precision does. It moves you on the roofline twice. The bytes halve, so your arithmetic intensity doubles and you slide right along the slanted roof. And the flat roof itself lifts, because the tensor cores do more per clock at narrower widths. Two independent wins from one change.

Quantisation gets sold almost entirely as a memory saving — the model fits on the card. On this hardware it is also an arithmetic saving of the same order, and that half rarely gets mentioned. The quantisation page is about what the precision drop costs you in accuracy and which numbers you are allowed to squash; this page only counts the throughput you get back.

The 30× is between two different things and I want to be honest about it. 67 TF/s is plain FP32 on the CUDA cores, no tensor core involved; 1979 TF/s is FP8 on the tensor cores. Most of that ratio is "you started using the tensor cores at all", not "you narrowed the dtype". The dtype-only comparison is the clean 2× per halving: 495 → 990 → 1979.

Occupancy: a small kernel wastes a large machine

The roofline says nothing about whether your work actually fills the chip. An H100 has 132 SMs. A thread block runs on exactly one SM. If your problem produces fewer blocks than there are SMs, the rest sit idle no matter which side of the ridge you are on.

Crudest possible model: equal-cost blocks dealt round-robin, kernel ends when the busiest SM does.

     batch     blocks    waves    utilisation       SMs idle
------------------------------------------------------------
         1          1        1           0.8%            131
         8          8        1           6.1%            124
        32         32        1          24.2%            100
        64         64        1          48.5%             68
       132        132        1         100.0%              0 ✓
       133        133        2          50.4%            131
       264        264        2         100.0%              0 ✓
       512        512        4          97.0%             16

At batch 1 you are using 0.76% of the machine and 131 of the 132 SMs have nothing to do. You did not buy a slow GPU. You bought a fast one and handed it one job.

The batch=133 row is the one that will actually bite you in production. One block past a full wave and utilisation halves, because the second wave is almost entirely empty but you wait for it anyway. Sizes that are not multiples of the SM count leave a quantised tail of idle time, and this is why tuning guides obsess over shapes that divide nicely.

This is the entire argument for batching. Batch-1 decode is memory-bound and leaves the machine idle — two separate failures with one fix. Batching raises intensity (the same weights serve more tokens) and fills the SMs. It costs you per-request latency, which is why continuous batching exists and why every serving stack has a knob labelled something like max_num_seqs. See speculative decoding for the other way out: more useful work per weight-load, without waiting for more requests.

Scaling out: NVLink is next door, InfiniBand is a lorry

One more level down the supply chain. Inside a server, GPUs talk over NVLink. Between servers, over InfiniBand. The published gap is about 18×, and that single ratio shapes every distributed training decision anyone makes.

A ring all-reduce — the gradient sync every data-parallel step — moves 2(N−1)/N × S bytes through each link, reduce-scatter then all-gather. That is bandwidth-optimal and is what the collectives library actually does. So:

Published link bandwidths (approximate, per GPU):
  NVLink (in a node)   : 900 GB/s
  InfiniBand NDR 400G  : 50 GB/s
  Ratio                : 18x

All-reduce of 7B BF16 gradients = 14.0 GB buffer.

configuration                      bytes/GPU      time
--------------------------------------------------------------
8 GPUs, 1 node, over NVLink          24.5 GB     27.2 ms ✓
  + 2 nodes, over InfiniBand         1.75 GB     62.2 ms  (56% on IB)
  + 4 nodes, over InfiniBand         2.62 GB     79.7 ms  (66% on IB)
  + 16 nodes, over InfiniBand        3.28 GB     92.8 ms  (71% on IB)

At two nodes the InfiniBand leg carries 7.1% of the bytes the NVLink leg does — and still takes the majority of the time. Inside a node, eight GPUs are effectively one machine. Across nodes they are posting parcels to each other.

That is why expert placement, all-to-all fan-out and overlapping communication with compute are genuine research problems rather than implementation details. Memory hierarchy என்பது ஒரு supply chain

Database பற்றி நீங்கள் ஏற்கனவே இப்படித்தான் யோசிக்கிறீர்கள். சில data process-ல், சில Redis-ல், சில அதே rack-ல் இருக்கும் disk-ல், சில வேறொரு region-ல். Chip கணக்கில் மெதுவாக இல்லை. அது பட்டினி கிடக்கிறது. ஒரு GPU-வுக்கு நீங்கள் எப்போதாவது செய்யப்போகும் கிட்டத்தட்ட ஒவ்வொரு optimisation-ம், குறைவான பயணங்களை எடுப்பதற்கான அல்லது அவற்றை hot loop-லிருந்து விலக்கி வைப்பதற்கான வழிதான். அவற்றில் எதுவுமே கணக்கைக் குறைப்பதைப் பற்றியது அல்ல.

அந்த ஒரு சூத்திரம்

Williams, Waterman மற்றும் Patterson இதை 2009-ல் வெளியிட்டார்கள் — Roofline: An Insightful Visual Performance Model for Multicore Architectures, Communications of the ACM-ல். இது CUDA-வின் எழுச்சிக்கும் முந்தையது, tensor cores-க்கும் முந்தையது, இந்தப் பக்கத்தில் உள்ள ஒவ்வொரு accelerator-க்கும் முந்தையது — இருந்தும் அத்தனையையும் விளக்குகிறது, ஏனெனில் அது இரண்டையே அனுமானிக்கிறது: கணக்குக்கு ஒரு உச்சவரம்பு, bandwidth-க்கு ஒரு உச்சவரம்பு.

attainable FLOP/s = min( peak FLOP/s ,  bandwidth × I )    where I = FLOPs ÷ bytes moved

அவ்வளவுதான். இரண்டு நேர்கோடுகளும் ஒரு min()-ம். பொருத்த வேண்டிய வளைவும் இல்லை, அளக்க வேண்டியதும் இல்லை. Code-ல்:

def roofline(intensity, peak_flops, bandwidth):
    memory_bound_ceiling = bandwidth * intensity
    attainable = min(peak_flops, memory_bound_ceiling)
    limiter = "compute" if memory_bound_ceiling >= peak_flops else "memory"
    return attainable, limiter

Ridge point, மற்றும் field ஏன் மேலும் memory-bound ஆகிறது

இரண்டு கூரைகளும் எங்கோ ஒரு இடத்தில் சந்திக்கின்றன. அந்தக் கடப்புதான் ridge point:

ridge = peak FLOP/s ÷ bandwidth   (FLOP per byte)

ஒரு chip-க்கு, ஒரு precision-க்கு ஒரே ஒரு எண். அதற்குக் கீழே memory-bound. மேலே compute-bound. நீங்கள் எழுதப்போகும் ஒவ்வொரு kernel-ன் தலைவிதியையும் அது தீர்மானிக்கிறது, அதை ஒரு datasheet-லிருந்து ஒரு துண்டுக் காகிதத்தில் கணக்கிட்டுவிடலாம்.

Bytes மலிவாகியதைவிட கிட்டத்தட்ட இரு மடங்கு வேகமாகக் கணக்கு மலிவாகியிருக்கிறது. அதாவது, compute-bound-ஆக இருக்க உங்களுக்குத் தேவைப்படும் intensity ஒவ்வொரு தலைமுறையிலும் ஏறுகிறது. V100-ன் arithmetic units-ஐ வசதியாகப் பயன்படுத்திய ஒரு operation, உங்கள் code-ல் ஒரு வரி கூட மாறாமல் H100-ல் memory-bound ஆகிவிடலாம். நீங்கள் upgrade செய்தீர்கள், உங்கள் kernel ஒப்பீட்டளவில் மோசமாகிவிட்டது.

இதைத்தான் ஐந்து வருடங்களுக்கு முன்பே யாராவது சொல்லியிருக்க வேண்டும் என்று நினைக்கிறேன். கடந்த ஐந்து ஆண்டுகளின் கிட்டத்தட்ட ஒவ்வொரு சுவாரஸ்யமான systems paper-ம், குறைவான கணக்குச் செய்வதைப் பற்றியல்லாமல் குறைவான bytes நகர்த்துவதைப் பற்றி இருப்பதற்குக் காரணம் இதுதான் — FlashAttention, GQA, quantised caches, paged attention, எல்லாமே. Memory-ஐப் பற்றிக் கவலைப்பட வேண்டும் என்று field முடிவெடுக்கவில்லை. Hardware அதற்காக முடிவெடுத்தது.

Tensor cores: precision என்பது ஒரு throughput knob

ஒரு tensor core என்பது ஒரு சிறிய நிலையான அளவு matrix multiply-accumulate-ஐ, ஒரு நேரத்தில் ஒரு multiply-add என்பதற்குப் பதிலாக, ஒரே instruction-ஆகச் செய்யும் unit. அது மிக வேகமானது, எண்கள் குறுகக் குறுக மேலும் வேகமானது. இதோ அதே matrix multiply, நான்கு முறை, dtype-ஐ மட்டும் மாற்றி:

Precision-ஐக் குறைப்பது என்ன செய்கிறது என்று பாருங்கள். அது உங்களை roofline-ல் இரு முறை நகர்த்துகிறது. Bytes பாதியாகின்றன, எனவே உங்கள் arithmetic intensity இரட்டிக்கிறது, சாய்ந்த கூரையில் வலப்பக்கம் நகர்கிறீர்கள். மேலும் தட்டையான கூரையே உயருகிறது, ஏனெனில் குறுகிய அகலங்களில் tensor cores ஒரு clock-க்கு அதிகம் செய்கின்றன. ஒரே மாற்றத்திலிருந்து இரண்டு தனித்தனி வெற்றிகள்.

Quantisation கிட்டத்தட்ட முழுவதுமாக ஒரு memory சேமிப்பாகவே விற்கப்படுகிறது — model card-ல் அடங்கிவிடும் என்று. இந்த hardware-ல் அது அதே அளவுக்கு ஒரு arithmetic சேமிப்பும்கூட, அந்தப் பாதி அரிதாகவே சொல்லப்படுகிறது. Quantisation பக்கம், precision குறைப்பு துல்லியத்தில் உங்களுக்கு என்ன விலை வைக்கிறது, எந்த எண்களை நசுக்க அனுமதி உண்டு என்பதைப் பற்றியது; இந்தப் பக்கம் திரும்பக் கிடைக்கும் throughput-ஐ மட்டுமே எண்ணுகிறது.

அந்த 30× என்பது இரு வேறுபட்ட விஷயங்களுக்கு இடையிலானது, அதை நேர்மையாகச் சொல்ல விரும்புகிறேன். 67 TF/s என்பது CUDA cores-ல் சாதாரண FP32, tensor core எதுவும் இல்லை; 1979 TF/s என்பது tensor cores-ல் FP8. அந்த விகிதத்தின் பெரும்பகுதி "நீங்கள் tensor cores-ஐப் பயன்படுத்தத் தொடங்கினீர்கள்" என்பதுதான், "dtype-ஐக் குறுக்கினீர்கள்" என்பதல்ல. Dtype மட்டும் ஒப்பிட்டால் ஒவ்வொரு பாதிப்பிற்கும் தூய 2×: 495 → 990 → 1979.

Occupancy: ஒரு சிறிய kernel ஒரு பெரிய இயந்திரத்தை வீணாக்குகிறது

உங்கள் வேலை உண்மையில் chip-ஐ நிரப்புகிறதா என்பதைப் பற்றி roofline ஒன்றும் சொல்வதில்லை. ஒரு H100-ல் 132 SMs உள்ளன. ஒரு thread block சரியாக ஒரு SM-ல்தான் ஓடும். SMs-ஐ விடக் குறைவான blocks-ஐ உங்கள் பிரச்சனை உருவாக்கினால், ridge-ன் எந்தப் பக்கத்தில் இருந்தாலும் மீதி வெறுமனே உட்கார்ந்திருக்கும்.

Production-ல் உண்மையில் உங்களைக் கடிக்கப் போவது batch=133 வரிசைதான். ஒரு முழு wave-ஐ ஒரே ஒரு block தாண்டியதும் utilisation பாதியாகிறது, ஏனெனில் இரண்டாவது wave கிட்டத்தட்ட முழுவதும் காலியாக இருந்தாலும் நீங்கள் அதற்குக் காத்திருக்கிறீர்கள். SM எண்ணிக்கையின் மடங்குகள் இல்லாத அளவுகள், வீணான நேரத்தின் ஒரு quantised வாலை விட்டுச்செல்கின்றன — அதனால்தான் tuning வழிகாட்டிகள் நேர்த்தியாக வகுபடும் shapes-ஐப் பற்றியே வெறிகொள்கின்றன.

Batching-க்கான முழு வாதமும் இதுதான். Batch-1 decode memory-bound மேலும் இயந்திரத்தையும் வெறுமையாக விடுகிறது — ஒரே தீர்வுக்கு இரண்டு தனித்தனி தோல்விகள். Batching intensity-ஐ உயர்த்துகிறது (அதே weights அதிக tokens-க்குச் சேவை செய்கின்றன) மற்றும் SMs-ஐ நிரப்புகிறது. அது ஒரு request-க்கான latency-ல் உங்களுக்கு விலை வைக்கிறது, அதனால்தான் continuous batching இருக்கிறது, அதனால்தான் ஒவ்வொரு serving stack-லும் max_num_seqs போன்ற ஒரு knob இருக்கிறது. வெளியேறும் மற்றொரு வழிக்கு speculative decoding பாருங்கள்: அதிக requests-க்குக் காத்திராமல், ஒவ்வொரு weight-load-க்கும் அதிக பயனுள்ள வேலை.

வெளியே விரிதல்: NVLink பக்கத்து வீடு, InfiniBand ஒரு லாரி

Supply chain-ல் இன்னும் ஒரு நிலை கீழே. ஒரு server-க்குள், GPUs NVLink வழியாகப் பேசுகின்றன. Servers-க்கு இடையே, InfiniBand வழியாக. வெளியிடப்பட்ட இடைவெளி தோராயமாக 18×, அந்த ஒரு விகிதமே யாரும் எடுக்கும் ஒவ்வொரு distributed training முடிவையும் வடிவமைக்கிறது.

ஒரு ring all-reduce — ஒவ்வொரு data-parallel step-லும் நடக்கும் gradient sync — ஒவ்வொரு link வழியாகவும் 2(N−1)/N × S bytes நகர்த்துகிறது, முதலில் reduce-scatter, பிறகு all-gather. அது bandwidth-optimal, collectives library உண்மையில் செய்வதும் அதுதான். எனவே:

அதனால்தான் expert placement, all-to-all fan-out மற்றும் communication-ஐ compute-உடன் ஒன்றின் மேல் ஒன்றாக நடத்துவது ஆகியவை implementation விவரங்கள் அல்ல, உண்மையான ஆராய்ச்சிப் பிரச்சனைகள். DeepSeek-V3 என்பது, NVLink எண் மேலும் பாதியாக வெட்டப்பட்ட hardware-ல், ஒரு குழு இதைப் பற்றிச் செய்தது. இந்தப் பக்கம் அவர்கள் எதிர்த்து வேலை செய்த கட்டுப்பாடு; அந்தப் பக்கம் அதற்கான பதில்.

मैंने FlashAttention वाला पेज लिखा और कहा कि SRAM छोटा है और HBM दूर है। मैंने KV cache वाला पेज लिखा और कहा कि decode memory-bound है। मैंने DeepSeek-V3 वाला पेज लिखा और कहा कि interconnect ही असली अड़चन है। तीन पेज, एक ही मशीन की तरफ़ तीन बार हाथ हिलाना — और उस मशीन को मैंने एक बार भी समझाया नहीं।

ध्यान दें: GPU, register, shared memory, L1, L2, HBM, NVLink, InfiniBand, streaming multiprocessor, warp, tensor core, roofline, arithmetic intensity, ridge point, occupancy, all-reduce, compute-bound, memory-bound — ये English technical words मैंने वैसे ही रखे हैं। क्योंकि code में और बाक़ी papers में आपको वही शब्द दिखेंगे। समझ हिंदी में, शब्दावली English में।

यही वह पेज है। यहाँ संक्षेप में बताने को कोई paper नहीं है — पर 2009 का एक paper है जो इस सब को एक साथ बाँधता है, और मैंने पूरी चीज़ को ऐसे गणित के रूप में बनाया है जिसे आप चला सकते हैं। दावा यह है: profile करने से पहले ही, एक अनुपात से आप बता सकते हैं कि आपका कौन-सा operation धीमा रहेगा।

इस पेज पर कुछ भी पढ़ने से पहले यह पढ़िए। यहाँ का हर hardware आँकड़ा एक published specification है — vendor datasheet का आँकड़ा, गोल किया हुआ, अनुमानित, और उस part के नाम के साथ जिससे वह आता है। कुछ भी मापा नहीं गया है। Peak आँकड़े वे छतें हैं जिन तक कोई नहीं पहुँचता; असली kernels उनसे काफ़ी नीचे रहते हैं। यह पेज बताता है कि आप किस दीवार के सामने खड़े हैं, यह नहीं कि आपका code कितनी तेज़ी से चलेगा।

वह एक सूत्र

Williams, Waterman और Patterson ने इसे 2009 में छापा — Roofline: An Insightful Visual Performance Model for Multicore Architectures, Communications of the ACM में। यह CUDA के उभार से पहले का है, tensor cores से पहले का, इस पेज के हर accelerator से पहले का, और फिर भी सबको समझाता है, क्योंकि यह सिर्फ़ दो बातें मानता है: गणित की एक छत, और bandwidth की एक छत।

attainable FLOP/s = min( peak FLOP/s ,  bandwidth × I )    where I = FLOPs ÷ bytes moved

बस इतना ही। दो सीधी रेखाएँ और एक min()। न कोई curve fit करनी है, न कुछ मापना है। Code में:

def roofline(intensity, peak_flops, bandwidth):
    memory_bound_ceiling = bandwidth * intensity
    attainable = min(peak_flops, memory_bound_ceiling)
    limiter = "compute" if memory_bound_ceiling >= peak_flops else "memory"
    return attainable, limiter

छह operations, और हर एक किस दीवार से टकराता है

यह रहा नतीजा। जो छह चीज़ें आप सचमुच चलाते हैं, उनके FLOPs और bytes मैंने गिने, एक को दूसरे से भाग दिया, और दो published H100 आँकड़ों से तुलना की। कुछ भी profile नहीं हुआ, कुछ भी GPU पर नहीं चला।

Byte की गिनती आदर्श स्थिति मानती है: हर input HBM से एक बार पढ़ा गया, हर output एक बार लिखा गया, बाक़ी सब chip पर ही रहा। असली kernels इससे ज़्यादा हिलाते हैं, इसलिए ये intensities आशावादी हैं — जिससे नीचे की बुरी ख़बर और बुरी होती है, बेहतर नहीं।

छह में से चार memory-bound हैं। बड़ा वर्गाकार matrix multiply ही यहाँ इकलौता operation है जो सचमुच उन arithmetic units का इस्तेमाल करता है जिनके आपने पैसे दिए, और यही वजह है कि benchmark में GPU तेज़ दिखता है। एक element-wise add chip की arithmetic peak के 0.1% तक पहुँचता है, क्योंकि वह हर byte को ठीक एक बार छूता है — इसीलिए kernel fusion किसी add के लिए micro-optimisation नहीं, बल्कि इकलौता उपलब्ध लीवर है। Sequence बढ़ने के साथ attention रेखा पार कर जाता है: seq=512 memory-bound, seq=8192 compute-bound, वही kernel, वही code। और आख़िरी पंक्ति:

एक single-token decode step 1.00 FLOP/byte पर बैठा है, ridge से लगभग 296× नीचे। हर weight HBM से खींचा जाता है और सिर्फ़ दो flops के काम आता है। KV cache वाला पेज cache की क़ीमत गिनकर, software की तरफ़ से यही तर्क देता है कि decode memory-bound है। यह वही निष्कर्ष है जो hardware की तरफ़ से आ रहा है, बिना किसी model को देखे। दो स्वतंत्र रास्ते, एक ही जवाब — आमतौर पर इसी से पता चलता है कि कोई दावा संरचनात्मक है, कोई संयोग नहीं।

Ridge point, और यह क्षेत्र लगातार और memory-bound क्यों होता जा रहा है

दोनों छतें कहीं न कहीं मिलती हैं। वह मिलन-बिंदु है ridge point:

ridge = peak FLOP/s ÷ bandwidth   (FLOP per byte)

हर chip के लिए, हर precision के लिए एक आँकड़ा। उससे नीचे memory-bound, ऊपर compute-bound। यह उस हर kernel की क़िस्मत तय करता है जो आप कभी लिखेंगे, और इसे आप datasheet देखकर काग़ज़ के टुकड़े पर निकाल सकते हैं।

गणित लगभग दोगुनी रफ़्तार से सस्ता हुआ, bytes के मुक़ाबले। इसका मतलब यह कि compute-bound बने रहने के लिए जितनी intensity चाहिए, वह हर पीढ़ी में बढ़ती जाती है। जो operation V100 की arithmetic units को आराम से इस्तेमाल करता था, वह आपके code की एक भी पंक्ति बदले बिना H100 पर memory-bound हो सकता है। आपने upgrade किया, और आपका kernel तुलनात्मक रूप से और ख़राब हो गया।

यही वह बात है जो काश कोई मुझे पाँच साल पहले बता देता। यही समझाता है कि पिछले पाँच सालों का लगभग हर दिलचस्प systems paper कम गणित करने के बजाय कम bytes हिलाने के बारे में क्यों है — FlashAttention, GQA, quantised caches, paged attention, सब। इस क्षेत्र ने memory की परवाह करने का फ़ैसला नहीं किया। Hardware ने उसके लिए फ़ैसला कर दिया।

Tensor cores: precision एक throughput knob है

एक tensor core वह unit है जो एक बार में एक multiply-add करने के बजाय एक छोटा, तयशुदा आकार का matrix multiply-accumulate एक ही instruction में कर देती है। वह कहीं तेज़ है, और संख्याएँ जितनी सँकरी होती जाती हैं उतनी और तेज़। यह रहा वही matrix multiply, चार बार, सिर्फ़ dtype बदलकर:

देखिए precision घटाने से क्या होता है। वह आपको roofline पर दो बार हिलाता है। Bytes आधे हो जाते हैं, तो आपकी arithmetic intensity दोगुनी होती है और आप ढलवाँ छत पर दाहिनी ओर सरक जाते हैं। और सपाट छत ख़ुद ऊपर उठ जाती है, क्योंकि सँकरी चौड़ाई पर tensor cores प्रति clock ज़्यादा करते हैं। एक ही बदलाव से दो अलग फ़ायदे।

Quantisation लगभग पूरी तरह memory की बचत के रूप में बेचा जाता है — model card पर आ जाएगा। इस hardware पर वह उतनी ही बड़ी arithmetic की बचत भी है, और वह आधा हिस्सा शायद ही कभी बताया जाता है। Quantisation वाला पेज इस बारे में है कि precision गिराने की क़ीमत accuracy में क्या पड़ती है और किन संख्याओं को दबाने की इजाज़त है; यह पेज सिर्फ़ वापस मिलने वाला throughput गिनता है।

वह 30× दो अलग-अलग चीज़ों के बीच है, और मैं इस बारे में ईमानदार रहना चाहता हूँ। 67 TF/s सादा FP32 है, CUDA cores पर, कोई tensor core शामिल नहीं; 1979 TF/s tensor cores पर FP8 है। उस अनुपात का ज़्यादातर हिस्सा "आपने tensor cores इस्तेमाल करना शुरू किया" है, "आपने dtype सँकरा किया" नहीं। सिर्फ़ dtype की तुलना साफ़ 2× प्रति आधा करने की है: 495 → 990 → 1979।

Occupancy: छोटा kernel बड़ी मशीन बर्बाद करता है

Roofline इस बारे में कुछ नहीं कहता कि आपका काम chip को सचमुच भरता है या नहीं। एक H100 में 132 SMs हैं। एक thread block ठीक एक SM पर चलता है। अगर आपकी समस्या SMs से कम blocks बनाती है, तो बाक़ी खाली बैठे रहते हैं, चाहे आप ridge के किसी भी तरफ़ हों।

Production में असल में जो पंक्ति आपको काटेगी वह batch=133 वाली है। पूरी wave से एक block आगे बढ़ते ही utilisation आधा हो जाता है, क्योंकि दूसरी wave लगभग पूरी ख़ाली है फिर भी आप उसका इंतज़ार करते हैं। जो आकार SM की गिनती के गुणज नहीं हैं, वे बेकार समय की एक quantised पूँछ छोड़ जाते हैं, और इसीलिए tuning गाइड ऐसे shapes पर अटके रहते हैं जो ठीक-ठीक भाग हो जाएँ।

Batching का पूरा तर्क यही है। Batch-1 decode memory-bound है और मशीन को ख़ाली छोड़ता है — दो अलग विफलताएँ, एक ही इलाज। Batching intensity बढ़ाता है (वही weights ज़्यादा tokens के काम आते हैं) और SMs भरता है। इसकी क़ीमत प्रति-request latency में चुकानी पड़ती है, इसीलिए continuous batching मौजूद है और इसीलिए हर serving stack में max_num_seqs जैसा कोई knob होता है। निकलने का दूसरा रास्ता देखने के लिए speculative decoding देखिए: ज़्यादा requests का इंतज़ार किए बिना, हर weight-load से ज़्यादा उपयोगी काम।

बाहर की ओर फैलाव: NVLink बग़ल में है, InfiniBand एक ट्रक है

Supply chain में एक और स्तर नीचे। एक server के भीतर GPUs NVLink पर बात करते हैं। Servers के बीच, InfiniBand पर। Published फ़ासला लगभग 18× का है, और वही एक अनुपात हर distributed training फ़ैसले को आकार देता है।

import numpy as np

# All figures are approximate, rounded, and taken from public vendor
# documentation (NVIDIA H100 Tensor Core GPU Architecture whitepaper and the
# H100 datasheet; NVLink and InfiniBand product pages). SXM form factor.
# They are PEAK numbers: the ceiling, not an achieved measurement.
H100 = {
    "sm_count":    132,              # streaming multiprocessors on the die
    "hbm_bytes":   80 * 1024**3,     # 80 GB of HBM3
    "hbm_bw":      3.35e12,          # ~3.35 TB/s memory bandwidth
    "l2_bytes":    50 * 1024**2,     # 50 MB L2, shared by all SMs
    "smem_bytes":  228 * 1024,       # up to 228 KB shared memory per SM
    "regs_bytes":  256 * 1024,       # 256 KB register file per SM
    # peak dense throughput, FLOP/s, no sparsity
    "fp32_novec":  67e12,            # plain FP32 CUDA cores, no tensor cores
    "tf32_tensor": 495e12,           # TF32 on tensor cores
    "fp16_tensor": 990e12,           # FP16/BF16 on tensor cores
    "fp8_tensor":  1979e12,          # FP8 on tensor cores
    "nvlink_bw":   900e9,            # ~900 GB/s NVLink per GPU, in a node
    "ib_bw":       50e9,             # 400 Gb/s InfiniBand NDR = ~50 GB/s
    "pcie_bw":     64e9,             # PCIe Gen5 x16, ~64 GB/s host<->device
}


# STAGE 1 -- arithmetic intensity. The whole page is this one ratio.
#     intensity = FLOPs performed / bytes moved from memory
# Units: FLOP per byte. It is a property of the OPERATION, not of the chip.
def arithmetic_intensity(flops, bytes_moved):
    return flops / bytes_moved


# STAGE 2 -- THE ROOFLINE. Williams, Waterman & Patterson, 2009.
#     attainable FLOP/s = min( peak FLOP/s,  bandwidth * intensity )
# Two straight lines. The slanted one is memory: if you can only move B bytes
# per second and you do I flops per byte, you can do at most B*I flops per
# second, no matter how good your arithmetic units are. The flat one is
# compute. The min of the two is the roof, and whichever term wins tells you
# what is limiting you.
def roofline(intensity, peak_flops, bandwidth):
    memory_bound_ceiling = bandwidth * intensity
    attainable = min(peak_flops, memory_bound_ceiling)
    limiter = "compute" if memory_bound_ceiling >= peak_flops else "memory"
    return attainable, limiter


# STAGE 3 -- the ridge point. Where the slanted roof meets the flat one.
#     ridge = peak FLOP/s / bandwidth      (units: FLOP per byte)
# Below this intensity you are memory-bound. Above it you are compute-bound.
def ridge_point(peak_flops, bandwidth):
    return peak_flops / bandwidth


# STAGE 5 -- occupancy, crudely. How much of the machine does the work fill?
# An SM is one of 132 independent processors on the die. A "warp" is a group
# of 32 threads that execute in lockstep; a kernel is chopped into thread
# blocks, and each block lands on exactly one SM. Fewer blocks than SMs and
# the leftover SMs idle. We model the crudest version: n_blocks of equal
# cost, dealt round-robin. The kernel finishes when the busiest SM finishes.
def utilisation(n_blocks, n_sms):
    if n_blocks == 0:
        return 0.0
    waves = int(np.ceil(n_blocks / n_sms))     # how many full passes needed
    capacity = waves * n_sms                    # block-slots we paid for
    return n_blocks / capacity                  # fraction actually used


# STAGE 6 -- ring all-reduce cost. The gradient sync every data-parallel step.
# It moves 2*(N-1)/N * S bytes through each link: reduce-scatter, then
# all-gather. Bandwidth-optimal, and what NCCL actually does.
def ring_allreduce_bytes(buffer_bytes, n_ranks):
    if n_ranks < 2:
        return 0.0
    return 2.0 * (n_ranks - 1) / n_ranks * buffer_bytes

On the maths anxiety

There isn't any here, and that is worth saying plainly. This page has one division. Arithmetic intensity is FLOPs over bytes. The ridge point is peak over bandwidth. The roofline is a min() of two numbers. If you can estimate how many multiply-adds a matrix multiply does and how many bytes a tensor occupies, you have everything.

What you do need is the counting discipline, and that is a habit rather than a skill. Before you profile: how many bytes does this operation have to move, at minimum? How many flops does it do? Divide. Compare to the ridge point of the card you are on. You now know which of the two possible problems you have, and you have not started a profiler.

The interview question here is almost never "derive the roofline". It is "why is your batch-1 latency not improving on the newer GPU?" or "you doubled the FLOPs and got nothing, what happened?" The answer both times is a ratio you can compute in your head. Say the number, say which roof you are under, and say what you would change. That is the whole answer.

Where this page stops: it says nothing about warp scheduling, memory coalescing, bank conflicts, instruction-level parallelism, or the actual register-pressure arithmetic that decides real occupancy. Those matter when you are writing kernels. Almost none of them matter when you are choosing a batch size, a dtype, or a parallelism strategy — which is what most of us are actually doing.

Where to go next

This page gave you one instrument: a ratio and a ceiling. That is deliberately narrow, and it is upstream of a lot. Three of these go deeper than I have; one is the original.

  • Roofline: An Insightful Visual Performance Model for Floating-Point Programs and Multicore Architectures Williams, Waterman & Patterson, 2008 tech report; published in Communications of the ACM, 2009. PDF.

    The original, and it has no arXiv id — it predates that habit. Read the model and the ridge-point argument; the multicore kernels they benchmark are of their era, but the reasoning transfers without a single change. Worth seeing how much of what we call "GPU intuition" was written down before the hardware existed.

  • Making Deep Learning Go Brrrr From First Principles Horace He. Prose, with PyTorch.

    The best essay on this subject, and it adds the third bottleneck I left out entirely: overhead. Compute, memory and the Python-side cost of launching kernels at all. If your model is small and your framework is eager, overhead is the wall you are hitting and no roofline will show it.

  • GPU Performance Background User's Guide NVIDIA. Documentation, with the vendor's own arithmetic.

    NVIDIA making exactly the argument on this page, in their own notation and with their own numbers. Useful precisely because it is the vendor: you can check my byte counts against theirs. The companion page on matrix multiplication explains the tile-quantisation effects behind my batch=133 row properly.

  • How to Optimize a CUDA Matmul Kernel Simon Boehm. A worklog, in CUDA C, with numbers at every step.

    Where this page stays at the napkin level, this one goes all the way down: coalescing, shared-memory tiling, register blocking, warp tiling, each step measured. It is the concrete answer to "so how do you actually get near that flat roof", and it will make the hierarchy table above feel much less abstract.

Order I'd take them in: Horace He first, because it is the same model told better and adds overhead; then the NVIDIA guide to check my arithmetic against the vendor's; then the Roofline paper, which will feel obvious by then and should; then Simon Boehm's worklog only if you are actually going to write a kernel.
