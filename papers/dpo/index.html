Direct Preference Optimization: the reward model was hiding in the policy

Rafailov, Sharma, Mitchell, Ermon, Manning & Finn, 2023

Two services, and it turns out one was a pure function of the other. So they deleted it and inlined the call.

Download dpo_from_scratch.py — everything below runs from it. NumPy for the algebra, a tiny CPU PyTorch loop for the training. Nine seconds.

I wrote the RLHF page and came away thinking the pipeline was irreducible. Three moving parts: a reward model fitted to votes with the Bradley-Terry loss, a policy that climbs it, and a KL penalty holding the policy near the frozen reference it started from. (One sentence each; if any of those three is new, read that page first, and the InstructGPT page for the three-stage recipe they sit inside.) Then this paper showed up and deleted the first one. Not approximated it. Deleted it, and proved it was never a separate thing.

The service that was a pure function

You have shipped this refactor. Two services, one calls the other: 

score   = reward_service.score(prompt, answer)   # a whole trained model
policy  = climb(score, start=ref, leash=beta)    # RL, sampling, the lot

And then someone reads the code properly and notices that reward_service has no state of its own. Everything it returns is derivable from what the caller already has. So you delete the service and inline the expression: 

def score(prompt, answer):                       # no model. Two log-probs.
    return beta * (log_prob(policy, answer) - log_prob(ref, answer))

That is DPO in one line, and the rest of this page is why the line is true. The paper's title says it outright: your language model is secretly a reward model. Not "can be used as one". Is one.

TermMeansProgrammer's analogy
Closed formThe exact maximiser of the RLHF objective, written down rather than searched forThe analytic solution you find after profiling the loop
The inversionRearranging that form so r is on the left and π is on the rightReading the getter and realising it's computed, not stored
Z(x)The normaliser. Depends on the prompt only, and is the one expensive termThe denominator you cancel before you ever evaluate it
Implicit rewardβ · log(π / πref), read off the trained policyThe inlined expression, still callable
βSame leash length as in RLHF, now living inside the loss instead of the rewardThe one knob you still tune by hand

The paper reports DPO matching or beating PPO-based RLHF on the tasks it tested — sentiment control, summarisation, single-turn dialogue — so the claim is parity plus simplicity, not dominance. The win is operational, and it is the kind an engineer feels immediately: one training loop instead of two, no sampling from the policy while training, no reward model to serve, no PPO hyperparameters (clip range, value head, GAE, rollout batch) to get wrong. What was a distributed system is now loss.backward() on a batch of pairs.

The one formula

π*(y|x) = πref(y|x) · exp( r(x,y) / β ) / Z(x)
⇒ r(x,y) = β · log( π*(y|x) / πref(y|x) ) + β · log Z(x)
lossDPO = −log σ( β·log(π(yw)/πref(yw)) − β·log(π(yl)/πref(yl)) )

Three lines, and only the first is new. Read them as pipeline stages:

StepShapeWhat it does
exp(r / β)(n answers,)Tilt the reference towards high reward. Big β = gentle tilt
· πref / Z(x)sums to 1Renormalise. This is the exact optimum of E[r] − β·KL — no RL needed to reach it
β·log(π*/πref)scalar per answerTake logs, move r to the left. The reward, recovered from the policy
+ β·log Z(x)scalar per promptThe leftover. Depends on x, not y — so it cancels in any comparison
−log σ(Δ)scalarBradley-Terry, unchanged from the RLHF page. Only what's inside σ changed

The last line is a binary classifier on pairs of responses. That's it. That is the whole training algorithm.

Step 1: the objective already had an answer

RLHF maximises Ey∼π[r(x,y)] − β·KL(π ‖ πref). PPO searches for the maximiser. But for a fixed prompt that objective is a concave problem over a probability distribution, and its maximiser can be written down: the reference, tilted by the exponential of the scaled reward, renormalised.

Don't take that on faith. The script climbs the same objective by brute force — 4000 steps of Adam on the logits, no formula anywhere — and compares where it lands with where the formula says it should. The toy world is the RLHF page's, unchanged: 4 prompts, 8 answers each, a hidden true reward, β = 0.5.

Don't take my word for it. Here's the actual output:

Four thousand gradient steps land where one line of algebra already was. So the RL in RLHF is a numerical search for a point you could have written down — if you had r. You don't have r. That's the next step.

Step 2: invert it, and the reward falls out of the policy

Take logs of that closed form and solve for r, and r comes out as a function of the policy. The awkward leftover is β·log Z(x): Z(x) sums over every possible answer to the prompt, which for a language model is every string that exists. Nobody can compute it. Nobody has to — it depends on the prompt, not the answer, and a preference model only ever compares two answers to the same prompt. Subtract, and it's gone.

  true r[3] - true r[7]      =  2.8866

Within a prompt the recovered reward ranks answers exactly as the hidden true reward does — correlation 1.000, residual spread 4·10−16, which is float noise. Across all 32 at once it drops to 0.849, and that gap is the point rather than a flaw: each prompt carries its own β·log Z offset, and comparing answers across prompts is the one thing preference data never does.

The reward model was a pure function of the policy all along. Anything you can express as a per-prompt-normalised score, you can express as a log-ratio between two policies. Fitting a separate network to do it was redundant work.

Step 3: substitute, and the second service disappears

Now put the inverted reward into the Bradley-Terry loss from the RLHF page. Both β·log Z terms cancel, r vanishes, and what's left mentions only the policy and the reference. Ten lines of PyTorch, no sampling, no rollouts, no second model to train and serve: 

margin = beta * (logp[p, w] - ref[p, w]) - beta * (logp[p, l] - ref[p, l])
loss   = -F.logsigmoid(margin).mean()

The script runs it on 2000 noisy votes and, on the same votes and the same β, runs the previous page's full RLHF pipeline — fit a reward model, REINFORCE against it with a KL penalty — so the two are comparable rather than merely described. true reward is the scoreboard neither ever sees.

The loss floors at 0.4541 rather than 0 because the votes are noisy — a close call is nearly a coin flip and no model should fit that. Don't read much into DPO's 2.898 beating RLHF's 2.535: four prompts, eight answers, and DPO also drifted further (KL 1.183 against 0.709). What the table earns is the last column. Comparable quality, one fewer model, no sampling loop.

DPO still needs the reference model in memory. Look at the loss: log πref appears twice. It's frozen and never gets gradients, so no optimiser state, but it is a second full set of weights resident during training. "No reward model" is not "one model".

The reward model was trained. It just isn't an object

The part that made it click for me: take the DPO-trained policy, compute β·log(π/πref) — the same expression, on a policy never told what a reward is — and check it against the hidden truth.

Nobody built a scorer, nobody scored an answer, and there is a scorer in there anyway, ordering answers roughly as people do. That's how you do best-of-n at eval time after a DPO run with no reward model deployed. The interview question is "where did the reward model go?" and the answer is "into the log-ratio".

β is the same leash, in a new place

On the RLHF page β was a coefficient on a KL term added to the reward. Here it multiplies the margin inside the loss. Same job — how far the policy is allowed to move from the reference — and the same trade. The script sweeps it twice: once on 2000 votes, once on 150.

  0.05       1.946         3.191       1.901            3.115

β = 5 barely leaves the reference either way — short leash, safe, useless. Small β means the policy trusts the votes completely and collapses onto their argmax; with 2000 votes that argmax is mostly right, so it looks free. It isn't free, it's a bet on your data. Same trade the KL coefficient made: how much do you trust what you're optimising against?

The limitation people actually argue about

The derivation assumes the pairs came from the reference policy. That assumption does real work and is easy to violate — your preference dataset was probably collected from some other model, months ago, by someone else. The script breaks it: same 2000 votes, but sampled from a long-winded policy the reference would essentially never produce. 

average reference probability of an answer in those pairs: 0.0249
same for the on-policy pairs:                              0.1805

  preference pairs drawn from    true reward    KL to ref
  the reference (as derived)          2.898        1.183
  a far-off policy                    1.927        1.241
  no training at all (reference)      1.117        0.000

Better than not training; considerably worse than on-policy pairs, at the same KL cost. DPO only gets gradient on the pairs you show it: shown long answers only, it raises the best of a bad bunch while the good short answers lose mass by normalisation alone. Nothing in the loss warns you. PPO samples from the current policy every step, so it is on-policy by construction and doesn't have this failure — it has different ones, as the RLHF page shows.

A trade, not a replacement. DPO is simpler, cheaper and more stable to train. On-policy methods still win in some settings, and iterated/online DPO variants exist precisely to close this gap. If someone says the question is settled, they're picking a side of a live argument.

Pure function-ஆக இருந்த அந்த service

இந்த refactor-ஐ நீங்கள் ship செய்திருக்கிறீர்கள். இரண்டு services, ஒன்று மற்றொன்றை அழைக்கிறது: 

score   = reward_service.score(prompt, answer)   # முழுமையாக train ஆன model
policy  = climb(score, start=ref, leash=beta)    # RL, sampling, எல்லாம்

பிறகு யாரோ ஒருவர் code-ஐ ஒழுங்காகப் படித்து, reward_service-க்கு தனக்கென எந்த state-ம் இல்லை என்பதைக் கவனிக்கிறார். அது திருப்பித் தரும் எல்லாமே, அழைப்பவரிடம் ஏற்கனவே இருப்பதிலிருந்தே பெறக்கூடியது. எனவே அந்த service-ஐ அழித்துவிட்டு, அந்த expression-ஐ inline செய்கிறீர்கள்: 

def score(prompt, answer):                       # model இல்லை. இரண்டு log-probs.
    return beta * (log_prob(policy, answer) - log_prob(ref, answer))

ஒரே வரியில் DPO அவ்வளவுதான்; இந்தப் பக்கத்தின் மீதி முழுவதும், அந்த வரி ஏன் உண்மை என்பதைப் பற்றியது. Paper-இன் தலைப்பே அதை நேரடியாகச் சொல்கிறது: உங்கள் language model ரகசியமாக ஒரு reward model. "ஒன்றாகப் பயன்படுத்தலாம்" அல்ல. அது ஒன்றாகவே இருக்கிறது.

படி 1: objective-க்கு ஏற்கனவே ஒரு விடை இருந்தது

RLHF, Ey∼π[r(x,y)] − β·KL(π ‖ πref)-ஐ அதிகப்படுத்துகிறது. PPO அந்த maximiser-ஐ தேடுகிறது. ஆனால் ஒரு நிலையான prompt-க்கு அந்த objective ஒரு probability distribution மீதான concave பிரச்சனை, அதன் maximiser-ஐ எழுதிவிட முடியும்: reference-ஐ எடுத்து, scaled reward-இன் exponential-ஆல் சாய்த்து, மீண்டும் normalise செய்யுங்கள்.

இதை நம்பிக்கையின் மேல் ஏற்காதீர்கள். Script அதே objective-ஐ brute force-ஆல் ஏறுகிறது — logits மீது 4000 steps Adam, எங்கும் சூத்திரம் இல்லை — பிறகு அது வந்து நிற்கும் இடத்தை, சூத்திரம் சொல்லும் இடத்துடன் ஒப்பிடுகிறது. Toy world RLHF பக்கத்தினுடையது, மாற்றமில்லாமல்: 4 prompts, தலா 8 answers, ஒரு மறைவான true reward, β = 0.5.

படி 2: அதைத் தலைகீழாக்குங்கள் — reward, policy-லிருந்து விழுகிறது

படி 3: பதிலிடுங்கள் — இரண்டாவது service மறைந்துவிடுகிறது

இப்போது தலைகீழாக்கப்பட்ட reward-ஐ RLHF பக்கத்தின் Bradley-Terry loss-க்குள் வையுங்கள். இரண்டு β·log Z பதங்களும் cancel ஆகின்றன, r மறைகிறது, மீதம் இருப்பது policy-ஐயும் reference-ஐயும் மட்டுமே குறிப்பிடுகிறது. பத்து வரி PyTorch; sampling இல்லை, rollouts இல்லை, train செய்து serve செய்ய இரண்டாவது model இல்லை: 

margin = beta * (logp[p, w] - ref[p, w]) - beta * (logp[p, l] - ref[p, l])
loss   = -F.logsigmoid(margin).mean()

मैंने RLHF पेज लिखा और यह सोचकर लौटा कि वह pipeline अब और नहीं घटाया जा सकता। तीन हिस्से: votes पर Bradley-Terry loss से fit किया गया एक reward model, उस पर चढ़ने वाली एक policy, और एक KL penalty जो policy को उस frozen reference के पास बाँधे रखती है जहाँ से वह चली थी। (हर एक पर एक वाक्य; इन तीनों में से कोई नया लगे तो पहले वह पेज पढ़ें, और जिस तीन-चरणीय recipe के भीतर ये बैठते हैं उसके लिए InstructGPT पेज।) फिर यह paper आया और पहले हिस्से को मिटा दिया। उसका approximation नहीं किया। मिटा दिया, और साबित किया कि वह कभी अलग चीज़ थी ही नहीं।

ध्यान दें: English technical words (reward model, policy, reference, KL, Bradley-Terry, implicit reward, log-ratio, closed form, off-distribution, preference pair…) मैंने वैसे ही रखे हैं। क्योंकि code में और बाक़ी papers में आपको वही शब्द दिखेंगे। समझ हिंदी में, शब्दावली English में।

वह service जो असल में एक pure function थी

यह refactor आप कर चुके हैं। दो services, एक दूसरे को call करती है: 

score   = reward_service.score(prompt, answer)   # पूरा trained model
policy  = climb(score, start=ref, leash=beta)    # RL, sampling, सब कुछ

फिर कोई code को ठीक से पढ़ता है और देखता है कि reward_service का अपना कोई state है ही नहीं। वह जो कुछ लौटाती है, वह सब caller के पास पहले से मौजूद चीज़ों से निकाला जा सकता है। तो आप service मिटा देते हैं और expression को inline कर देते हैं: 

def score(prompt, answer):                       # model नहीं। दो log-probs।
    return beta * (log_prob(policy, answer) - log_prob(ref, answer))

एक लाइन में DPO यही है, और इस पेज का बाक़ी हिस्सा यही बताता है कि वह लाइन सच क्यों है। Paper का शीर्षक साफ़ कहता है: आपका language model गुप्त रूप से एक reward model है। "उसे reward model की तरह इस्तेमाल किया जा सकता है" नहीं। वह है।

चरण 1: objective के पास जवाब पहले से था

RLHF, Ey∼π[r(x,y)] − β·KL(π ‖ πref) को अधिकतम करता है। PPO उस maximiser को खोजता है। पर किसी एक prompt के लिए वह objective एक probability distribution पर concave समस्या है, और उसका maximiser लिखा जा सकता है: reference को scaled reward के exponential से झुकाओ, फिर normalise कर दो।

इसे भरोसे पर मत लीजिए। Script उसी objective पर brute force से चढ़ता है — logits पर 4000 steps Adam, कहीं कोई formula नहीं — और फिर देखता है कि वह कहाँ पहुँचा और formula कहाँ कहता है। Toy world वही है जो RLHF पेज पर था: 4 prompts, हर एक पर 8 answers, एक छिपा true reward, β = 0.5.

चरण 2: उसे उलटिए, और reward policy से गिर पड़ता है

उस closed form का log लीजिए और r के लिए हल कीजिए; r policy के एक function के रूप में निकल आता है। अटपटा बचा हुआ पद है β·log Z(x): Z(x) उस prompt के हर संभव answer पर जोड़ लगाता है — language model के लिए यानी हर मौजूद string। इसे कोई नहीं निकाल सकता। निकालने की ज़रूरत भी नहीं — यह prompt पर निर्भर है, answer पर नहीं, और preference model हमेशा एक ही prompt के दो answers की तुलना करता है। घटाइए, और वह ग़ायब।

Reward model शुरू से ही policy का एक pure function था। जिसे भी आप prompt-वार normalise किया गया score कह सकते हैं, उसे दो policies के बीच log-ratio के रूप में भी लिखा जा सकता है। इसके लिए अलग network fit करना दोहरा काम था।

चरण 3: प्रतिस्थापित कीजिए, और दूसरी service ग़ायब हो जाती है

अब उलटे हुए reward को RLHF पेज वाले Bradley-Terry loss में रख दीजिए। दोनों β·log Z पद cancel हो जाते हैं, r ग़ायब हो जाता है, और जो बचता है उसमें सिर्फ़ policy और reference का ज़िक्र है। दस लाइन PyTorch, कोई sampling नहीं, कोई rollouts नहीं, train और serve करने को दूसरा model नहीं: 

margin = beta * (logp[p, w] - ref[p, w]) - beta * (logp[p, l] - ref[p, l])
loss   = -F.logsigmoid(margin).mean()

β वही leash है, नई जगह पर

RLHF पेज पर β reward में जोड़े गए KL पद का coefficient था। यहाँ वह loss के भीतर margin को गुणा करता है। काम वही — policy को reference से कितनी दूर जाने दिया जाए — और सौदा भी वही। Script इसे दो बार sweep करता है: एक बार 2000 votes पर, एक बार 150 पर।

यह एक सौदा है, replacement नहीं। DPO सरल है, सस्ता है और train करने में ज़्यादा स्थिर। कुछ हालात में on-policy तरीक़े अब भी जीतते हैं, और इसी फ़र्क़ को पाटने के लिए iterated/online DPO variants मौजूद हैं। अगर कोई कहे कि सवाल तय हो चुका है, तो वह एक चालू बहस में पक्ष चुन रहा है।

The code

NumPy for the mechanism: the world, the closed form, the inversion, the KL. A torch loop for the training, because that is what DPO is — an objective, and hand-rolling its backprop would bury the idea. CPU, nine seconds. No function over 25 lines. Below, the four functions that are the paper; the toy world, the votes and the RLHF baseline are in the script.

Download the full script — 514 lines including seven runnable demos. Then: 

python3 dpo_from_scratch.py
def optimal_policy(r, ref_logp, beta):
    """The closed form above, in log space so nothing overflows. (4, 8)."""
    return log_softmax(ref_logp + r / beta)


def implicit_reward(logp, ref_logp, beta):
    """beta * log-ratio. The reward, recovered from the policy, up to a
    per-prompt constant. This is the whole 'secretly a reward model' claim."""
    return beta * (logp - ref_logp)


def dpo_loss(logp, ref_logp, p, w, l, beta, drop_reference=False,
             no_pair=False):
    """logp: torch (4, 8) log-probs of the policy. p/w/l: prompt, winner,
    loser index tensors. The two flags are the deliberate breaks."""
    ref = torch.zeros_like(logp) if drop_reference else ref_logp
    margin_w = beta * (logp[p, w] - ref[p, w])
    if no_pair:
        return -F.logsigmoid(margin_w).mean()      # the break: no contrast
    margin_l = beta * (logp[p, l] - ref[p, l])
    return -F.logsigmoid(margin_w - margin_l).mean()


def train_dpo(comparisons, ref_logp, beta=BETA, steps=600, lr=0.05,
              log_every=0, drop_reference=False, no_pair=False, swap=False):
    """Fit the policy directly on the votes. Returns its log-probs, (4, 8).
    The policy is a table of logits here; in the paper it is a language
    model and logp is the sum of token log-probs of the whole answer."""
    torch.manual_seed(0)
    ref = torch.tensor(ref_logp, dtype=torch.float32)
    logits = ref.clone().requires_grad_(True)       # start AT the reference
    opt = torch.optim.Adam([logits], lr=lr)
    p, w, l = (torch.tensor([c[i] for c in comparisons]) for i in range(3))
    if swap:
        w, l = l, w                                 # the break: winner/loser
    for step in range(1, steps + 1):
        loss = dpo_loss(F.log_softmax(logits, dim=-1), ref, p, w, l, beta,
                        drop_reference=drop_reference, no_pair=no_pair)
        opt.zero_grad()
        loss.backward()
        opt.step()
    with torch.no_grad():
        return F.log_softmax(logits, dim=-1).numpy()

On the maths anxiety

The formula sheet: a log, an exponential, a sigmoid, a weighted average. Log and exp are inverses, which is the entire trick — the closed form has an exp in it, you take logs, and a multiplication becomes a subtraction you can cancel. Nothing else happens.

Worth sitting with: why Z(x) may disappear. Not because it's small — it's enormous and uncomputable — but because it's constant in the thing you're differencing. Same move as cancelling a common denominator, or the - max in a numerically safe softmax. Cancellation, not approximation.

What you don't need: the uniqueness proof for the KL-constrained optimum, the Plackett-Luce generalisation to rankings, any of the convex analysis. Demo 1 replaces the proof with a number you can rerun, which for engineering purposes is worth more.

Where to go next

This page gave you one thing: the inversion, and the cancellation that makes it usable. It skipped the language-model reality — token-level log-probs, memory, many epochs — and the argument over whether DPO is the right default.

  • Direct Preference Optimization: Your Language Model is Secretly a Reward Model Rafailov, Sharma, Mitchell, Ermon, Manning, Finn, 2023. The original.

    Read the derivation with the script open, then Appendix A.1 for the closed form. Their experiments are what I have no equivalent of: real models, real judges, and the stability comparison against PPO.

  • Fine-tune Llama 2 with DPO Hugging Face. Working code on a real model.

    What my four-by-eight table of logits looks like as a 7B model: how the preference dataset is shaped, where the frozen reference lives, what beta is in practice. The bridge to something you'd run.

  • Is DPO Superior to PPO for LLM Alignment? Xu, Fu, Gao et al., 2024. The other side.

    The argument I flagged, argued properly: it pins DPO's weakness to the distribution shift demo 6 prints, and shows PPO ahead on harder benchmarks. Read it so "which would you use?" gets a condition, not a preference.

Order I'd take them in: the paper's derivation → the Hugging Face fine-tuning post → the DPO-versus-PPO study. Theory, practice, then doubt. And read the RLHF page first if you haven't: DPO is a refactor, and a refactor only makes sense once you've seen the code it replaced.
