Quantisation: what fits on your GPU

Dettmers et al., 2022 — with Frantar et al. 2022, Lin et al. 2023, Dettmers et al. 2023

Four papers, one question: which numbers are you allowed to be sloppy about?

Download quantization_from_scratch.py — everything below runs from it. NumPy only.

I'm an AI Engineer. I've passed load_in_4bit=True to from_pretrained, watched a 13B model appear on a card that should not have held it, and had no idea what I'd just agreed to. What is NF4? Why is group_size=128 in every config file? Why does GPTQ need a calibration dataset when bitsandbytes doesn't? Nobody told me the whole field is one operation and one argument about it.

A float is a storage budget, and most of it is wasted

You already know this idea. It's JPEG. Almost none of a photograph's exactness survives being saved at quality 80, and it looks the same. You can throw away a lot before anyone notices — but throw away the wrong thing and it's obvious instantly: ringing round the text, banding across the sky.

A weight matrix is the same bargain. fp16 spends 16 bits per number on a range up to 65504, and your weights all sit between about −3 and 3. So compress them: 

scale = abs(x).max() / 127        # map your range onto 255 slots
q     = round(x / scale)          # <- the lossy step. Information dies here
store(q)                          # one byte per weight instead of two
x2    = q * scale                 # multiply back. Close to x. Not x.

That's it. That is every paper on this page. Everything else — LLM.int8(), GPTQ, AWQ, NF4 — is an argument about which numbers share a scale, where the levels sit, and which numbers you refuse to compress at all.

The one formula

q = clamp(round(x / s), −2b−1+1, 2b−1−1)   x̂ = q · s   where s = max|x| / (2b−1−1)

Read it as pipeline stages:

StepShapeWhat it does
max|x|scalar (or per column, or per group)The only choice you make. Everything on this page is an argument about this line
x / s(n, d)Rescale into integer units. Now the numbers mean "how many slots"
round(n, d)The lossy step. Worst case half a slot of error, per weight
clamp(n, d)Anything past the end saturates. Cheap in int8, brutal if you clipped an outlier
q · s(n, d)Back to float, in the kernel, just before the matmul. This is weight-only quantisation

Symmetric assumes the data straddles zero. If it doesn't — a ReLU output, say — you waste the negative half of the grid, and an integer zero_point shifts the grid to fix it:

Where the scale lives is the whole game

One scale for a whole tensor means the loudest channel decides the resolution for every quiet one. This is the single most useful thing on this page, and it is why naive quantisation fails.

Here's a 64×8 matrix where one column has been made 50× louder and one 50× quieter, quantised to int8 both ways: 

channel absmax: [135.558  31.      2.466   1.988   2.553   2.176   2.138   0.057]

per-tensor  one scale  = 1.067387
per-channel scales     = [1.067 0.244 0.019 0.016 0.02  0.017 0.017 0.   ]

per-channel error, column by column:
  col 0: per-tensor  0.007493   per-channel 0.007493
  col 2: per-tensor  0.290450   per-channel 0.005758
  col 7: per-tensor  1.000000   per-channel 0.007100

distinct int8 codes in the quietest column (col 7):
  per-tensor : 1 of 255
  per-channel: 53 of 255

Column 7 has relative error 1.0. Every value in it rounded to zero. The column is gone. It cost one float per column to save it — eight floats for the whole matrix.

Group-wise scales are the same idea at finer grain: chop each column into groups of g weights and give each group a scale. Here is 4096 weights at int4, eight of them 30× larger than the rest: 

   group   rel error   scales   bits/weight
   whole    0.662549        1         4.004
     128    0.257297       32         4.125
      64    0.187432       64         4.250
      32    0.146733      128         4.500

same sweep with NO outliers, so you can see what the outliers cost:
   whole    0.152834
     128    0.116649
Now you know why every config file says group_size: 128. It buys most of the accuracy back for 0.125 extra bits per weight — one fp16 scale per 128 weights. Going to 32 costs four times the overhead for a fraction more. QLoRA's double quantisation then quantises those scales too, which the paper reports saves about 0.37 bits per parameter.

LLM.int8(): the outliers are systematic

Dettmers et al. found something that is not obvious: past roughly 6.7B parameters, transformers develop outlier features — a small number of hidden dimensions whose activations are far larger than everything else, and they appear in the same dimensions across layers and across inputs. They are not noise. Zero them out and the model's performance collapses.

They're also fatal for per-tensor int8, because the scale is set by the max. One huge value spends the whole grid on empty space. Here are 32 tokens × 16 dimensions, with outliers injected into dims 3 and 11: 

clean activations, absmax 3.056
  per-tensor int8 relative error: 0.006828

with outliers in dims 3 and 11, absmax 105.047
  per-tensor scale went 0.024066 -> 0.827141  (34.4x coarser)
  per-tensor int8 relative error: 0.017330
  error on the NON-outlier dims only: 0.243144
  distinct int8 codes used by dim 0: 5 of 255

mixed precision: keep columns [3, 11] in 16-bit,
  that is 2/16 = 12.5% of the dimensions
  relative error, whole tensor : 0.000466
  relative error, non-outlier  : 0.006992

Whole-tensor error looks like 1.7%, which is survivable. That average is a lie: it's dominated by the two outliers, which are huge and quantise fine. The dimensions that matter to everything else are at 24% error, and dimension 0 is using five of its 255 codes. The damage is hidden by the metric.

LLM.int8()'s fix is not clever, and that's the point. Pull the outlier columns out, do those in fp16, do the other 99.9% in int8, add the two results. One mixed-precision matmul. The paper's claim is that this holds full 16-bit quality while halving the weight memory — the first int8 method that survived 175B scale.

This is where weight quantisation and activation quantisation part company. Weights are well-behaved: bounded, roughly normal, known ahead of time. Activations depend on the input and are where the outliers live. That is why GPTQ, AWQ and NF4 are all weight-only — they shrink the checkpoint and dequantise before the matmul. LLM.int8() is doing the harder thing.

GPTQ: quantise in an order, and apologise as you go

Everything above quantises every weight independently, in one shot, and accepts the error. GPTQ asks a better question: when I round this weight down, can I nudge the weights I haven't done yet to compensate?

It goes column by column. Quantise a column, measure the error, then update the columns not yet done so they absorb it — using approximate second-order information (a Hessian, estimated from a small calibration set) to decide how. Each rounding decision leaves a debt, and the not-yet-frozen weights pay it.

Three things follow, and they are the interview material. It is one-shot post-training: no retraining, no gradients, no labels. It needs calibration data, which bitsandbytes' int8 and NF4 don't — the usual reason a GPTQ build is awkward in a pipeline. And it is weight-only, 3 to 4 bit: the paper's headline is 3 and 4-bit quantisation up to 175B with negligible accuracy loss, which is why GPTQ checkpoints are everywhere on the Hub. The Hessian update is not in my script — it needs a calibration set and a Cholesky, and it would bury the idea.

AWQ: protect the weights the activations care about

AWQ's finding: a small fraction of weights are salient, and protecting roughly 1% of them recovers most of the quality. The non-obvious part is how you find them. Not by weight magnitude — by activation magnitude. The weights that matter are the ones multiplying the input channels carrying large activations. That is the LLM.int8() finding again, seen from the weight side.

And AWQ does not keep them in fp16, because mixed precision is ugly in a kernel: ragged layout, slow paths. Instead it scales the salient channels up before quantising and scales the matching activations down, so the maths is unchanged and the important weights land on a finer part of the grid. Everything stays uniform int4, which is why AWQ kernels are fast.

The distinction to keep straight: LLM.int8() is mixed-precision and finds outliers at runtime, per batch, in the activations. AWQ is uniform int4 and uses activation statistics once, at quantisation time, to decide how to scale the weights. GPTQ uses a calibration set to correct rounding error. Three answers to "which numbers do I protect", and no backprop in any of them.

QLoRA and NF4: put the levels where the data is

Every scheme so far spaces its levels evenly, and QLoRA's argument is that this is obviously wrong. Pretrained weights are roughly normally distributed, piled up around zero, so evenly spaced levels spend most of their resolution in the tails where almost nothing lives. 4-bit NormalFloat puts the 16 levels at equal-probability quantiles of a normal distribution instead. Same 4 bits, levels crowded where the weights are — here are both sets, and the error on 100,000 draws from N(0,1): 

linear int4 levels (evenly spaced):
  [-1.    -0.867 -0.733 -0.6   -0.467 -0.333 -0.2   -0.067  0.067 ...]
normal-quantile levels (NF4-style):
  [-1.    -0.708 -0.542 -0.417 -0.311 -0.216 -0.127 -0.042  0.042 ...]

weights ~ N(0,1), n=100000, absmax 4.369
  linear int4 relative error: 0.167915
  NF4-style   relative error: 0.118978
  improvement: 29.1%

how much data each of the 16 levels actually gets:
  linear: emptiest level      1  busiest  22082  levels under 1% of the data: 8/16
  NF4   : emptiest level     10  busiest  14431  levels under 1% of the data: 4/16

Half the linear levels are holding under 1% of the data each. One of them caught a single weight out of a hundred thousand. That is half your bit budget spent on the tails.

Honest caveat: the real NF4 table in the paper is built asymmetrically, so that exact zero is one of the levels and zero-padding stays exact. Mine is the same construction idea in five lines, and the error numbers above are from my version, not theirs.

Why QLoRA needs LoRA

Here is the bit that made QLoRA click for me. Once weights are on a 4-bit grid you cannot fine-tune them. A gradient step smaller than half the grid step rounds straight back to where it started: 

4-bit grid step (the scale) = 0.189194

after one SGD step at lr=0.001:
  moved by         : [-0.001 -0.002 -0.     0.001  0.001 -0.002 -0.     0.002]
  after re-quantise: [0. 0. 0. 0. 0. 0. 0. 0.]
  weights that actually changed: 0 of 8

same gradient at lr=0.5: 7 of 8 weights changed
  step sizes taken : [-0.378  0.    -0.189  0.568  0.189 -0.757 -0.189  0.946]

frozen 4-bit base + fp16 LoRA adapter, same lr=0.001:
  adapter output after : max |delta| = 9.424e-07
  weights that actually changed: 8 of 8, by steps smaller than
  the 4-bit grid step of 0.189194

The update silently disappears. Turn the learning rate up until something moves and every step is a whole grid step — that isn't fine-tuning, it's vandalism. So QLoRA freezes the 4-bit base and trains a small higher-precision LoRA adapter on top of it. Gradients flow through the frozen quantised weights into the adapter; the base is never updated. I won't re-explain LoRA — that page does.

The paper's three contributions: NF4; double quantisation, which quantises the block scales themselves; and paged optimisers, which use unified memory to survive the gradient-checkpointing spikes that would otherwise OOM you. The headline result is finetuning a 65B model on one 48GB GPU without degrading 16-bit finetuning performance.

Symmetric என்பது data பூஜ்ஜியத்தின் இரு பக்கமும் பரவியிருக்கிறது என்று கருதுகிறது. இல்லையென்றால் — உதாரணமாக ஒரு ReLU output — grid-ன் எதிர்மறைப் பாதி வீணாகிறது; ஒரு integer zero_point grid-ஐ நகர்த்தி அதைச் சரி செய்கிறது: 

now shift the data to [0.17, 2.60] -- nothing is negative:
  symmetric  relative error: 0.003939  (half the grid unused)
  asymmetric relative error: 0.001680  zero_point=-18
  symmetric  int8 codes: 8 .. 127 (of -127..127, 47% of the grid used)
  asymmetric int8 codes: 0 .. 255 (of 0..255, 100% used)

Scale எங்கே இருக்கிறது என்பதுதான் முழு விளையாட்டு

ஒரு tensor முழுமைக்கும் ஒரே scale என்றால், மிகச் சத்தமான channel எல்லா அமைதியான channel-க்கும் resolution-ஐத் தீர்மானிக்கிறது. இந்தப் பக்கத்தில் இதுதான் மிகவும் பயனுள்ள விஷயம், மேலும் naive quantisation தோற்பதற்கான காரணமும் இதுதான்.

இதோ ஒரு 64×8 matrix — ஒரு column 50× சத்தமாகவும், இன்னொன்று 50× அமைதியாகவும் ஆக்கப்பட்டிருக்கிறது, இரு வழிகளிலும் int8-க்கு quantise செய்யப்பட்டது:

Group-wise scales என்பது இதே கருத்து இன்னும் நுணுக்கமான அளவில்: ஒவ்வொரு column-ஐயும் g weights கொண்ட groups-ஆக வெட்டி, ஒவ்வொரு group-க்கும் ஒரு scale கொடுங்கள். இதோ int4-ல் 4096 weights, அவற்றில் எட்டு மற்றவற்றை விட 30× பெரியவை:

LLM.int8(): outliers ஒழுங்கானவை

Dettmers et al. வெளிப்படையாகத் தெரியாத ஒன்றைக் கண்டுபிடித்தார்கள்: தோராயமாக 6.7B parameters-ஐத் தாண்டியதும் transformers-ல் outlier features உருவாகின்றன — சில hidden dimensions-ன் activations மற்ற எல்லாவற்றையும் விட மிகப் பெரியவை; அவை layers முழுவதும், inputs முழுவதும் ஒரே dimensions-ல் தோன்றுகின்றன. அவை noise அல்ல. அவற்றைப் பூஜ்ஜியமாக்கினால் model-ன் செயல்திறன் சரிந்துவிடும்.

Per-tensor int8-க்கு அவை கொலைகாரர்களும் கூட, ஏனெனில் scale-ஐ max தீர்மானிக்கிறது. ஒரு பெரிய மதிப்பு முழு grid-ஐயும் காலி இடத்துக்குச் செலவழிக்கிறது. இதோ 32 tokens × 16 dimensions, dims 3 மற்றும் 11-ல் outliers செலுத்தப்பட்டவை: 

clean activations, absmax 3.056
  per-tensor int8 relative error: 0.006828

with outliers in dims 3 and 11, absmax 105.047
  per-tensor scale went 0.024066 -> 0.827141  (34.4x coarser)
  per-tensor int8 relative error: 0.017330
  error on the NON-outlier dims only: 0.243144
  distinct int8 codes used by dim 0: 5 of 255

mixed precision: keep columns [3, 11] in 16-bit,
  that is 2/16 = 12.5% of the dimensions
  relative error, whole tensor : 0.000466
  relative error, non-outlier  : 0.006992

முழு tensor-ன் பிழை 1.7% போலத் தெரிகிறது — அது தாங்கக்கூடியது. ஆனால் அந்தச் சராசரி ஒரு பொய்: அது இரண்டு outliers-ஆல் ஆளப்படுகிறது, அவை பெரியவை, நன்றாகவே quantise ஆகின்றன. மற்ற எல்லாவற்றுக்கும் முக்கியமான dimensions 24% பிழையில் இருக்கின்றன, dimension 0 அதன் 255 codes-ல் ஐந்தையே பயன்படுத்துகிறது. சேதத்தை metric மறைக்கிறது.

LLM.int8()-ன் தீர்வு புத்திசாலித்தனமானது அல்ல — அதுதான் முக்கியம். Outlier columns-ஐ வெளியே எடுங்கள், அவற்றை fp16-ல் செய்யுங்கள், மீதி 99.9%-ஐ int8-ல் செய்யுங்கள், இரு முடிவுகளையும் கூட்டுங்கள். ஒரு mixed-precision matmul. Weight memory-ஐ பாதியாக்கியும் முழு 16-bit தரத்தைத் தக்கவைக்கிறது என்பது paper-ன் கூற்று — 175B அளவில் தாக்குப்பிடித்த முதல் int8 முறை.

இங்கேதான் weight quantisation-ம் activation quantisation-ம் பிரிகின்றன. Weights நல்ல நடத்தை உள்ளவை: வரம்புக்குட்பட்டவை, தோராயமாக normal, முன்கூட்டியே தெரிந்தவை. Activations input-ஐச் சார்ந்தவை, outliers வாழ்வதும் அங்கேதான். அதனால்தான் GPTQ, AWQ, NF4 எல்லாமே weight-only — அவை checkpoint-ஐச் சுருக்கி, matmul-க்கு முன் dequantise செய்கின்றன. LLM.int8() கடினமான வேலையைச் செய்கிறது.

GPTQ: ஒரு வரிசையில் quantise செய், போகும்போதே மன்னிப்புக் கேள்

மேலே உள்ள எல்லாமே ஒவ்வொரு weight-ஐயும் தனித்தனியாக, ஒரே முறையில் quantise செய்து, பிழையை ஏற்றுக்கொள்கின்றன. GPTQ சிறந்த ஒரு கேள்வி கேட்கிறது: இந்த weight-ஐ கீழ்நோக்கி round செய்யும்போது, இன்னும் செய்யாத weights-ஐச் சிறிது நகர்த்தி அதை ஈடுகட்ட முடியுமா?

அது column by column-ஆகச் செல்கிறது. ஒரு column-ஐ quantise செய், பிழையை அளவிடு, பிறகு இன்னும் செய்யாத columns-ஐ அந்தப் பிழையை உள்வாங்கும்படி update செய் — எப்படி என்பதை தோராயமான second-order தகவல் வைத்து (ஒரு Hessian, ஒரு சிறிய calibration set-லிருந்து மதிப்பிடப்பட்டது) தீர்மானிக்கிறது. ஒவ்வொரு rounding முடிவும் ஒரு கடனை விட்டுச் செல்கிறது; இன்னும் உறையவைக்கப்படாத weights அதைக் கட்டுகின்றன.

இதிலிருந்து மூன்று விஷயங்கள் வருகின்றன, அவைதான் interview material. இது one-shot post-training: retraining இல்லை, gradients இல்லை, labels இல்லை. இதற்கு calibration data தேவை — bitsandbytes-ன் int8-க்கும் NF4-க்கும் அது தேவையில்லை; pipeline-ல் ஒரு GPTQ build சிக்கலாக இருப்பதற்கான வழக்கமான காரணம் இதுதான். மேலும் இது weight-only, 3 முதல் 4 bit: 175B வரை 3 மற்றும் 4-bit quantisation, கண்டுகொள்ளத்தக்க accuracy இழப்பின்றி என்பதுதான் paper-ன் தலைப்புச் செய்தி; அதனால்தான் Hub முழுவதும் GPTQ checkpoints. Hessian update என் script-ல் இல்லை — அதற்கு ஒரு calibration set-ம் ஒரு Cholesky-ம் தேவை, அது கருத்தையே புதைத்துவிடும்.

AWQ: activations கவலைப்படும் weights-ஐக் காப்பாற்று

AWQ-ன் கண்டுபிடிப்பு: weights-ல் ஒரு சிறு பகுதி salient, அவற்றில் தோராயமாக 1%-ஐக் காப்பாற்றினால் தரத்தில் பெரும்பகுதி திரும்பக் கிடைக்கிறது. வெளிப்படையாகத் தெரியாத பகுதி — அவற்றை எப்படிக் கண்டுபிடிப்பது என்பது. Weight magnitude-ஆல் அல்ல — activation magnitude-ஆல். பெரிய activations சுமக்கும் input channels-ஐப் பெருக்கும் weights-தான் முக்கியமானவை. இது LLM.int8()-ன் கண்டுபிடிப்பேதான், weight பக்கத்திலிருந்து பார்த்தால்.

மேலும் AWQ அவற்றை fp16-ல் வைத்துக்கொள்வதில்லை, ஏனெனில் kernel-ல் mixed precision அசிங்கமானது: ragged layout, மெதுவான paths. அதற்குப் பதிலாக, quantise செய்வதற்கு முன் salient channels-ஐ மேலே scale செய்து, அதற்கேற்ப activations-ஐக் கீழே scale செய்கிறது — கணிதம் மாறாது, முக்கியமான weights grid-ன் நுணுக்கமான பகுதியில் வந்து விழுகின்றன. எல்லாமே சீரான int4-ஆகவே இருக்கிறது; அதனால்தான் AWQ kernels வேகமானவை.

தெளிவாக வைத்திருக்க வேண்டிய வேறுபாடு: LLM.int8() என்பது mixed-precision; அது outliers-ஐ runtime-ல், ஒவ்வொரு batch-க்கும், activations-ல் கண்டுபிடிக்கிறது. AWQ சீரான int4; weights-ஐ எப்படி scale செய்வது என்பதைத் தீர்மானிக்க activation statistics-ஐ quantisation நேரத்தில் ஒரு முறை மட்டும் பயன்படுத்துகிறது. GPTQ rounding பிழையைத் திருத்த ஒரு calibration set-ஐப் பயன்படுத்துகிறது. "நான் எந்த எண்களைக் காப்பாற்றுவது" என்பதற்கு மூன்று பதில்கள், எதிலும் backprop இல்லை.

QLoRA மற்றும் NF4: data இருக்கும் இடத்தில் levels-ஐ வை

இதுவரை உள்ள ஒவ்வொரு முறையும் தன் levels-ஐச் சமமான இடைவெளியில் வைக்கிறது; அது வெளிப்படையாகத் தவறு என்பதுதான் QLoRA-ன் வாதம். Pretrained weights தோராயமாக normal distribution-ல், பூஜ்ஜியத்தைச் சுற்றிக் குவிந்திருக்கின்றன; எனவே சமமான இடைவெளி levels தங்கள் resolution-ல் பெரும்பகுதியை கிட்டத்தட்ட எதுவும் இல்லாத tails-ல் செலவழிக்கின்றன. 4-bit NormalFloat அதற்குப் பதிலாக 16 levels-ஐ ஒரு normal distribution-ன் சம-நிகழ்தகவு quantiles-ல் வைக்கிறது. அதே 4 bits, weights இருக்கும் இடத்தில் நெருக்கமான levels — இதோ இரு தொகுப்புகளும், N(0,1)-லிருந்து 100,000 draws-ல் ஏற்படும் பிழையும்: 

linear int4 levels (evenly spaced):
  [-1.    -0.867 -0.733 -0.6   -0.467 -0.333 -0.2   -0.067  0.067 ...]
normal-quantile levels (NF4-style):
  [-1.    -0.708 -0.542 -0.417 -0.311 -0.216 -0.127 -0.042  0.042 ...]

weights ~ N(0,1), n=100000, absmax 4.369
  linear int4 relative error: 0.167915
  NF4-style   relative error: 0.118978
  improvement: 29.1%

how much data each of the 16 levels actually gets:
  linear: emptiest level      1  busiest  22082  levels under 1% of the data: 8/16
  NF4   : emptiest level     10  busiest  14431  levels under 1% of the data: 4/16

Linear levels-ல் பாதி ஒவ்வொன்றும் data-வில் 1%-க்கும் குறைவாகவே வைத்திருக்கின்றன. அவற்றில் ஒன்று ஒரு லட்சத்தில் ஒரே ஒரு weight-ஐப் பிடித்திருக்கிறது. அது உங்கள் bit budget-ல் பாதியை tails-ல் செலவழித்தது.

நேர்மையான எச்சரிக்கை: paper-ல் உள்ள உண்மையான NF4 table asymmetric-ஆகக் கட்டப்பட்டது — அதனால் சரியான பூஜ்ஜியம் ஒரு level-ஆக இருக்கும், zero-padding துல்லியமாகவே இருக்கும். என்னுடையது அதே கட்டுமானக் கருத்து ஐந்து வரிகளில்; மேலே உள்ள பிழை எண்கள் என் version-லிருந்து வந்தவை, அவர்களுடையதிலிருந்து அல்ல.

QLoRA எனக்குப் புரிய வைத்த பகுதி இதுதான். Weights ஒரு 4-bit grid-க்கு வந்த பிறகு நீங்கள் அவற்றை fine-tune செய்ய முடியாது. Grid step-ன் பாதியை விடச் சிறிய ஒரு gradient step, ஆரம்பித்த இடத்துக்கே round ஆகித் திரும்பிவிடும்:

Update சத்தமில்லாமல் மறைந்துவிடுகிறது. ஏதாவது நகரும் வரை learning rate-ஐ ஏற்றினால் ஒவ்வொரு step-ம் ஒரு முழு grid step ஆகிவிடும் — அது fine-tuning அல்ல, அது சேதம். எனவே QLoRA 4-bit base-ஐ உறையவைத்து, அதன் மேல் ஒரு சிறிய உயர்-துல்லிய LoRA adapter-ஐப் பயிற்றுவிக்கிறது. Gradients உறைந்த quantised weights வழியாகப் பாய்ந்து adapter-ஐ அடைகின்றன; base ஒருபோதும் update ஆவதில்லை. LoRA-ஐ நான் மீண்டும் விளக்கப் போவதில்லை — அந்தப் பக்கம் செய்கிறது.

4-bit grid-la fine-tune panna mudiyaadhu: chinna gradient step round aagi poyidum, 0 of 8 weights dhaan maarum. Adhaan QLoRA base-a freeze pannitu mela oru fp16 LoRA adapter-a train pannuthu.

Paper-ன் மூன்று பங்களிப்புகள்: NF4; double quantisation, அது block scales-ஐயே quantise செய்கிறது; மேலும் paged optimisers, அவை unified memory-ஐப் பயன்படுத்தி, இல்லையேல் உங்களை OOM ஆக்கிவிடும் gradient-checkpointing உச்சங்களைத் தாண்டி வர உதவுகின்றன. தலைப்பு முடிவு: ஒரே 48GB GPU-ல் ஒரு 65B model-ஐ finetune செய்வது, 16-bit finetuning செயல்திறனைக் குறைக்காமல்.

एक float एक storage budget है, और उसका ज़्यादातर हिस्सा बर्बाद जाता है

यह विचार आप पहले से जानते हैं। यह JPEG है। किसी तस्वीर को quality 80 पर सेव करने के बाद उसकी सटीकता में लगभग कुछ नहीं बचता, फिर भी वह वैसी ही दिखती है। आप बहुत कुछ फेंक सकते हैं और किसी को पता नहीं चलेगा — पर गलत चीज़ फेंक दीजिए और तुरंत दिख जाएगा: अक्षरों के चारों ओर ringing, आसमान में banding।

Weight matrix भी वही सौदा है। fp16 हर संख्या पर 16 bits खर्च करता है, 65504 तक की range के लिए, जबकि आपके सारे weights लगभग −3 और 3 के बीच बैठे हैं। तो उन्हें compress कीजिए: 

scale = abs(x).max() / 127        # अपनी range को 255 slots पर बिठाओ
q     = round(x / scale)          # <- lossy step. जानकारी यहीं मरती है
store(q)                          # हर weight पर दो नहीं, एक byte
x2    = q * scale                 # वापस गुणा। x के पास। x नहीं।

बस इतना ही। इस पेज का हर paper यही है। बाकी सब कुछ — LLM.int8(), GPTQ, AWQ, NF4 — इसी बात पर बहस है कि कौन-सी संख्याएँ एक scale साझा करती हैं, levels कहाँ बैठते हैं, और किन संख्याओं को आप compress करने से साफ़ इनकार कर देते हैं।

Scale कहाँ रहता है, पूरा खेल यही है

पूरे tensor के लिए एक scale का मतलब है कि सबसे तेज़ आवाज़ वाला channel हर शांत channel का resolution तय करेगा। इस पेज पर यही सबसे काम की बात है, और यही वजह है कि naive quantisation नाकाम होती है।

यह रहा एक 64×8 matrix जिसमें एक column को 50× तेज़ और एक को 50× धीमा बनाया गया है, दोनों तरीक़ों से int8 पर quantise किया गया:

LLM.int8(): outliers व्यवस्थित हैं

Dettmers et al. ने कुछ ऐसा पाया जो स्पष्ट नहीं है: लगभग 6.7B parameters के बाद transformers में outlier features पैदा हो जाते हैं — कुछ ही hidden dimensions, जिनके activations बाक़ी सबसे कहीं बड़े होते हैं, और वे layers और inputs दोनों के आर-पार उन्हीं dimensions में दिखते हैं। वे noise नहीं हैं। उन्हें शून्य कर दीजिए और model का प्रदर्शन ढह जाता है।

वे per-tensor int8 के लिए जानलेवा भी हैं, क्योंकि scale max से तय होता है। एक बहुत बड़ा मान पूरा grid खाली जगह पर ख़र्च कर देता है। यह रहे 32 tokens × 16 dimensions, जिनमें dims 3 और 11 में outliers डाले गए हैं:

  per-tensor scale went 0.024066 -> 0.827141  (34.4x coarser)
  per-tensor int8 relative error: 0.017330

  distinct int8 codes used by dim 0: 5 of 255

पूरे tensor की त्रुटि 1.7% दिखती है, जो झेली जा सकती है। वह औसत झूठ है: उस पर दोनों outliers हावी हैं, जो बहुत बड़े हैं और ठीक-ठाक quantise हो जाते हैं। जो dimensions बाक़ी सबके लिए मायने रखते हैं वे 24% त्रुटि पर हैं, और dimension 0 अपने 255 codes में से पाँच इस्तेमाल कर रहा है। नुक़सान को metric छिपा रहा है।

LLM.int8() का हल चतुर नहीं है, और यही बात है। Outlier columns को बाहर निकालिए, उन्हें fp16 में कीजिए, बाक़ी 99.9% को int8 में कीजिए, दोनों नतीजे जोड़ दीजिए। एक mixed-precision matmul. Paper का दावा है कि यह weight memory आधी करते हुए भी पूरी 16-bit गुणवत्ता बनाए रखता है — 175B पैमाने पर टिकने वाला पहला int8 तरीक़ा।

यहीं weight quantisation और activation quantisation के रास्ते अलग होते हैं। Weights सुशील हैं: सीमित, लगभग normal, पहले से ज्ञात। Activations input पर निर्भर करते हैं और outliers वहीं रहते हैं। इसीलिए GPTQ, AWQ और NF4 सब weight-only हैं — वे checkpoint छोटा करते हैं और matmul से पहले dequantise कर लेते हैं। LLM.int8() मुश्किल वाला काम कर रहा है।

GPTQ: एक क्रम में quantise कीजिए, और चलते-चलते भरपाई कीजिए

ऊपर का सब कुछ हर weight को अलग-अलग, एक ही बार में quantise करता है और त्रुटि स्वीकार कर लेता है। GPTQ एक बेहतर सवाल पूछता है: जब मैं इस weight को नीचे round करता हूँ, तो क्या मैं बचे हुए weights को थोड़ा हिलाकर उसकी भरपाई कर सकता हूँ?

यह column दर column चलता है। एक column quantise कीजिए, त्रुटि नापिए, फिर बचे हुए columns को इस तरह update कीजिए कि वे उसे सोख लें — कैसे, यह तय करने के लिए अनुमानित second-order जानकारी (एक Hessian, जो एक छोटे calibration set से आँका जाता है) इस्तेमाल होती है। हर rounding फ़ैसला एक क़र्ज़ छोड़ जाता है, और जो weights अभी जमे नहीं हैं वे उसे चुकाते हैं।

इससे तीन बातें निकलती हैं, और वही interview का माल हैं। यह one-shot post-training है: न retraining, न gradients, न labels. इसे calibration data चाहिए, जो bitsandbytes के int8 और NF4 को नहीं चाहिए — pipeline में GPTQ build के असहज होने की आम वजह यही है। और यह weight-only, 3 से 4 bit है: paper की मुख्य बात है 175B तक 3 और 4-bit quantisation, नगण्य accuracy नुक़सान के साथ, और इसीलिए Hub पर हर जगह GPTQ checkpoints मिलते हैं। Hessian update मेरी script में नहीं है — उसके लिए calibration set और एक Cholesky चाहिए, और वह मूल विचार को दबा देता।

AWQ: उन weights को बचाइए जिनकी activations को परवाह है

AWQ की खोज: weights का एक छोटा हिस्सा salient होता है, और उनमें से लगभग 1% को बचा लेने से ज़्यादातर गुणवत्ता वापस आ जाती है। कम स्पष्ट हिस्सा यह है कि आप उन्हें ढूँढ़ते कैसे हैं। weight magnitude से नहीं — activation magnitude से। जो weights मायने रखते हैं वे वही हैं जो बड़े activations ढोने वाले input channels से गुणा होते हैं। यह LLM.int8() वाली खोज ही है, weight की तरफ़ से देखी हुई।

और AWQ उन्हें fp16 में नहीं रखता, क्योंकि kernel में mixed precision भद्दा है: ragged layout, धीमे paths. इसके बजाय वह quantise करने से पहले salient channels को ऊपर scale करता है और उससे मेल खाते activations को नीचे — गणित वही रहता है और ज़रूरी weights grid के बारीक़ हिस्से पर आ बैठते हैं। सब कुछ एकसमान int4 रहता है, इसीलिए AWQ kernels तेज़ हैं।

यह फ़र्क़ साफ़ रखिए: LLM.int8() mixed-precision है और outliers को runtime पर, हर batch में, activations में ढूँढ़ता है। AWQ एकसमान int4 है और activation statistics को एक ही बार, quantisation के समय, इस्तेमाल करता है यह तय करने के लिए कि weights को कैसे scale किया जाए। GPTQ rounding त्रुटि सुधारने के लिए calibration set इस्तेमाल करता है। "मैं किन संख्याओं को बचाऊँ" के तीन जवाब, और किसी में भी backprop नहीं।

QLoRA और NF4: levels वहाँ रखिए जहाँ data है

अब तक की हर योजना अपने levels बराबर दूरी पर रखती है, और QLoRA का तर्क है कि यह ज़ाहिर तौर पर ग़लत है। Pretrained weights लगभग normal रूप से बँटे होते हैं, शून्य के आसपास ढेर लगाए हुए, इसलिए बराबर दूरी वाले levels अपना ज़्यादातर resolution उन tails पर ख़र्च करते हैं जहाँ लगभग कुछ है ही नहीं। 4-bit NormalFloat इसके बजाय 16 levels को normal distribution के बराबर-प्रायिकता quantiles पर रखता है। वही 4 bits, पर levels वहाँ भीड़ लगाते हैं जहाँ weights हैं — यह रहे दोनों सेट, और N(0,1) से 100,000 draws पर त्रुटि:

The code

Pure NumPy. No torch, no autograd, no training — quantisation is arithmetic, and you can watch every rounded number. Every function under 12 lines.

Download the full script — about 70 lines of core plus seven runnable demos. (The asymmetric pair, quantize_asymmetric and its inverse, is in the file; it is the same four lines with a zero_point.) Then: 

python3 quantization_from_scratch.py
def quantize_symmetric(x, bits=8):
    qmax = 2 ** (bits - 1) - 1              # 127 for int8
    scale = np.abs(x).max() / qmax          # one float per tensor
    q = np.clip(np.round(x / scale), -qmax, qmax)   # the lossy step
    return q.astype(np.int32), scale

def dequantize_symmetric(q, scale):
    return q * scale                        # back to float. Not the original.

def quantize_per_channel(W, bits=8, axis=0):
    qmax = 2 ** (bits - 1) - 1
    scale = np.abs(W).max(axis=axis, keepdims=True) / qmax   # one per column
    q = np.clip(np.round(W / scale), -qmax, qmax)
    return q.astype(np.int32), scale

def quantize_grouped(x, bits=4, group=128):
    flat = x.reshape(-1, group)                     # rows of g values
    qmax = 2 ** (bits - 1) - 1
    scale = np.abs(flat).max(axis=1, keepdims=True) / qmax
    q = np.clip(np.round(flat / scale), -qmax, qmax)
    return (q * scale).reshape(x.shape), scale.size  # recovered, n_scales

def normal_levels(bits=4):
    n = 2 ** bits
    ps = [(i + 0.5) / n for i in range(n)]          # equal probability mass
    lv = np.array([NormalDist().inv_cdf(p) for p in ps])
    return lv / np.abs(lv).max()                    # squash into [-1, 1]

def quantize_to_levels(x, levels):
    """Snap each value to the nearest level, after absmax-scaling to [-1, 1]."""
    scale = np.abs(x).max()
    idx = np.abs(x[:, None] / scale - levels[None, :]).argmin(axis=1)
    return levels[idx] * scale

def outlier_columns(X, threshold=6.0):
    return np.where(np.abs(X).max(axis=0) >= threshold)[0]

def quantize_mixed(X, outlier_cols, bits=8):
    keep = np.zeros(X.shape[1], dtype=bool)
    keep[outlier_cols] = True
    out = X.copy()                                  # outlier cols stay fp16-ish
    rest = X[:, ~keep]
    q, s = quantize_symmetric(rest, bits)           # the rest goes to int8
    out[:, ~keep] = dequantize_symmetric(q, s)
    return out

On the maths anxiety

There is almost none here. Division, rounding, clamping, and one idea about where to put 16 tick marks on a number line. If you can write round(x / scale) you have implemented the core of every paper on this page. No torch, no autograd, no GPU.

Two places real maths does appear, and you can leave both to the library. GPTQ's compensation step uses second-order information — a Hessian, an approximation of how sensitive the loss is to each weight — and the implementation involves a Cholesky decomposition for numerical stability. NF4's levels come from the inverse normal CDF. I called NormalDist().inv_cdf from the standard library and moved on.

Worth your time instead: the arithmetic in the memory section, and the vocabulary — weight-only vs activation quantisation, post-training vs quantisation-aware training, per-tensor vs per-channel vs per-group, symmetric vs asymmetric. Those distinctions are what the questions are actually about, and none of them need a proof.
