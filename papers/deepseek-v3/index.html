DeepSeek-V3: the recipe, and the interconnect that shaped it

DeepSeek-AI, 2024

Almost every choice in this model is downstream of one number on a spec sheet.

Download deepseek-v3_from_scratch.py — everything below runs from it. NumPy only, and nothing in it is a benchmark: it counts bytes and simulates schedules.

I read this report the way everyone did — looking for the trick. There isn't one. There are about eight, and they all point the same direction, and I couldn't see the direction until I noticed which GPUs they were on.

US export controls meant DeepSeek trained on H800s. Same chip as an H100 for arithmetic. Roughly half the NVLink — the chip-to-chip link inside a server. For a mixture-of-experts model that is the cruellest possible cut, because routing tokens to experts is an all-to-all, and all-to-all is exactly what a narrow link punishes.

You've built this system before

You have a service that fans a request out to backends and merges the replies. On a fast local network you write it the obvious way: 

def handle(req):
    picks = router.pick(req, k=8)              # 8 backends, wherever they live
    return merge([call(b, req) for b in picks])   # ship the payload to each

Then you move it to a link a third the speed, and it falls over. Not because the backends got slower — they didn't — but because the payload now spends longer on the wire than in the handler. You already know the three fixes, because you've shipped all of them: 

def handle(req):
    picks = router.pick(req, k=8, max_racks=4)  # 1. cap the fan-out
    payload = compress(req)                     # 2. shrink every byte
    fut = send_async(picks, payload)            # 3. overlap the wire with work
    local = do_other_work()
    return merge(fut.result(), local)

That is DeepSeek-V3's engineering half, in three lines. Cap the fan-out is node-limited routing. Shrink every byte is FP8. Overlap the wire with work is DualPipe. Everything else is detail about how far below the abstraction layer they were willing to go to make those three actually happen.

The one formula

Not a loss function. The formula that matters here is the one that decides whether your GPUs are computing or waiting:

tcomm / tcompute = (bytes / bandwidth) ÷ (FLOPs / throughput)

Read it as pipeline stages:

StepFor one MoE layerWhat it does
FLOPsk × 3 × 2 × dmodel × dffn per tokenTop-8 SwiGLU experts. Three matrices each, two flops per multiply-add
bytesnodes × dmodel × (1 + 2) on IB, k × dmodel × (1 + 2) on NVLinkOne copy per destination node out, results back. FP8 out, BF16 back

ratio < 1compute-boundYour tensor cores set the clock. Make the model bigger
ratio > 1comm-boundYour wire sets the clock. Every design decision changes

The constraint, counted

DeepSeek-V3 is 671B total parameters, 37B active per token, 61 layers, dmodel 7168, 256 routed experts plus one shared, top-8 routing, expert hidden size 2048. Take one GPU with a micro-batch of 4096 tokens through one MoE layer and count.

The bandwidth numbers below are published specifications, not something I measured, and the "times" are bytes divided by those specifications. This is the same kind of counting the FlashAttention page does for HBM traffic — a roofline sketch, not a profile.

2,731 FLOP per byte is what this layer offers. 2,199 is what an H100's NVLink can feed. 4,948 is what an H800's can. The layer sits between them. That is the entire story, and here it is as time: 

  machine          compute   NVLink leg   comm/compute   verdict
  H100  900 GB/s    1.46ms      0.78ms          0.54x   COMPUTE-bound
  H800  400 GB/s    1.46ms      1.76ms          1.21x   COMM-bound

  same layer, same arithmetic, one number on a spec sheet halved,
  and the bottleneck moves from the tensor cores to the wire.
Nothing about the model changed. Same weights, same FLOPs, same batch. One spec-sheet number halved and the layer crossed from compute-bound to communication-bound. Every remaining section of this page is a response to that crossing.

And the cross-node leg, which export controls did not touch, is worse than either — which is why the node cap exists at all: 

the cross-node leg, which the export cut did NOT touch:
  H100: IB  7.05ms + NVLink  0.78ms = 5.37x compute   (9.0x the NVLink leg)
  H800: IB  7.05ms + NVLink  1.76ms = 6.04x compute   (4.0x the NVLink leg)

The report is explicit that it tuned the node cap so the InfiniBand and NVLink legs can be overlapped, citing an effective NVLink-to-IB bandwidth ratio of about 3.2:1. That implies an achieved NVLink figure nearer 160 GB/s than 400. Treat my 900 and 400 as ceilings nobody reaches; the shape of the table is the point, not the decimals.

Auxiliary-loss-free balancing: the neatest idea in the paper

A router that plays favourites is the hot-shard problem, and the MoE page fixes it the standard way: add an auxiliary loss that penalises uneven routing. It works. It also adds a gradient — one that is, by construction, not the task's gradient. You are asking the router to be balanced instead of being right.

V3 replaces it with something an SRE would recognise immediately: a thermostat.

selection_score = affinity + bias      # bias affects WHO IS PICKED
gate            = affinity             # and never the loss, so grad(bias) = 0

bias[expert] -= gamma * sign(load[expert] - mean_load)   # after each step

Overloaded expert, bias down. Starved expert, bias up. Fixed step, sign only. It moves the selection and leaves the gradient alone. My script sets up a toy world where token demand is Zipf-skewed — so the routing the model wants is genuinely imbalanced, and balance and quality really do fight.

max/min expert occupancy, by step (1.0 = perfectly balanced):

     0      11.2        11.2           11.2
    10       8.7         3.8            8.1
    20       6.6         3.2            2.0
    40       6.1         3.0            2.2
    59       6.1         3.0            2.1

Both balance. Now the number that motivates the whole idea — the gradient the balancing mechanism contributes to the router's weights, and how well the router still picks the right expert once you take the bias back off:

Better balance and no accuracy loss. Turn the auxiliary weight up and you get the failure the paper is built to avoid — you buy balance you already had, with quality:

  balance  max/min : 3.1  (aux 1.50: 3.0, bias: 2.1)
  router accuracy  : 0.7324  <- balanced, and worse
  balancing grad   : 1.323678

The thermostat has its own failure mode, and it's the one you'd guess:

BREAK IT: bias update rate gamma=8.0 instead of 0.6
  max/min occupancy, last 8 steps:
    [202.   81.8 224.  202.   63.6 153.   63.4 153. ]
   vs gamma=0.6: [2.  1.6 2.  1.6 2.  1.6 1.3 2.1]
  final bias vector: [144. 144. 144. 144. 144. 152. 144. 144.]
Step size too big, and it oscillates instead of settling. It's a controller. It has a gain, and you tune the gain. The report's own caveat is worth keeping: they also use a small sequence-wise balancing loss as a backstop, so "auxiliary-loss-free" means the primary mechanism is the bias, not that no balancing loss exists anywhere.

Node-limited routing: capping the fan-out

A token wants its top-8 experts wherever they live. Left alone it can touch eight different servers, and every extra server is another InfiniBand copy of the same 7168-wide vector across the slowest link in the machine. The cap: score each node by the sum of its experts' affinities, keep the best M nodes, and pick the top-8 only from those. V3 uses M = 4. 

256 experts over 32 nodes (8 experts per node), top-8, 4096 tokens

  uncapped: mean 6.652 nodes/token, max 8
  capped  : mean 3.748 nodes/token, max 4  (M=4)

  InfiniBand bytes, uncapped: 585.9 MB  (11.72 ms at 50 GB/s)
  InfiniBand bytes, capped  : 330.1 MB  (6.60 ms at 50 GB/s)
  saved: 43.7%

what the cap costs -- experts still reachable per token:
  uncapped : 256 of 256 (100.0%)
  capped   : 32 of 256 (12.5%)
  mean overlap with the uncapped choice: 3.62 of 8 experts

It is not free, and the script prints exactly how unfree: a capped token gets 3.62 of the 8 experts it would otherwise have chosen, and only an eighth of the expert pool is reachable at all. You are trading model freedom for wire time. Sweep the cap and watch the trade: 

  M=2: 2.000 nodes/token,    176.1 MB IB, overlap 2.57/8
  M=4: 3.748 nodes/token,    330.1 MB IB, overlap 3.62/8
  M=8: 5.330 nodes/token,    469.5 MB IB, overlap 5.00/8
  M=32: 6.652 nodes/token,    585.9 MB IB, overlap 8.00/8

M is not chosen to minimise traffic — M=2 would do that. It is chosen so the IB leg and the NVLink leg are close enough in size to hide underneath each other, given that 3.2:1 ratio. The cap and the overlap are one design, not two.

FP8: the other half of the byte reduction

Halving the fan-out halves the copies. Halving the payload halves what each copy carries. V3 trains the GEMMs in 8-bit floating point — which, if you've read the quantisation page, you'll recognise as the same argument one octave further down. Two formats exist and neither is good enough alone: 

format   exp  man     max finite   min normal   steps per octave
  e4m3    4    3            448    1.562e-02      8
  e5m2    5    2         57,344    6.104e-05      4

e4m3 has the precision and not the range. e5m2 has the range and not the precision. Cast real tensors straight in and watch which dies: 

direct cast, one tensor, no scaling -- relative L2 error:
  tensor                     e4m3        e5m2     e4m3 finite?
  weights   (N(0,0.02))    0.310877    0.051356     True
  activation (N(0,1))      0.027098    0.053512     True
  act+outlier (x1500)           inf    0.024086     False
  grads     (N(0,1e-5))    1.000000    1.000000     True

which tensor dies first: the one with the outlier.
  max |activation| = 1,500.0  vs e4m3 max 448
  values that became inf: 1
  gradients underflow e4m3's min normal: 4096 of 4096 -> 0

One value out of 4096 exceeded 448 and the tensor is gone. A single FP32 scale per tensor brings it back — but that scale is set by the loudest value, and the quiet ones pay for it. Smaller blocks, more scales, fewer dead values: 

  direct cast, no scale : inf   <- overflowed, the tensor is gone
  one FP32 scale        : 0.001151   finite again

4096 activations, N(0,1), with four values of 3000 dropped in.
Error measured on the 4092 ORDINARY values only:
  block   err on quiet values   dead (rounded to 0)   bits/value
   4096             0.031677                   343        8.008
    512             0.029651                   184        8.062
    128             0.026348                    38        8.250
     32             0.024253                    12        9.000

That is V3's fine-grained quantisation: 1×128 tiles for activations, 128×128 for weights. The format did not get better. The blocks got smaller. The report pairs it with FP32 accumulation and wider master weights and optimiser state, because the places 8 bits are unacceptable are exactly the places error compounds. What it buys: 

  one activation tile, 4096 tokens x 7168:
    BF16                    58.72 MB
    FP8 (1x128 scales)      30.28 MB
  all-to-all bytes/token: BF16 dispatch 344,064 B ->
                          FP8  dispatch 258,048 B (25.0% less)

Multi-token prediction: two targets for one forward pass

A standard language model gets one training signal per position: predict the next token, as on the GPT page. V3 adds a second head that predicts the token after that, sequentially, keeping the full causal chain. Same forward pass, twice the targets. 

micro-batch: 4096 positions
  MTP depth 0 (1 head): 4,096 prediction targets per forward pass  (1.0x)
  MTP depth 1 (2 heads): 8,192 prediction targets per forward pass  (2.0x)
  MTP depth 2 (3 heads): 12,288 prediction targets per forward pass  (3.0x)

what each head predicts, for the sentence positions 0..4:
  pos 0 (the  ) -> head 1: cat     head 2: ate
  pos 1 (cat  ) -> head 1: ate     head 2: the
  pos 2 (ate  ) -> head 1: the     head 2: food

V3 uses depth 1 — one extra head. It is a training objective; the extra head is dropped for ordinary inference. But you can keep it, and then it is a draft model that costs almost nothing, which is speculative decoding with the drafter already inside the target model. The report puts second-token acceptance at 85–90% and reports roughly 1.8× decoding throughput from using it that way. 

expected tokens accepted per decoding step = 1 + p(second accepted):
  acceptance 0.85  ->  1.85 tokens/step (1.85x, before the extra head's own cost)
  acceptance 0.90  ->  1.90 tokens/step (1.90x, before the extra head's own cost)

The 1 + p arithmetic is mine, not theirs, and it ignores verification cost. The 85–90% and the 1.8× are the report's.

Overlapping communication with compute

You cannot delete the all-to-all. You can make it happen while the GPU is doing something else — the async call you already write without thinking. My script simulates a 1F1B pipeline, 8 stages, 32 microbatches, and asks what the device is doing. This is a simulation of a schedule, not a measurement of DeepSeek's. 

pipeline: 8 stages, 32 microbatches, compute 1.0, all-to-all 0.8 per microbatch

  schedule            makespan   device busy   bubble
  no overlap             70.20        45.6%     54.4%
  comm hidden            39.00        82.1%     17.9%

  wall-clock penalty for not overlapping: 1.80x
  illustration only: a 56.7-day run with this shape becomes 102.1 days

The second column is the one worth staring at. Once communication is hidden, making it more expensive stops mattering until it exceeds compute: 

  comm    bubble (no overlap)   bubble (overlapped)   speedup
   0.2                31.6%                 17.9%       1.20x
   0.5                45.3%                 17.9%       1.50x
   0.8                54.4%                 17.9%       1.80x
   1.2                62.7%                 31.6%       1.83x
   2.0                72.6%                 59.0%       1.50x
That flat 17.9% is the design goal. Get the communication cost under the compute cost and it vanishes from the wall clock entirely. DualPipe goes further than my simulation — it runs the pipeline from both ends at once — but the part that matters here is the part I can show you: hide the wire behind the maths.

What "went below the abstraction layer" actually means

Three things in the report that most write-ups skip, and that are the reason the three fixes above were achievable rather than aspirational:

What they didWhy
Wrote PTX, NVIDIA's assembly-level layer below CUDA, for the communication kernelsThe dispatch/combine kernels had to be tuned by hand. Inline asm, because the compiler wouldn't do it
Reserved a fraction of each GPU's streaming multiprocessors for communicationComm and compute genuinely run at once. You budget the cores, the way you'd pin a thread pool
Avoided tensor parallelism entirelyIt is the most communication-hungry parallelism there is — it talks inside every layer. On a narrow link it's the first thing to go

Multi-head latent attention is theirs too, from DeepSeek-V2: it compresses the key-value cache into one low-rank latent vector per token, so long-context serving stops being a memory problem. It has its own page — multi-head latent attention, built on the byte counting from the KV cache page — so I've deliberately not re-derived it here.

The number everyone gets wrong

You will be asked about the $5.6M. Do the division yourself once and you'll never repeat it carelessly: 

  final pre-training GPU-hours (report) : 2,788,000 H800-hours
  assumed rental price (report's own)   : $2.00 per GPU-hour
  product                               : $5.576M
  on 2048 GPUs that is 56.7 days of wall clock
  tokens: 14.8e12 over 671e9 params, 37e9 active per token
  tokens per active parameter           : 400
  approx forward+backward FLOPs (6*N*D) : 3285.6 ZFLOP
  implied MFU against BF16 peak         : 33.1%
  against the FP8 peak they actually used: 16.5%
That figure is the final pre-training run only, at a rental price the report itself assumes. It excludes research, ablations, failed runs, the earlier DeepSeek models this one builds on, salaries, and the cluster. The report says so directly. "DeepSeek built a frontier model for $5.6M" is not what the report claims.

The 400 tokens per active parameter is worth a second look next to the scaling laws page — it is far past Chinchilla-optimal, which is what you do when you intend to serve the model rather than win a compute-optimal argument.

இந்த system-ஐ நீங்கள் ஏற்கனவே கட்டியிருக்கிறீர்கள்

ஒரு request-ஐப் பல backends-க்கு fan-out செய்து பதில்களை merge செய்யும் service உங்களிடம் இருக்கிறது. வேகமான local network-இல் நீங்கள் இதை வெளிப்படையான வழியில் எழுதுவீர்கள்: 

def handle(req):
    picks = router.pick(req, k=8)              # 8 backends, எங்கிருந்தாலும்
    return merge([call(b, req) for b in picks])   # ஒவ்வொன்றுக்கும் payload

பிறகு அதை மூன்றில் ஒரு பங்கு வேகமுள்ள link-க்கு நகர்த்துகிறீர்கள், அது விழுந்துவிடுகிறது. backends மெதுவாகிவிட்டதால் அல்ல — அவை மாறவே இல்லை — ஆனால் payload இப்போது handler-இல் இருப்பதைவிட wire-இல் அதிக நேரம் செலவழிக்கிறது. மூன்று திருத்தங்களும் உங்களுக்குத் தெரியும், ஏனெனில் மூன்றையும் நீங்கள் ship செய்திருக்கிறீர்கள்: 

def handle(req):
    picks = router.pick(req, k=8, max_racks=4)  # 1. fan-out-ஐ cap செய்
    payload = compress(req)                     # 2. ஒவ்வொரு byte-ஐயும் சுருக்கு
    fut = send_async(picks, payload)            # 3. wire-ஐ வேலையுடன் overlap செய்
    local = do_other_work()
    return merge(fut.result(), local)

DeepSeek-V3-இன் engineering பாதி இதுதான், மூன்று வரிகளில். fan-out-ஐ cap செய்வது node-limited routing. ஒவ்வொரு byte-ஐயும் சுருக்குவது FP8. wire-ஐ வேலையுடன் overlap செய்வது DualPipe. மீதி எல்லாம், இந்த மூன்றையும் உண்மையில் நடக்கவைக்க abstraction layer-க்குக் கீழே அவர்கள் எவ்வளவு தூரம் இறங்கத் தயாராக இருந்தார்கள் என்பதன் விவரம்.

Auxiliary-loss-free balancing: paper-இன் மிக நேர்த்தியான யோசனை

சிலரையே பிரியப்படும் ஒரு router என்பது hot-shard பிரச்சனை, அதை MoE page வழக்கமான முறையில் சரிசெய்கிறது: சமமற்ற routing-ஐத் தண்டிக்கும் ஒரு auxiliary loss சேர்ப்பது. அது வேலை செய்கிறது. ஆனால் அது ஒரு gradient-ஐயும் சேர்க்கிறது — கட்டமைப்பாலேயே அது task-இன் gradient அல்ல. Router-ஐ, சரியாக இருப்பதற்கு பதிலாக சமநிலையாக இருக்கச் சொல்கிறீர்கள்.

V3 அதை ஒரு SRE உடனே அடையாளம் காணும் ஒன்றால் மாற்றுகிறது: ஒரு thermostat.

selection_score = affinity + bias      # bias யாரைத் தேர்வு செய்வது என்பதை மாற்றும்
gate            = affinity             # loss-ஐ அல்ல, எனவே grad(bias) = 0

bias[expert] -= gamma * sign(load[expert] - mean_load)   # ஒவ்வொரு step-க்குப் பின்

சுமை அதிகமான expert, bias கீழே. பட்டினி கிடக்கும் expert, bias மேலே. நிலையான step, sign மட்டும். இது selection-ஐ நகர்த்துகிறது, gradient-ஐத் தொடுவதில்லை. என் script ஒரு பொம்மை உலகை அமைக்கிறது, அதில் token demand Zipf-skewed — அதாவது model விரும்பும் routing உண்மையிலேயே சமமற்றது, எனவே balance-ம் தரமும் நிஜமாகவே சண்டையிடுகின்றன.

ஒரு token தன் top-8 experts-ஐ, அவை எங்கிருந்தாலும் விரும்புகிறது. சும்மா விட்டால் அது எட்டு வெவ்வேறு servers-ஐத் தொடலாம், ஒவ்வொரு கூடுதல் server-ம் அதே 7168-அகல vector-இன் இன்னொரு InfiniBand நகல், அதுவும் இயந்திரத்தின் மிக மெதுவான link-இல். Multi-token prediction: ஒரு forward pass, இரண்டு targets

ஒரு வழக்கமான language model-க்கு ஒவ்வொரு position-லும் ஒரே ஒரு training signal: அடுத்த token-ஐக் கணி, GPT page-இல் உள்ளதுபோல. V3 ஒரு இரண்டாவது head-ஐச் சேர்க்கிறது, அது அதற்கு அடுத்த token-ஐ வரிசையாகக் கணிக்கிறது, முழு causal சங்கிலியையும் காப்பாற்றுகிறது. அதே forward pass, இரண்டு மடங்கு targets. 

micro-batch: 4096 positions
  MTP depth 0 (1 head): 4,096 prediction targets per forward pass  (1.0x)
  MTP depth 1 (2 heads): 8,192 prediction targets per forward pass  (2.0x)
  MTP depth 2 (3 heads): 12,288 prediction targets per forward pass  (3.0x)

what each head predicts, for the sentence positions 0..4:
  pos 0 (the  ) -> head 1: cat     head 2: ate
  pos 1 (cat  ) -> head 1: ate     head 2: the
  pos 2 (ate  ) -> head 1: the     head 2: food

V3 depth 1 பயன்படுத்துகிறது — ஒரு கூடுதல் head. இது ஒரு training நோக்கம்; வழக்கமான inference-க்கு அந்தக் கூடுதல் head கைவிடப்படுகிறது. ஆனால் அதை வைத்துக்கொள்ளலாம், அப்போது அது ஏறக்குறைய செலவே இல்லாத ஒரு draft model — அதாவது target model-க்குள்ளேயே drafter இருக்கும் speculative decoding. இரண்டாவது token-இன் acceptance-ஐ 85–90% என்று report சொல்கிறது, அப்படிப் பயன்படுத்தினால் decoding throughput சுமார் 1.8× என்று தெரிவிக்கிறது. 

expected tokens accepted per decoding step = 1 + p(second accepted):
  acceptance 0.85  ->  1.85 tokens/step (1.85x, before the extra head's own cost)
  acceptance 0.90  ->  1.90 tokens/step (1.90x, before the extra head's own cost)

1 + p கணக்கு என்னுடையது, அவர்களுடையது அல்ல, verification செலவை அது கணக்கில் எடுக்கவில்லை. 85–90%-ம் 1.8×-ம் report-இன் எண்கள்.

"abstraction layer-க்குக் கீழே போனது" என்பதன் உண்மையான அர்த்தம்

பெரும்பாலான விளக்கங்கள் தவிர்க்கும் மூன்று விஷயங்கள் report-இல் இருக்கின்றன, மேலே சொன்ன மூன்று திருத்தங்களும் கனவாக இல்லாமல் நிஜமாக முடிந்ததற்கு அவைதான் காரணம்:

அவர்கள் செய்ததுஏன்

यह system आप पहले बना चुके हैं

आपके पास एक service है जो एक request को कई backends में fan out करती है और जवाब merge करती है। तेज़ local network पर आप इसे सीधे-सीधे लिखते हैं: 

def handle(req):
    picks = router.pick(req, k=8)              # 8 backends, कहीं भी हों
    return merge([call(b, req) for b in picks])   # हर एक को payload भेजो

फिर आप इसे एक तिहाई रफ़्तार वाले link पर ले जाते हैं, और यह गिर जाती है। इसलिए नहीं कि backends धीमे हो गए — वे वही हैं — बल्कि इसलिए कि payload अब handler के मुक़ाबले wire पर ज़्यादा समय बिताता है। तीनों उपाय आप जानते ही हैं, क्योंकि तीनों आप ship कर चुके हैं: 

def handle(req):
    picks = router.pick(req, k=8, max_racks=4)  # 1. fan-out को cap करो
    payload = compress(req)                     # 2. हर byte को छोटा करो
    fut = send_async(picks, payload)            # 3. wire को काम से overlap करो
    local = do_other_work()
    return merge(fut.result(), local)

यही DeepSeek-V3 का engineering वाला आधा हिस्सा है, तीन लाइनों में। fan-out को cap करना node-limited routing है। हर byte को छोटा करना FP8 है। wire को काम से overlap करना DualPipe है। बाक़ी सब इस बात का ब्यौरा है कि इन तीनों को सचमुच करने के लिए वे abstraction layer के कितने नीचे तक जाने को तैयार थे।

वह अड़चन, गिनकर

DeepSeek-V3 में कुल 671B parameters हैं, प्रति token 37B active, 61 layers, dmodel 7168, 256 routed experts और एक shared, top-8 routing, expert hidden size 2048. 4096 tokens के micro-batch वाले एक GPU को एक MoE layer से गुज़ारिए और गिनिए।

नीचे दिए bandwidth के आँकड़े प्रकाशित specifications हैं, मेरे नापे हुए नहीं, और "समय" उन्हीं specifications से bytes को भाग देकर निकला है। यह वैसी ही गिनती है जैसी FlashAttention page HBM traffic के लिए करती है — एक roofline खाका, profile नहीं।

मेरी बात पर मत जाइए। असली output यह रहा:

tokens on this GPU        : 4096
d_model                   : 7168, top-8 routed experts, capped at 4 nodes
expert FLOPs per token    : 704.6 MFLOP
expert FLOPs, this batch  : 2.89 TFLOP

NVLink bytes      (out+in): 704.6 MB (8 expert copies inside the nodes)
arithmetic intensity of this layer:
  2,731 FLOP per byte moved
machine balance (FLOP per byte the link can feed, FP8 compute):
  H100 NVLink 900 GB/s: 2,199
  H800 NVLink 400 GB/s: 4,948
  InfiniBand   50 GB/s: 39,580

2,731 FLOP per byte वह है जो यह layer देती है। 2,199 वह है जो एक H100 का NVLink खिला सकता है। 4,948 वह है जो H800 का। Layer इन दोनों के बीच बैठी है। पूरी कहानी यही है, और समय के रूप में यह रही: 

  machine          compute   NVLink leg   comm/compute   verdict
  H100  900 GB/s    1.46ms      0.78ms          0.54x   COMPUTE-bound
  H800  400 GB/s    1.46ms      1.76ms          1.21x   COMM-bound

  same layer, same arithmetic, one number on a spec sheet halved,
  and the bottleneck moves from the tensor cores to the wire.
Model में कुछ भी नहीं बदला। वही weights, वही FLOPs, वही batch. spec-sheet का एक number आधा हुआ और layer compute-bound से communication-bound में चली गई। इस पेज का बाक़ी हर हिस्सा उसी पार जाने का जवाब है।

और cross-node leg, जिसे export controls ने छुआ नहीं, दोनों से बुरी है — यही वजह है कि node cap है ही: 

the cross-node leg, which the export cut did NOT touch:
  H100: IB  7.05ms + NVLink  0.78ms = 5.37x compute   (9.0x the NVLink leg)
  H800: IB  7.05ms + NVLink  1.76ms = 6.04x compute   (4.0x the NVLink leg)

Report साफ़ कहती है कि उसने node cap को इस तरह tune किया कि InfiniBand और NVLink दोनों legs को overlap किया जा सके, और वह NVLink-से-IB का प्रभावी bandwidth अनुपात क़रीब 3.2:1 बताती है। इसका मतलब है कि असल में मिलने वाला NVLink आँकड़ा 400 से ज़्यादा 160 GB/s के पास है। मेरे 900 और 400 को ऐसी छतें मानिए जिन तक कोई नहीं पहुँचता; बात table की शक्ल की है, दशमलव की नहीं।

Auxiliary-loss-free balancing: paper का सबसे सुंदर विचार

पक्षपात करने वाला router यानी hot-shard समस्या, और MoE page इसे मानक तरीक़े से ठीक करती है: एक auxiliary loss जोड़ो जो असमान routing को सज़ा दे। यह काम करता है। यह एक gradient भी जोड़ता है — ऐसा gradient जो बनावट से ही task का gradient नहीं है। आप router से कह रहे हैं कि वह सही होने के बजाय संतुलित हो।

V3 इसकी जगह वह चीज़ रखता है जिसे कोई भी SRE तुरंत पहचान लेगा: एक thermostat.

selection_score = affinity + bias      # bias तय करता है कौन चुना जाएगा
gate            = affinity             # loss को कभी नहीं, इसलिए grad(bias) = 0

bias[expert] -= gamma * sign(load[expert] - mean_load)   # हर step के बाद

Expert पर बोझ ज़्यादा, तो bias नीचे। Expert भूखा, तो bias ऊपर। तय क़दम, सिर्फ़ sign. यह selection को हिलाता है और gradient को छूता तक नहीं। मेरी script एक खिलौना दुनिया बनाती है जिसमें token demand Zipf-skewed है — यानी model जो routing चाहता है वह सचमुच असंतुलित है, और balance तथा गुणवत्ता वाक़ई आपस में लड़ते हैं।

  [162  90  73  49  43  35  27  33]

दोनों संतुलन ले आते हैं। अब वह आँकड़ा जो पूरे विचार की जड़ है — balancing तंत्र router के weights में कितना gradient जोड़ता है, और bias हटा देने के बाद router कितनी अच्छी तरह सही expert चुनता है:

बेहतर balance और accuracy में कोई नुक़सान नहीं। auxiliary weight बढ़ाइए तो वही नाकामी मिलेगी जिससे बचने के लिए यह paper बना है — आप वह balance ख़रीदते हैं जो पहले से था, और क़ीमत गुणवत्ता से चुकाते हैं:

  balance  max/min : 3.1  (aux 1.50: 3.0, bias: 2.1)

  balancing grad   : 1.323678

Thermostat की अपनी नाकामी भी है, और वही जिसका आप अंदाज़ा लगाएँगे:

    [202.   81.8 224.  202.   63.6 153.   63.4 153. ]

Step size बहुत बड़ा हो तो यह जमने के बजाय झूलने लगता है। यह एक controller है। इसका एक gain है, और gain को आप tune करते हैं। Report की अपनी चेतावनी याद रखने लायक़ है: backstop के तौर पर वे एक छोटा sequence-wise balancing loss भी इस्तेमाल करते हैं, इसलिए "auxiliary-loss-free" का मतलब है कि मुख्य तंत्र bias है, यह नहीं कि कहीं कोई balancing loss है ही नहीं।

Node-limited routing: fan-out पर ढक्कन

एक token अपने top-8 experts चाहता है, वे जहाँ भी हों। खुला छोड़ दें तो वह आठ अलग servers को छू सकता है, और हर अतिरिक्त server का मतलब उसी 7168-चौड़े vector की एक और InfiniBand copy, मशीन के सबसे धीमे link पर। ढक्कन यह है: हर node को उसके experts की affinities के योग से अंक दो, सबसे अच्छे M nodes रखो, और top-8 सिर्फ़ उन्हीं में से चुनो। V3 में M = 4. 

256 experts over 32 nodes (8 experts per node), top-8, 4096 tokens

  uncapped: mean 6.652 nodes/token, max 8
  capped  : mean 3.748 nodes/token, max 4  (M=4)

  InfiniBand bytes, uncapped: 585.9 MB  (11.72 ms at 50 GB/s)
  InfiniBand bytes, capped  : 330.1 MB  (6.60 ms at 50 GB/s)
  saved: 43.7%

what the cap costs -- experts still reachable per token:
  uncapped : 256 of 256 (100.0%)
  capped   : 32 of 256 (12.5%)
  mean overlap with the uncapped choice: 3.62 of 8 experts

यह मुफ़्त नहीं है, और script ठीक-ठीक छापती है कि कितना महँगा है: capped token को उन 8 experts में से 3.62 मिलते हैं जो वह वरना चुनता, और पूरे expert pool का सिर्फ़ आठवाँ हिस्सा ही पहुँच में रहता है। आप model की आज़ादी को wire के समय से बदल रहे हैं। Cap को sweep कीजिए और सौदा देखिए: 

  M=2: 2.000 nodes/token,    176.1 MB IB, overlap 2.57/8
  M=4: 3.748 nodes/token,    330.1 MB IB, overlap 3.62/8
  M=8: 5.330 nodes/token,    469.5 MB IB, overlap 5.00/8
  M=32: 6.652 nodes/token,    585.9 MB IB, overlap 8.00/8

M को traffic घटाने के लिए नहीं चुना गया — वह तो M=2 करता। इसे इसलिए चुना गया कि उस 3.2:1 अनुपात को देखते हुए IB leg और NVLink leg आकार में इतने पास हों कि एक दूसरे के नीचे छिप जाएँ। Cap और overlap दो design नहीं, एक हैं।

FP8: bytes घटाने का दूसरा आधा हिस्सा

fan-out आधा करने से copies आधी होती हैं। payload आधा करने से हर copy का बोझ आधा होता है। V3 GEMMs को 8-bit floating point में train करता है — अगर आपने quantisation page पढ़ी है तो पहचान जाएँगे कि यह वही तर्क है, एक octave और नीचे। दो formats हैं और अकेले कोई भी काफ़ी नहीं: 

format   exp  man     max finite   min normal   steps per octave
  e4m3    4    3            448    1.562e-02      8
  e5m2    5    2         57,344    6.104e-05      4

e4m3 के पास precision है, range नहीं। e5m2 के पास range है, precision नहीं। असली tensors को सीधे cast कीजिए और देखिए कौन मरता है: 

direct cast, one tensor, no scaling -- relative L2 error:
  tensor                     e4m3        e5m2     e4m3 finite?
  weights   (N(0,0.02))    0.310877    0.051356     True
  activation (N(0,1))      0.027098    0.053512     True
  act+outlier (x1500)           inf    0.024086     False
  grads     (N(0,1e-5))    1.000000    1.000000     True

which tensor dies first: the one with the outlier.
  max |activation| = 1,500.0  vs e4m3 max 448
  values that became inf: 1
  gradients underflow e4m3's min normal: 4096 of 4096 -> 0

4096 में से एक value 448 से ऊपर गई और पूरा tensor गया। प्रति tensor एक FP32 scale उसे वापस ले आता है — पर वह scale सबसे तेज़ आवाज़ वाली value तय करती है, और क़ीमत चुकाते हैं चुपचाप बैठे छोटे मान। छोटे blocks, ज़्यादा scales, कम मरी हुई values:

  one FP32 scale        : 0.001151   finite again

Multi-token prediction: एक forward pass, दो targets

एक सामान्य language model को हर position पर एक ही training signal मिलता है: अगला token बताओ, जैसा GPT page पर है। V3 एक दूसरा head जोड़ता है जो उसके बाद वाला token बताता है, क्रम से, पूरी causal शृंखला बनाए रखते हुए। वही forward pass, दुगुने targets. 

micro-batch: 4096 positions
  MTP depth 0 (1 head): 4,096 prediction targets per forward pass  (1.0x)
  MTP depth 1 (2 heads): 8,192 prediction targets per forward pass  (2.0x)
  MTP depth 2 (3 heads): 12,288 prediction targets per forward pass  (3.0x)

what each head predicts, for the sentence positions 0..4:
  pos 0 (the  ) -> head 1: cat     head 2: ate
  pos 1 (cat  ) -> head 1: ate     head 2: the
  pos 2 (ate  ) -> head 1: the     head 2: food

V3 depth 1 इस्तेमाल करता है — एक अतिरिक्त head. यह एक training objective है; सामान्य inference के लिए वह अतिरिक्त head हटा दिया जाता है। पर आप उसे रख भी सकते हैं, और तब वह लगभग मुफ़्त का draft model है — यानी speculative decoding, जिसमें drafter target model के भीतर ही बैठा है। Report दूसरे token की acceptance 85–90% बताती है और इस तरह इस्तेमाल करने पर लगभग 1.8× decoding throughput. 

expected tokens accepted per decoding step = 1 + p(second accepted):
  acceptance 0.85  ->  1.85 tokens/step (1.85x, before the extra head's own cost)
  acceptance 0.90  ->  1.90 tokens/step (1.90x, before the extra head's own cost)

1 + p वाला गणित मेरा है, उनका नहीं, और यह verification की लागत नहीं गिनता। 85–90% और 1.8× report के आँकड़े हैं।

Communication को compute से overlap करना

आप all-to-all मिटा नहीं सकते। आप उसे तब करा सकते हैं जब GPU कुछ और कर रहा हो — वही async call जो आप बिना सोचे लिख देते हैं। मेरी script एक 1F1B pipeline simulate करती है, 8 stages, 32 microbatches, और पूछती है कि device कर क्या रहा है। यह एक schedule की simulation है, DeepSeek की माप नहीं। 

pipeline: 8 stages, 32 microbatches, compute 1.0, all-to-all 0.8 per microbatch

  schedule            makespan   device busy   bubble
  no overlap             70.20        45.6%     54.4%
  comm hidden            39.00        82.1%     17.9%

  wall-clock penalty for not overlapping: 1.80x
  illustration only: a 56.7-day run with this shape becomes 102.1 days

दूसरा column ही घूरने लायक़ है। एक बार communication छिप गया, तो उसे और महँगा करना तब तक मायने नहीं रखता जब तक वह compute से आगे न निकल जाए: 

  comm    bubble (no overlap)   bubble (overlapped)   speedup
   0.2                31.6%                 17.9%       1.20x
   0.5                45.3%                 17.9%       1.50x
   0.8                54.4%                 17.9%       1.80x
   1.2                62.7%                 31.6%       1.83x
   2.0                72.6%                 59.0%       1.50x
वह सपाट 17.9% ही design का लक्ष्य है। communication की लागत को compute की लागत से नीचे ले आइए और वह wall clock से पूरी तरह ग़ायब हो जाती है। DualPipe मेरी simulation से आगे जाता है — वह pipeline को दोनों सिरों से एक साथ चलाता है — पर यहाँ जो मायने रखता है वह हिस्सा है जो मैं दिखा सकता हूँ: wire को गणित के पीछे छिपा दीजिए।

"abstraction layer के नीचे जाना" का असल मतलब

Report में तीन बातें हैं जिन्हें ज़्यादातर लेख छोड़ देते हैं, और वही वजह हैं कि ऊपर के तीनों उपाय ख़्वाब न रहकर सचमुच हो पाए:

उन्होंने क्या कियाक्यों
communication kernels के लिए PTX लिखा, यानी CUDA से नीचे NVIDIA की assembly-स्तर की layerdispatch/combine kernels को हाथ से tune करना ज़रूरी था. Inline asm, क्योंकि compiler वह नहीं करता
हर GPU के streaming multiprocessors का एक हिस्सा communication के लिए आरक्षित रखाComm और compute सचमुच साथ-साथ चलते हैं. आप cores का budget बनाते हैं, जैसे thread pool pin करते हैं
Tensor parallelism से पूरी तरह बचेयह सबसे ज़्यादा communication माँगने वाला parallelism है — यह हर layer के भीतर बात करता है. सँकरे link पर सबसे पहले यही हटता है

Multi-head latent attention भी उन्हीं का है, DeepSeek-V2 से: यह key-value cache को प्रति token एक low-rank latent vector में दबा देता है, जिससे long-context serving memory की समस्या नहीं रह जाती। उसका अपना पेज है — multi-head latent attention, जो KV cache page की byte-गिनती पर खड़ा है — इसलिए यहाँ मैंने जानबूझकर उसे दोबारा नहीं निकाला।

The code

Pure NumPy. No torch, no GPU, no training run. Everything is arithmetic: bytes counted, formats simulated, schedules stepped. Every function under 20 lines.

def moe_flops_per_token():
    """One token through top-8 SwiGLU experts. 3 matrices, 2 flops per MAC."""
    per_expert = 3 * 2 * D_MODEL * EXPERT_HIDDEN
    return TOPK_ROUTED * per_expert


def all_to_all_bytes_per_token(nodes_touched, dispatch_bytes, combine_bytes):
    """Bytes a single token pushes across each link type in one MoE layer.

    Dispatch: the hidden vector goes OUT to every node holding a chosen
    expert -- one InfiniBand copy per node, then NVLink fans it out to the
    GPUs inside that node. Combine: the expert outputs come back the same
    way. V3 dispatches in FP8 and combines in BF16, so the two directions
    are not the same size.
    """
    ib = nodes_touched * D_MODEL * (dispatch_bytes + combine_bytes)
    nvl = TOPK_ROUTED * D_MODEL * (dispatch_bytes + combine_bytes)
    return ib, nvl


def seconds(byte_count, bandwidth):
    """Bytes / bandwidth. This is the whole 'timing' model. No GPU was run."""
    return byte_count / bandwidth


def route(X, W_g, bias=None, k=1):
    """Affinity scores, then top-k selection. Bias shifts SELECTION only."""
    scores = X @ W_g                       # (n_tokens, n_experts)
    probs = softmax(scores)                # what the model believes
    sel_scores = scores if bias is None else scores + bias
    chosen = np.argsort(-sel_scores, axis=1)[:, :k]
    return probs, chosen


def bias_balance_step(bias, chosen, n_experts, gamma):
    """V3's replacement, in three lines. Auxiliary-loss-free balancing.

    Starved expert -> bias up. Hot expert -> bias down. Fixed step size,
    sign only, like a thermostat. Never touches the loss, so it contributes
    NO gradient to W_g -- the router keeps learning what it wanted to learn.
    """
    load = load_counts(chosen, n_experts)
    err = load - load.mean()                 # + means overloaded
    return bias - gamma * np.sign(err)


def node_limited_topk(scores, n_nodes, k, m_cap):
    """Restrict candidates to the m_cap best nodes, then take top-k."""
    n_tokens, n_experts = scores.shape
    node_id = node_of_expert(n_experts, n_nodes)
    per_node = n_experts // n_nodes
    node_score = scores.reshape(n_tokens, n_nodes, per_node).sum(axis=2)
    keep = np.argsort(-node_score, axis=1)[:, :m_cap]      # (n_tokens, m_cap)
    allowed = np.zeros((n_tokens, n_nodes), dtype=bool)
    np.put_along_axis(allowed, keep, True, axis=1)
    masked = np.where(allowed[:, node_id], scores, -np.inf)
    return np.argsort(-masked, axis=1)[:, :k]

On the maths anxiety

There is almost no maths on this page, and that is not me being kind. The spine of DeepSeek-V3 is division: bytes over bandwidth, FLOPs over throughput, compare. If you have ever sized a queue, worked out whether a job is IO-bound, or argued about payload compression, you already own the reasoning.

The two places actual maths appears, you can take on trust. The auxiliary loss has a gradient and a bias term does not — that's a one-line consequence of what "in the loss" means, and my script prints the two norms rather than deriving them. FP8's range and precision come from counting exponent and mantissa bits, which is a spec-sheet lookup, not analysis.

What this page does not give you: the actual convergence behaviour of FP8 training, the real profile of their kernels, and anything about post-training. Those need a cluster, and no amount of NumPy substitutes for one. What it gives you is the ability to say why each choice exists, which is the interview question.
